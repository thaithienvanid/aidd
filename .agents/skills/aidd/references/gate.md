# Evidence and the gate

`aidd gate` locally and `aidd gate github|gitlab` in CI run the same rules. In CI, the config comes from the base branch, and every fact comes from the platform: diff, commits, reviews, comments, the test run, and Policy. The Change Request block says only which Spec or inline declaration applies.

Decisions: `pass` (every rule holds), `pending` (waiting on a human or a runner), `fail` (something must change).

Read the gate's state from the `aidd/gate` status and its run summary (`gh pr checks <n>` on GitHub, `glab ci status` on GitLab). With no gate workflow in the repository (`aidd init --ci none`), check locally with `aidd gate --spec specs/<ID>.md`. Without a platform, `aidd gate` reads the approvals a person recorded with `aidd approve`. A local run is untrusted, so it only advises. `aidd gate --explain <rule>` says what a rule checks.

## Approvals

- Merge approval is a platform review (GitHub "Approve", GitLab "Approve") on the current head commit. Under the solo profile only, the author may instead comment `/aidd approve-merge <full head SHA>` (the earlier `/aidd approve <full head SHA>` still counts): on major, at least the cool-off after the last push.
- Spec approval is the comment `/aidd approve-spec <ID> <hash> <sha>` that `aidd hash --line` prints. The commit at its end lets the gate prove Spec approval came before implementation (required under audited). The hash covers only the Spec, its test files, its design files, and its frozen linked docs (`docs` unless `frozen: false`). So Spec approval stays valid across implementation commits.
- A command counts only at column 0 of a line of its own, in a comment never edited, outside quotes, code, and HTML comments. Never write these commands anywhere on the platform yourself.
- The authors are the PR/MR author plus every commit author and committer. Accounts in `identities.bots` are implementers and can never approve. Bots approve only when listed by name.
- A major change also needs an approval from each specialist pool its reasons name (`owners.specialists`). A pool is `security`, `data`, `privacy`, `finance`, `compliance`, or a pool a risk rule names. An unbound pool falls back to `security`. With no pool bound at all, the gate fails and says which pool to bind. Under audited, each pool also approves the Spec hash.

## Evidence file

`aidd test` writes `evidence.json` (CI uploads it from the runner's temp folder). Every result carries its `command`, `exit`, `status` (passed, failed, timeout, not_started), `red_green` (green or red), and log path. The file is bound to `head_sha` and `base_sha`. Evidence for any other commit does not count. A local run is for you. The gate reads only the artifact of the test workflow that `evidence.workflow_path` names (default `.github/workflows/aidd-tests.yml`), from a run of this change's own branch.
