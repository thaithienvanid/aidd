# CLI reference

Commands that work on a repository run from its root, wherever you start them. `--base` defaults to the remote default branch. aidd tries `origin/HEAD` first, then `origin/main`, `origin/master`, `main`, and `master`. `aidd <command> --help` prints the same flags with a sentence each.

## Which command when

Seven commands cover a normal day, and they come first. The other commands do less frequent jobs. `aidd --help` lists only the everyday commands you type yourself, the ones the README names. `aidd help --all` lists every command by group, and `aidd help <command>` shows one command's arguments and flags.

What the table cannot say:

- **`init`** writes the config, the skill, `AGENTS.md`, the CI workflows, and the PR template. It also wires [every coding agent it detects](INSTALL.md#your-coding-agent). Every profile needs someone in `owners.approvers`, or no change can merge, so every profile except `solo` needs `--approvers`. Under `solo`, init names you when you leave it out. It uses your GitHub login, found in the local configuration, or else the email your commits use. The gate starts in the profile's mode, advisory under solo and team and enforce under org and audited, unless `--enforce`.
- **`validate`** with no paths checks the whole repository, including overdue emergency reviews. It warns, without failing, when a Spec has leftover TODO placeholders, or when a normal or major Spec has no Intent. It also warns, without failing, when a major Spec has no diagram or little Design prose, no Alternatives, or no Pre-mortem. A normal Spec written from the short template, which `aidd new spec` writes without `--full`, validates with no warning once its TODOs are filled.
- **`gate --paths GLOB...`** gives a change's route before the first edit, and takes `--type`, `--dimension`, and `--irreversible` too. The gate enforces the higher of what the change touches and what its author declares ([Route](GLOSSARY.md)). It prints the route as a header with the reasons, then the lane's first step, such as "Route: normal (spec lane), needed by the planned paths (1 path)". It records nothing. On the branch, `gate` computes the route again from the real diff, and prints it with the reasons and the other branches whose Specs change the same code. Before any code, **`new spec --paths`** computes the same route, and writes it and the Task's scope. When the fast lane needs no Spec, it writes nothing, says so on stderr, and exits 1. `--force` writes one anyway. **`describe`** prints the same reasons above its block, and a local **`gate`** prints the route it computed from the diff.
- **`list`** shows all open work, with one copy of every item from the base branch and every open branch. Each item has its derived status, its next step, and who holds it. That's the agent, the author, an Approver, a triager, or a decision maker. Which change to work on is a person's choice. `--mine` keeps your own work, `--waiting-on-me` is the Approver inbox, and `--agent [ROLE]` keeps the Tasks an agent may start. `--blocked`, `--label`, and `--priority` narrow it further. `--branch` keeps only this branch's change. It shows the steps of the Specs it changes, read from the working tree, and the other branches that change the same code. Several REPO paths list a project in several repositories.
- **`list --upkeep`** lists the upkeep that is due instead of the open work. That is library standards past review, flags past `cleanup_due`, open emergency backfills, and flaky tests, read from the gate events `--events` names. It is also waivers ending within 30 days, runbooks past their drill, and doctor warnings. Each item names the command or skill that takes it. `--json` prints `{schema_version, items}`, as `schemas/upkeep.schema.json` defines it. `/aidd-team:maintain` runs it on a rhythm.
- **`describe`** prints the Change Request block for the branch's change. With `--commit`, it records the block in an empty commit on the branch, for a local land with no PR/MR description.
- **`hash --summary`** prints what the Spec hash approves on one phone screen first.
- **`gate`** runs three ways. With no platform, it is a local preflight of the branch. The preflight is untrusted because it can't see real approvals, so `--approvals` supplies a dry-run file. With `--context`, it judges a context file from any CI. With `github` or `gitlab`, it is the CI entry point that gathers a trusted context and posts `aidd/gate`.
- **`record verify`** checks an agent change record's subject, tenant, decision, and human approvals. With `--bundle` or `--online`, it checks its signature too. **`record export`** writes gate records or events as JSON or CSV.
- **`list --json`** prints `{schema_version, steps}` for scripts, or `{schema_version, repos}` for several repositories. **`standard list --json`** and **`stack list --json`** carry `schema_version` too. **`gate --paths --json`** prints `{schema_version, route, steps, overlaps}` with the same steps, as `schemas/forecast.schema.json` defines. **`gate --json`** prints the decision record of `schemas/record.schema.json`, with `schema_version` and nothing else. A Spec's step also lists its Tasks under `tasks`, each with `id`, `title`, `scope`, `depends_on`, `skills` and `role` when the Spec names them, and `status`. The `status` is `todo`, `in_progress`, `blocked` with `why` and any `waiting_on`, `stopped`, or `done`. `todo` is the one an agent may start, so a coordinator can [start one agent per todo Task](HOW-TO.md#many-agents-at-once).
- **`observe`** runs the Spec's observe command once, with the environment below. With `--window`, it runs the command every `--every` until the Spec's window ends, and stops when the rollback trigger fires. It never rolls back. With `--band METRIC SERIES`, it judges a metric series against its control band instead, and `--baseline N` values make the baseline. With `--write`, it turns a breach into a draft Spec for a person to triage.
- **`aidd explore FOLDER`** renders an exploration's comparison page into `.aidd/views/explore-<folder>.html`. The page shows the directions side by side with their trade-offs, the rounds, and a choice to copy. `aidd new exploration FOLDER --title "..."` writes `exploration.md` from its template first, and never overwrites one. Its front matter follows `schemas/exploration.schema.json`.
- **`autopilot`** runs the AIDD loop between your decisions; aidd decides each next step and stops whenever a person must decide, as [METHOD §5.3](METHOD.md#53-autopilot) says. The autopilot command starts it with `aidd autopilot start --work SPEC-1`, which prints the session id. Then, each turn, it runs `aidd autopilot next --session ID --json` and does what the action says. After that, it records the result with `aidd autopilot note "<code> <result>" --session ID`, adding `--head` with the commit the step ran on when that is not this checkout's HEAD. It ends with `aidd autopilot stop --session ID`. `aidd autopilot status` shows the lease and the journal, and `--session ID` only that session's. `aidd autopilot next --json` prints `{action, why, code, ...}`, as `schemas/autopilot-next.schema.json` defines. The action is `run` with the team command, `ask` with who decides and the decision page, or `stop` with the reason.
- **`context`** is **experimental**. `aidd context SPEC-1 --role developer` lists what a step reads, by path, with a token estimate each. It never prints a file's contents, and it never reads a path outside the repository.
- **`list --html`** writes the decision page. It holds every listed step, a person's decisions first, each with how to decide it and the command for its own page. With `--waiting-on-me`, the page holds every decision waiting on you. Like every view, it never approves.
- **`metrics --roles`** prints one row for each aidd-team role. It reads the gate events, the Specs' Tasks, the guard's log, the trunk's reverts, and `--eval-record`, an `aidd eval roles --record` file. It never reads the autopilot journal or a handoff note, because a role writes those itself. A row with fewer than 10 changes says it's too few to judge. It's display only and always exits 0. Never put a role's number into its prompt, because a measure that becomes a target stops measuring.
- **`doctor --autopilot`** checks what aidd can see of an autopilot run's settings, and prints the `permissions.allow` rules a run needs that the settings lack. It warns when a run would hold all three legs of the Rule of Two, and when `GH_TOKEN` or `GITHUB_TOKEN` holds a long-lived GitHub token (`ghp_` or `gho_`), from its prefix alone ([AUTOPILOT.md](AUTOPILOT.md#credentials-for-a-run)). It also says whether an advisor is configured in `advisorModel`, as information only. Then it lists what only you can check, such as the sandbox and the permission mode.
- **`hook`** runs one Claude Code hook. The aidd plugin and `aidd init --claude-hooks` wire them. `pre-tool` is the guard, with `agents.delegate`. `session-start` briefs the agent, `prompt-submit` adds the next step to each prompt, `stop` reminds the agent to run `aidd test`, and `pre-compact` saves the state of the work in the git directory.
- **`gen-docs`** regenerates every `aidd:gen` block in the Markdown files, the skill's references, and the domain-pack skills. With `--check` it changes nothing and fails when any is stale, or when a generated table would have no rows.

## Exit codes

<!-- aidd:gen cli:exit -->
| Command | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| `gate` (local or `--context`) | pass | fail | error | pending |
| `gate github` | posted (pass or pending; advisory always) | fail | error (an `error` status is posted) |  |
| `gate gitlab` | pass (pending with `--pending-ok`; advisory always) | fail, pending, or a stale pipeline | error |  |
| `record verify` | the change record holds and is signed (or unsigned with `--allow-unsigned`) | it does not hold, its signature does not verify, or it is unsigned | error (no such record) |  |
| everything else | success | a check failed | error |  |
<!-- aidd:end -->

A crash is always 2, never 1. [Error codes](ERRORS.md) lists every code aidd shows, from the gate's findings to the guard's denials, each with what to do.

The two CI entry points differ on pending on purpose. On GitHub, the control is the posted `aidd/gate` status, which a ruleset or branch protection requires from the gate App. The job's exit code is not the control. A pull request that waits for a person is not a failed job, so pending exits 0. A failure still exits 1 in enforce mode. On GitLab the job itself is the check a merge request waits for, so pending fails it unless `--pending-ok`. Where the platform cannot require a status, as on a private repository on GitHub Free, nothing blocks a merge on GitHub. The gate reports, and a person reads it.

## The approvals file

`gate --approvals` takes the context format, for local dry runs:

```json
{"comments": [{"user": "bob", "body": "/aidd approve-spec SPEC-1 <commit>"}],
 "reviews": [{"user": "bob", "state": "approved", "commit_sha": "<head sha>"}]}
```

One more belongs to [`install.sh`](INSTALL.md#the-cli) alone. `AIDD_REF`, in the table above, takes a `vX.Y.Z` tag or a commit SHA.
