# CLI reference

Commands that work on a repository run from its root, wherever you start them. `--base` defaults to the remote default branch. aidd tries `origin/HEAD` first, then `origin/main`, `origin/master`, `main`, and `master`, then the branch the repository's own `git config init.defaultBranch` names. Where none is there, it says so and names `git remote set-head origin --auto` and that setting. `aidd <command> --help` prints the same flags with a sentence each.

## Which command when

Four commands cover a normal day, and they come first. Your agent runs them as it works, and you can too. `aidd --help` lists only those, `aidd help --all` lists every command by group, and `aidd help <command>` shows one command's arguments and flags.

What the table cannot say:

- **`init`** writes the config, the skill, `AGENTS.md`, the CI workflow, the PR template, and each detected coding agent's ask rules ([every coding agent](GUIDE.md#every-coding-agent)). Where the team's roles run in Claude Code, `--aidd-team` also sets `worktree.baseRef` to `head` in `.claude/settings.json`, so each role's worktree starts from your current commit. It grants no permission and changes no ask rule. A value the file holds stays, and the plan says so. `aidd upgrade` adds the setting the same way, `aidd doctor` notes when no settings file sets it, and `aidd uninstall` takes it out only while it holds the value aidd wrote. It never replaces a file that exists without `--force`. `--dry-run` runs the same code in a plan that holds every write, so it changes nothing. It prints what it finds, each line a real run prints (as what it would do, a deletion included), and the config the real run writes. It checks every flag's value as a real run does. `--force` rewrites aidd's generated files and keeps every value in the config. Only a value a flag sets changes, each as a `config` line of output, shown in full with every comment it drops. A flag that names one item sets that item. `--specialist POOL=WHO` sets one pool, and `--test` sets the `unit` or `smoke` entry that init writes. `--environment` and `--own-environment` set each environment they name, and `--compliance-target` adds to the old targets. `--environment NAME=REF` says that a push to REF deploys to NAME, where REF is a branch or `refs/tags/PATTERN` and the flag repeats. `--own-environment NAME=REF` does the same for an environment only you use and writes `shared: false`, so name its branch or tag with no wildcard. `--environment none` says no push deploys, and it stands alone: init refuses it beside another `--environment` or an `--own-environment`. With neither flag, init reads your workflows (GitHub Actions and GitLab CI) for the branches and tags that start a deploy, and the job's `environment:` name. When one of them names the default branch, init writes them as `environments`, each with a comment on its file and line. Otherwise it leaves `environments` unset and says what it read, so a delegated merge stays yours. When git cannot tell the default branch, init writes none and says why. `--delegate` writes the delegation block when there is none. It keeps a block that is there as it is, because a renewal is your own edit of `review_due`, and it says so. `--environment none` refuses when the config lists environments, because dropping them could let a delegated merge pass where it deferred before. Without `--force`, init keeps the config that is there, and with `--force` it keeps the `environments` you wrote unless a flag names them. A config it cannot read back refuses the run before it writes any file. A dry run asks GitHub nothing and makes no cache folder. It shows what needs GitHub as its offline fallback. The CI pin reads `would pin the aidd workflow to the commit of the latest release`, and the Claude Code marketplace has no `stable` ref.
- **A mistake names itself.** A flag with fixed choices says which flag and which value was wrong, such as ``aidd init --ci: 'gitub' is not a choice. Did you mean `github`?``, or lists the choices when none is close. An unknown command, option, or `explain` word gets its closest match the same way, and exits 2. So does an unknown config key in `risk`, `test`, `new`, and `standard`, the commands that decide; `status`, `recall`, `explain`, and `doctor` print it first, show what they can, and exit 1. `--specialist` takes only a pool that a risk dimension asks for, which is `data`, `security`, `privacy`, `finance`, or `compliance`. `standard --list` and `records --list` say `standard list` and `records list`. `records --type` takes the types in `schemas/records.json`. A value aidd retired, such as `--change-type infra`, says what to type now, from its row of `schemas/retired-names.json`: `--change-type build --dimension availability`. Nothing is accepted and then ignored:
  - `--approvers`, `--specialist`, and `--harness` take one value each time and repeat, so a word after them is the next argument, never swallowed. A bare `@name` after `--approvers` or `--specialist` gets the way to give more. `--approvers` also splits commas, and the MCP `risk` tool refuses a qualifier beside a mode it does not go with, as the CLI does. `--paths` of `risk` takes many values because `risk` has no positional after it. `new --paths` takes many too, so `new` names the words it took when the title is missing, and the title goes before it.
  - `--harness none` says no coding agent and stands alone, as `--environment none` does. Beside a name it is an error that names both.
  - `risk` answers one mode. A qualifier goes with its modes: `--change-type`, `--dimension`, and `--irreversible` with `--paths`, `--area` with `--action`, `--branch` and `--role` with `--command` or `--action`, `--folder` with `--command`, and `--route` with `--action spec.approve`. Any other pairing is an error that names both flags, and two modes say "give only one of".
  - `standard --stack` and library ids go with `add`; without it they are an error that names `add`.
  - `init --security-ci` with no CI files to write, under `--ci none` or with no git remote, writes nothing and says so in one note.
- **An unreadable rule stops the command.** `risk --action` takes only an action aidd knows, a built-in one or one the config defines under `risks.actions`. A name that is none, such as `pr.mrge`, exits 2 and names the closest action and `aidd risk --list`. `--area` and `--role` are checked the same way, and a role a rule in force names counts as a role. A config rule that names an unknown action fails the config's load at its line; a prefix (`spec.*`) and `*` stay valid. A config that does not load stops `risk`, `test`, `new`, and `standard`, and the MCP `risk` tool, with the error and `aidd validate` as the next step, never a guess from the built-in rules alone. `status`, `recall`, `explain`, and `doctor` print the problem first, show what they can, and exit 1; the MCP `status` and `recall` tools lead with it the same way. The MCP `validate` tool returns an error that names it, with or without paths. When the config's `aidd_version` is newer than this aidd, the error adds that the config was written for that aidd. It names two ways out: upgrade aidd, or move the pin to that version. An action only a newer aidd knows still fails the load, because aidd cannot tell it from a typo. Every config error names its line where the file holds the key. An error found after `extends` parents merged, or in a parent's rule, names the file alone.
- **`status`** shows every open work item with its stored status and its next step, and who takes it: the agent, a person, or nobody, while an approved Spec waits on other work. A draft that holds no placeholder and passes `aidd validate` reads as finished, so its step is to set `ready` and ask for Spec approval. `--all-branches` does not validate a branch tip, so a draft there keeps "finish it". `--who person` keeps only what waits on a person, and `--who agent` only what an agent does next. An open exploration comes first, with its question, because a person owes its pick. `--json` lists it in `explorations`. When no open step is a person's, both end with each root blocker and the choice (`--json` carries the line as `root_blocker`), such as "SPEC-1 blocks 23 Specs: finish it, or choose a Spec to specify". `--delivery-team <name>` keeps only one delivery team's work, from the config's `delivery_teams`: its Intents, their Specs, the Specs whose `delivery_team` names it, and the Specs whose Task scope touches its areas. With `--json`, an item may also carry `owner`, `delivery_team`, `teams_in_scope`, `waiting_on`, `blocked_by`, `tasks`, `emergency` (only when it is whole), `last_test_run`, and `unsaved`, and a step may carry `person`, `words`, and `why`; the answer lists the config's `delivery_teams`. `waiting_on` is the Spec's own text. `blocked_by` lists the items it still waits for, read now, so it can differ from the `blocked_by` the Spec stores. `unsaved` names the paths nobody committed yet on the branch for that item, such as `spec/SPEC-1`. `handoff` gives where the work stopped, from the note in the last commit's message. It shows on a branch of your own whose Spec holds no note. For a `batched` Intent, with an id or without, one line says its Merge approval for `intent/<ID>` is pending until that branch lands on the default branch (`intent_branch_state`: `pending`). Each Spec then says where its `spec/<ID>` branch stands (`spec_branch_state`). It says "nothing left to merge into intent/<ID>" (`merged`) or "waits to merge into intent/<ID>" (`unmerged`). When a branch is missing, it says which one and what to do (`missing`, `remote_only`, `invalid_name`, or `intent_branch_missing`). A Spec merged into the Intent's branch is `done`, yet the Intent stays open, and nothing is shipped until its branch lands. Git is read again on each run, and nothing is stored. `--html` writes the work-items page to `.aidd/views/status-work.html`, or to `status-work-<team>.html`, `status-work-all-branches.html`, or `status-<ID>.html` for a filtered run, so no run overwrites another. With an id, it shows that item even when it is finished.
- **`status <path or id>`** shows what stands behind a path, a Spec, or an Intent, after a work item's status and history. That is the Specs whose Task scope covers it, the open Specs whose scope overlaps it, and their tests, docs, and interfaces. It adds the route from `risk --paths`, and the last commits with their work ids and `Assisted-by` trailers. For a work item, it also lists the work that shares its `trace_id`. It reads git and the work items' files on demand and stores nothing. `--commits N` reads at most N commits (1 to 100, default 20), and says it does nothing with no id, or with a proposal's. For a path, `--json` follows `schemas/trace.schema.json`. For a Spec or an Intent, it follows `schemas/status.schema.json`, with the trace nested as `trace`.
- **`risk --paths`** gives a change's route before the first edit, and the level of editing those paths. The route reads the paths, each risk dimension declared with `--dimension`, which raises it as an area's dimension does, and `--irreversible`. The change type never raises it. The next step, `aidd new spec`, carries each declared dimension and `--irreversible`, so the Spec takes the same route. Without `--paths`, `aidd new spec` takes the route they give when it is above `--route`. `aidd validate` refuses an open Spec whose `route` is below the route its `risk` gives, and warns about an ended one. In a subfolder, a relative path reads from there and from the repository's top, as `git diff --name-only` prints it, and the stricter reading routes, with a hint when they differ. A folder keeps its trailing slash, even when typed without one. A glob or a folder stands for every tracked file under it, so a risky file anywhere inside raises the route. The JSON lists at most 50 paths of each area, unless `limits.max_paths_shown` sets another, in `areas[].paths`, gives the full count in `areas[].path_count`, and names in a hint how many an area left out. The route and the edit level come from every path. A link reads as typed and also where it leads, and the stricter wins. A path outside the repository, or an empty one, is an error. `status <path>` and `new spec --paths` read paths the same way. **`risk --command`** gives the level of a shell command line, reading the branch a `git push` reaches from git. A `git merge` that lands other work, or a `git pull` with any word that is no option, is `git.merge`, so it asks while the default branch is checked out, and is allowed on your own branch. `pr.merge`, a PR/MR merged into its base, asks on any branch. A listing, a preview the tool documents as sending nothing, or a request for help reads `allow` when it is one of the forms in `read_forms` and `help_forms` of `schemas/risks.json`, such as `git tag -l`. A note says so. Anything else on the line keeps the action's level. A write to a file is an edit of it. That covers the target of a redirection, such as `>`, `>>`, `>|`, `<>`, `&>`, or `2>`, and the file a writer names. The writers are `tee`, `cp`, `mv`, `install`, `ln`, `sed -i`, `perl -i`, `dd of=`, `truncate`, `rm`, and `unlink`, listed in `code.edit`'s `file_writes` in `schemas/risks.json`. The command gets the level `risk --paths` gives that file, or its own level when that is higher, and a note names the file. A relative path reads from the folder the command was typed in, and no `cd` is followed. After a word that may change the folder, such as `cd`, `pushd`, `popd`, `env -C`, `sudo -D`, or a command word the shell expands, the path reads by its name alone, as the strictest file or area glob that guards that name. A subshell changes the folder only through such a word inside it. A bare name that only a folder-wide area guards raises nothing, and a note names the file. A copy or a move of a folder reads the folder it lands in as `risk --paths` reads that folder. A device (`/dev/null`), a file under the system's temporary folder, and a file in aidd's own output folders (`.aidd/*/`) that git ignores are no edit. A path outside the repository counts only when an area names it with a glob that starts with `/`. A word the shell expands, such as `$LOG`, `$(...)`, a glob, or a brace, is left unchecked, and a note says so. SECURITY.md lists the limits. `--folder <path>` reads the branch in the folder the command runs in, when that is not this one; a folder that is no git checkout, or does not exist, says so in a note. A push reads as its words say. A setting that may send a push elsewhere only raises it. If `remote.<name>.push` is set or `remote.<name>.mirror` is true for the remote it goes to, or `push.default` is `upstream`, `tracking`, or `matching`, the push reads as one that may reach the default branch, with a note. A push that names a `<src>:<dst>` for every refspec is not raised by `remote.<name>.push`. A `-c` or `--config-env` on the same git command whose key starts with `remote.`, `push.`, `branch.`, `include.`, or `includeIf.` raises it too, whatever its value. A `git checkout` or `git switch` earlier on the line is read beside the branch checked out, for every action a rule makes branch-dependent. A `*` in a refspec reads as every branch. The note says how to see the settings. A branch aidd cannot read, such as a detached HEAD, reads as the strictest level over branches. That holds for every action with a rule that names a branch, as with `--action` and no `--branch`. A branch it read gives that branch's level. A command reads as a POSIX shell reads it, so a program by its Windows name (`git.exe`, `C:\Git\bin\git.exe`) matches no action. A command that no action matches gives `allow` with a note that no rule gave it, in the text and in `notes` of the JSON. Outside every git repository, the branch is unknown, so a command that turns on the branch asks, and a note says to run it inside the repository the change touches. A reader such as `cat`, `grep`, or `source` on a file that holds secrets, from its own list in `schemas/risks.json`, such as `cat .env`, is `secret.use`, which asks, while an example file such as `.env.example` stays allowed. **`risk --list`** shows every rule in force and where it comes from, whether the built-in rules, the profile, or the config. Each answer is advice. aidd enforces nothing, and a command pattern is a net, not a control. `risk --list` prints every rule in force. A `lock:` line then names the narrower rules each locked rule raises, and says it lowers none.
- **`recall WORD ...`** searches what the team already wrote: the records, the Specs and the documents in their folders, the ADRs, the glossary, the product brief, the improvement log, and the last 1000 commit subjects. It shows each line that holds every word, with its file and line, a record's id, or a commit's short sha. A record that `aidd records pull` added is another clone's words, so its match says `pulled` (`"pulled": true` in `--json`). Dated matches come first, newest first. Each word matches the start of a word, through SQLite's full-text search in the index. Where SQLite has no full-text search, it matches the word anywhere in a line. A file over 256 KiB or a link is skipped and named. It is a cache of the files: never a source of truth, never evidence, never a yes. `--limit N` shows at most N matches (1 to 200, default 20), and `--json` follows `schemas/recall.schema.json`.
- **`test`** runs the repository suite and the Spec's commands on the head, and each new-behavior command on the base too, where it must fail. `--changed` runs only what the working tree's changes select, green only, and marks the evidence partial. It is a quick check between steps. A config command with `related_tests` runs only the tests its runner relates to the change, when the runner sees every changed path the command covers, and in full otherwise. A command that names `report: <path>`, a JUnit XML file it writes, adds its failed test cases to its result in the evidence. A missing, stale, or unreadable report is a finding, and the exit code stays the evidence.
- **`validate`** with no paths checks the whole repository, including overdue emergency reviews. It warns, without failing, when a Spec, a document it links, or a repository document from `aidd new` has a leftover placeholder (TODO, `YYYY-MM-DD`, or an id such as `SPEC-?`). It also warns when a normal or major Spec has no `## Request` section with content. A planned Spec, a draft whose every Task still holds a placeholder, gets a note instead, because Specify fills it in. A note never fails the run, and `--json` lists notes in `notes`. It also lists every error, warning, and note as a finding in `findings` (see [Problems in `--json` output](#problems-in---json-output)).
- **`explain WORD`** says what one of aidd's words means and why it matters, read from the file that owns it. It knows the actions and areas of the risk rules in force, the three levels (`allow`, `report`, `ask`), and the routes, and the word for each type, such as `action`, `level`, and `profile`. It also knows the loop steps, the decisions a person makes, the roles, the document types, the statuses, the profiles, the finding codes of `schemas/findings.json`, such as `validate.warning`, and the step codes `aidd status` gives, such as `spec.draft`. A reason code that `aidd delegate check` prints without its group, such as `delegation_review_due`, answers as the one code it names. A word of two types, such as `Plan`, gets both. `--list` lists every word it knows, by type. An unknown word exits 2, names the closest word when one is close, and points to `--list` and `aidd recall`. With `--json` it still prints an empty `matches`, and adds the error object under `error`. `--json` follows `schemas/explain.schema.json`.
- **`explore FOLDER`** renders an exploration's comparison page into `.aidd/views/explore-<folder>.html`. The page records nothing and approves nothing: the owning role writes the pick and its reason.
- **`gen-docs`** regenerates every `aidd:gen` block in the Markdown files, the skill's references, and the domain-pack skills. With `--check` it changes nothing and fails when any is stale, or when a generated table would have no rows.

## Scripts on `aidd status --json`

`aidd status --json` follows `schemas/status.schema.json`, and its `schema_version` changes only when a field changes meaning. Each next step has a stable `code`, such as `spec.approve`, so a script matches the code, never the sentence. These four `jq` recipes answer the common questions:

```sh
aidd status --json | jq -r '.items[] | select(.next.who == "person") | "\(.id)\t\(.next.what)"'   # what waits on me
aidd status --json | jq -r '.items[] | select(.next.code == "spec.blocked" or .next.code == "spec.blocked_by") | .id'   # what is blocked
aidd status --json | jq -r '.due[] | "\(.path)\t\(.what)"'   # what is past due
aidd status --json | jq -r '.items[] | select(.id == "SPEC-3") | .next.what'   # one Spec's next step
```

## Problems in `--json` output

`aidd validate --json`, `aidd doctor --json`, and `aidd status --json` print `findings` beside the lists they always printed. A finding has a `code`, a `severity` (`error`, `warning`, or `note`), a `message`, a `next` step, and a `path` when the message opens with a file of the repository. A script matches the code and the severity, never the message. Each line of `errors`, `warnings`, and `notes` is the message of one finding, so the two never disagree. `aidd doctor` gives a finding for each check that failed or warned, and `aidd status` for a config that does not load, a work item it cannot read, and each entry of `due`.

The codes stand for a kind today, such as `validate.warning` or `doctor.check_failed`, because the checks do not carry codes of their own yet. `aidd explain <code>` says what a code means and what to do. `schemas/findings.json` holds every code, and the schemas of the three outputs name the shape.

```sh
aidd validate --json | jq -r '.findings[] | select(.severity == "error") | "\(.path // "-")\t\(.message)"'   # what fails the run
aidd explain validate.error   # what a code means
```

A `--json` command that stops with exit 2 prints one error object on stdout: `{"schema_version": "1", "error": {...}}`, where `error` is a finding whose `code` starts with `cli.` (or is `config.unreadable` for a config that does not load). The words for a person go to stderr as before, and the exit code stays 2. A command line the parser refuses prints the object too, when `--json` is among its arguments. `aidd explain` for an unknown word keeps its empty `matches` and adds `error`. An MCP tool returns the same object when it fails, with its message in the words of the tool's arguments: `change_type` where the command says `--change-type`.

## Environment variables

aidd reads three kinds of variable, and this section lists each one. The first kind is the variables aidd defines, all named `AIDD_*`: aidd keeps their names and meanings. The second kind is the variables another tool or the platform defines, which aidd reads for one job each. The owner decides a name and its value, so a minor release may read one more or stop reading one. The third kind is the variables aidd reads only to tell where it runs, a CI platform's or a coding agent's. aidd lists their names and promises nothing about them. A test fails when the code reads a variable that none of the three lists.

<!-- aidd:gen cli:env -->
The variables aidd defines:

| Variable | Read by | Meaning |
| --- | --- | --- |
| `AIDD_OFFLINE` | every command that loads the config, and `aidd self-update` | `1` stops every optional network call: `extends` parents by URL are skipped with a warning, no update check runs, and `aidd init --claude-plugins` wires the repository instead |
| `AIDD_ORG_PRESET` | every command that loads the config | the path of an org preset, read as the first parent of every config |
| `AIDD_DEBUG` | every command | `1` prints the traceback of an error to stderr; a crash then asks you to report it |
| `AIDD_AGENT` | `aidd self-update`'s daily check | any non-empty value tells aidd an agent runs the shell, so the daily update check stays off |
| `AIDD_UPDATE` | every command a person runs at a terminal | the daily check for a newer release: `off` runs none, `notify` (the default) says one is out, `install` installs it, verified |
| `AIDD_REF` | the one-line installer | the release tag or commit to install, such as `v1.0.0` |
| `AIDD_WORKTREE` | your test commands (set by `aidd test`) | the worktree's folder name as a slug, so a project can name its test database by it |

The variables another tool or the platform defines, which aidd reads:

| Variable | Read by | Meaning |
| --- | --- | --- |
| `CDPATH` | `aidd risk --command` | when set, a relative `cd` target is not resolved, because the shell may find another folder first |
| `CLAUDE_CODE_PLUGIN_CACHE_DIR` | `aidd self-update` | where Claude Code keeps its plugin cache, to tell a plugin copy from a checkout |
| `CLAUDE_CONFIG_DIR` | every command that reads Claude Code's user settings | Claude Code's user folder, instead of `~/.claude` |
| `CLAUDE_PROJECT_DIR` | `aidd mcp`, the delegate hook | the project folder Claude Code sets for its hooks and MCP servers, which also marks a Claude Code session |
| `GITHUB_TOKEN` | `aidd eval standards --online`, `aidd self-update` | a read-only GitHub token, for a higher rate limit; never required |
| `GH_TOKEN` | `aidd eval standards --online`, `aidd self-update` | the same, when `GITHUB_TOKEN` is not set |
| `GIT_CONFIG_COUNT` | every command that runs git | the number of config pairs your environment already gives git, so aidd's own pairs follow yours |
| `PATH` | `aidd init` | where it looks for the coding agents' programs |
| `SOURCE_DATE_EPOCH` | the build of the `.pyz` file | the time stamp of every file in it, so a build is the same twice |
| `XDG_CACHE_HOME` | every command run from the `.pyz` file, and the daily update check | the folder of aidd's cache, instead of `~/.cache` |
| `XDG_DATA_HOME` | `aidd self-update` | the folder of aidd's own virtual environment, instead of `~/.local/share` |

The variables aidd reads only to tell where it runs, as a CI platform or a coding agent's shell sets them: `CI`, `CI_JOB_ID`, `CI_JOB_URL`, `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`, `GITHUB_ACTIONS`, `GITHUB_HEAD_REF`, `GITHUB_REPOSITORY`, `GITHUB_RUN_ID`, `GITHUB_SERVER_URL`, `GITLAB_CI`, `AI_AGENT`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDECODE`, `CODEX_SANDBOX`, `OPENCODE`, `ANTIGRAVITY_AGENT`.

Stripped from the environment of every test command: `GITHUB_TOKEN`, `GH_TOKEN`, `AIDD_GITLAB_TOKEN`, `CI_JOB_TOKEN`, `ACTIONS_RUNTIME_TOKEN`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`.
<!-- aidd:end -->

One more belongs to [`install.sh`](GUIDE.md#install) alone. `AIDD_REF`, in the table above, takes a `vX.Y.Z` tag or a commit SHA. A tag installs that version's wheel from its GitHub Release, once the wheel matches the release's `SHA256SUMS`. `AIDD_SHA256`, when set, must match too. `AIDD_RELEASE_URL` points the installer at a mirror of the releases, which needs `AIDD_SHA256` or `gh` too. A commit SHA builds from source, for testing unreleased code only. With no `AIDD_REF` and no release yet, the installer resolves `main` to one commit and builds from source there, and says it is unreleased and unverified.
