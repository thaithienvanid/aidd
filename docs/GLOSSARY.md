# Glossary

| Term | Meaning |
| --- | --- |
| Advisory mode | `mode = "advisory"` in the config, or the gate workflow's input `mode: advisory` when the config sets no mode: the verdict is posted on `aidd/gate (advisory)`, which never blocks a merge. For rollouts. |
| Agent | An AI system that edits code. An implementer, never an Approver. |
| Agent role | One of the optional aidd-team roles ([TEAM.md](TEAM.md)): a subagent guided to write only its own files. Never an Approver. |
| AIDD | AI-Driven Development, the method: the loop, the routes, the two approvals, the objects, and the profiles. Capitals when it means the practice: the AIDD loop, an AIDD Spec, an AIDD delivery team. |
| aidd | The software: the CLI and Python package, the `aidd` and `aidd-team` plugins, the skill, the `.aidd/` directory, the `aidd/gate` status, and the release number. Lowercase always, even at the start of a sentence. |
| aidd-team | The optional plugin that runs the loop with a cross-functional delivery team of agent roles, led by humans ([TEAM.md](TEAM.md)). |
| `aidd/gate` | The required status the verifier posts. Green means every rule holds. *Avoid:* calling a person's decision a gate. "The gate" means this status and the verifier behind it; a person gives an approval, which the gate checks for but never makes. |
| Approval hash | The Spec hash a Spec approval names: `aidd hash specs/<ID>.md --comment` prints the approval line that carries it. See Spec hash. |
| Approver | A person in `owners.approvers`, eligible to approve a Spec or a change. Not an author (except solo). *Avoid:* "reviewer" for an Approver. The reviewer role is an agent that writes findings and never approves. |
| `assisted_by` | The `harness/model` values of every agent that wrote code or tests. It must be non-empty whenever a commit names an agent (an `Assisted-by:` trailer, a `Co-authored-by:` agent, or a bot author); under regulated, every commit carries a trailer (`Assisted-by: none` when no agent wrote it). |
| Author | The people accountable for a change: the PR/MR author plus every commit author and committer. They cannot approve their own change, except under solo. |
| Autonomy stage | What `aidd metrics --autonomy` suggests for an agent and a kind of change, from its gate events: review every change, review the trade-offs, or candidate standard change. A person decides whether to act on it. |
| Blast radius | Who or what behaves differently if the change is wrong. Recorded as `risk.summary` and `risk.dimensions`. |
| Brownfield | Adopting aidd in an existing codebase: advisory mode first, the real layout mapped, characterization where tests are thin. |
| Budget | The most changed lines a route allows (`max_changed_lines`, per profile in [METHOD.md §9](METHOD.md#9-profiles)), excluding `budget_exclude_paths` and, for a Spec, the Spec and the files Spec approval froze. |
| Change Request | The PR/MR. Its description holds one `toml aidd` block (see that row). *Avoid:* "PR" alone in text meant for every platform: say PR/MR. |
| Change record | `change-record.intoto.json`, which `aidd gate --record` writes beside the gate record: an in-toto statement of the decision whose subject is the head commit, with the tenant, the route, each approval, the red and green exit codes, and the finding codes ([METHOD.md §7](METHOD.md#change-record)). Unsigned unless the gate workflow signs it; `aidd verify` checks it. *Avoid:* confusing it with the gate record (`aidd-record.json`), which holds every rule's result. |
| Characterization | Pinning today's behavior with a test before changing code that has none. |
| Context (verifier) | The facts an adapter collects for the verifier: diff, commits, reviews, comments, evidence, policy. |
| Control band | The range `aidd watch` expects a metric in: its recent baseline plus or minus a number of standard deviations (2 lets an agent diagnose read-only, 3 lets it propose a change as a draft Spec). Set per metric in `[[observe.bands]]`. |
| Cool-off | Minutes that must pass after the platform first saw the head commit before an approval counts (`cooloff_minutes`); 30 on major under solo ([METHOD.md §8](METHOD.md#solo)). Locally there is no platform time, so it starts at the head commit's committer date, which the committer sets: a reminder, not a control. |
| Day 0 | A new repository's first commit: the aidd setup and the project scaffold, committed straight to the default branch as the baseline every later change is gated against. |
| Delivery team | The aidd-team roles together: product, design, architecture, security, compliance, testing, software, AI, data, and platform engineering, documentation, verification, review, reliability, and process improvement, each an agent limited to its own files; humans hold every decision. |
| Design direction | One of two or three rough, low-fidelity takes on the same brief that the product designer offers before any detailed prototype. A person picks one, recorded in the Spec's `## Design` section with who, when, and why; only then is it built in detail. *Avoid:* "approving" a direction: picking one is a recorded decision, and the design is approved only at Spec approval. |
| Design files | `design.files` in a Spec: the prototype, its `DESIGN.md` and tokens file, the flow diagram, and the rough directions, which Spec approval freezes with the tests. Never implementation scope, and never imported by product code. *Avoid:* "mockups" for the whole set: a mockup is one kind of design file. |
| Dimension | A kind of blast radius in words any role uses: `data`, `security`, `privacy`, `financial`, `compliance` (force major and name a pool), `availability`, `third_party`, `cost` (rule out minor). |
| Domain pack | A skill (`aidd-team:<pack>`) generated from `schemas/roles.json` for one domain: its standards with editions and checked dates, a checklist per loop step, and executable checks for the Spec's tests. Loaded on top of a role for every domain a change touches. |
| Domain expert | A person who knows one business area deeply (payments, clinical safety, tax, a regulator's rules). In aidd, a member of a named reviewer pool in `owners.reviewers` that a risk rule sends changes to, so a major change in that area needs their approval ([Adoption](ADOPTION.md#domain-experts-as-reviewers)). Always a person, never an agent role. |
| Edit-time guard | `aidd hook pre-edit` and the MCP `check_edit` tool: allow or deny, never a mid-build prompt: deny edits outside the active Spec's `scope`, a test or design file once Spec approval froze it, and a protected path outside an approved scope, each deny naming its route. A local guide; the gate decides. |
| Emergency | The route for a production repair: allowed under a freeze, needs smoke tests, a named human commander, a committed backfill Spec, and a review by `review_due`. |
| Epic, Initiative | Optional containers above Specs. |
| Evidence | `aidd-evidence/evidence.json`: exit codes per command and phase, bound to the head SHA. *Avoid:* calling a pasted log, a screenshot, or an agent's statement evidence. Model prose is never evidence ([METHOD.md](METHOD.md)); a log counts only as the test runner recorded it. |
| Extension | A skill, plugin, MCP server, or tool a team role loads on top of its packs; listed per role in `schemas/roles.json` as starting points, verified and pinned, and installed through a change. |
| Flow | The roles a team command runs, in order, with the groups that run in parallel and the human decision it stops at; data in `schemas/roles.json`, and each command is tested against it. |
| Freeze | A Policy answer that stops every route except emergency. *Avoid:* "freeze" for what Spec approval does to test and design files: say they are frozen by Spec approval, not under a freeze. |
| Gate record | `aidd-record.json`, written by every gate run: the decision, each rule's result, and the approvals, evidence, and agents it counted. Validated against `schemas/record.schema.json`; what each field evidences is in [CONTROLS.md](CONTROLS.md#what-the-record-evidences). |
| Go/no-go | The first human decision on a Proposal: pursue it or not, recorded in `go_no_go` before the team drafts. |
| Goal | `goal` in the config: the team's current measurable target, one sentence the humans agree on, that every agent steers by when a choice is open. It sits under the mission and changes when the target does. |
| Greenfield | Adopting aidd in a new repository: Day 0, then a first Spec that brings the test runner and the first test. |
| Handoff note | The four lines every team role ends a run with: Done, Next, Needs, Stopped at. The next role reads it before the file. Written into the Spec or the PR/MR as a fenced `aidd-handoff` block of TOML (`done`, `next`, `needs`, `stopped_at`, optional `spend`), which `aidd next` reads to name the role that has the work and to surface Needs to a person. Never evidence; the Spec approval hash leaves it out. |
| Harness | The program that runs a coding agent and its tools: Claude Code, Codex, Cursor, Copilot, and the others `aidd init` wires ([INSTALL.md](INSTALL.md#your-coding-agent)). An `Assisted-by:` trailer names it with the model, as `harness/model`. |
| Head SHA | The commit at the tip of the change. Evidence and approvals bind to it. |
| Hypothesis | A Spec field, frozen by Spec approval: the metric a change should move, its baseline, the expected move, and by when. Learn records `outcome.result` against it; a miss is a product decision, not a rollback. |
| Human feedback | The paths on which a person sends work back: Spec approval with changes requested to Specify, Merge approval with changes requested (or a review comment) to Implement, Ship's incident, rollback, or missed hypothesis to Learn, and Learn's lesson to Plan as a new change. Dashed in the loop diagram. |
| Implement | The loop step where the change is built, one Task at a time, inside its scope, checked at every edit; it loops with Verify until the head is green. |
| Implementer | Whoever writes the change: usually an agent, directed by the author. Never an Approver of their own work. |
| Incident commander | The human named in an emergency block who runs the incident. An eligible Approver, not an author, and must approve the repair. |
| Inner loop | Autonomous agentic execution: Specify, Implement ⟲ Verify, Review. The agent drafts the contract in Specify, Spec approval freezes it, and the agent then works inside it, bounded by the Task's scope, red-then-green, and three retries. |
| Label | One of up to eight lowercase tags on a Spec, Epic, or Initiative (`labels = ["area:billing"]`), for filtering with `aidd next --all --label`. It never changes the route or the gate, and the Spec approval hash ignores it. |
| Lane | The path through the loop that follows from the route: fast (minor, standard), spec (normal, major), or emergency. *Avoid:* "route" for the lane. The route is how much control a change gets; the lane is its path through the loop. |
| Learn | The loop step after Ship, run on a signal (a Merge approval rejection, a rollback, an incident, three failed retries) and on a cadence (the retrospective). Each lesson becomes a change to tests, rules, or agent instructions, linked in `outcome.learn_ref`. |
| Local approval | A Spec approval or Merge approval a person records on their own machine, with no platform: `aidd approve spec` or `aidd approve merge`, a commit on the private ref `refs/aidd/approvals`. Weaker than a platform's approval ([METHOD.md §8](METHOD.md#local-approvals)). |
| Loop version | `loop.version` in `schemas/roles.json`, semantic versioning: adding, removing, or reordering a step, a human approval, or a lane bumps the major number. Gate events carry it as `loop_version`. |
| Major | A route computed by the gate: a protected path, a major dimension, an irreversible change, or a major type. Normal plus specialist review, an observe block, and stricter profile gates. |
| Maturity | `established` (the default) or `emerging`, on every standard and extension in the registry. Emerging means a draft, a first edition, a pre-1.0 release, a community extension, or a practice adopted by few: a role applies it only when the change clearly needs it, and says so in the Spec. |
| MCP server | `aidd mcp`: aidd's checks as agent tools over the Model Context Protocol. |
| Merge approval | A human's approval of what was built: the exact head commit, as a platform review (solo also: `/aidd approve <full head SHA>`). Rule `merge_approval`. *Avoid:* "sign-off" for it, and calling the reviewer role's findings an approval: only a person's approval of the head commit lets the change merge. |
| Minor | A small, reversible change with no Spec file: an inline block with `route`, `type`, and `assisted_by`; the changed paths are its scope unless it declares one. |
| Normal | The route for a change that needs a Spec but touches nothing major: Spec approval before the code (from the team profile up; under solo only major needs it), frozen tests, red-then-green, and one Merge approval. It takes the spec lane. |
| Mission | `mission` in the config: the team's enduring purpose, set by humans, which changes rarely. The goal is the current measurable target under it. `aidd next` opens each Spec's why chain with it, and the session-start hook briefs the agent with both. |
| Observe window | `observe.window` in a Spec: how long after release the change is watched, with the command or signals that judge it and the `rollback_trigger`. Required on major, and on normal under regulated; `aidd observe` runs the check once. |
| Org preset | A config the platform team owns, applied as the root parent of every repository config (`org-preset-url` on the reusable workflow, or `AIDD_ORG_PRESET`). Repositories can only tighten it. |
| Outer loop | Human strategy and governance: Plan, Ship, Learn, and the two approvals. An agent drafts all of it and decides none of it. |
| Plan | The optional step before the loop, for work bigger than one Spec: an Initiative, Epics, and ranked Spec stubs that a human agrees to. *Avoid:* "approve the plan": a person agrees to it. aidd keeps "approval" for Spec approval and Merge approval. |
| Policy | An optional command, run from the base branch without tokens, that can hold or stop a change (freeze calendars, deny lists). |
| Pool | A named group of specialist reviewers in `owners.reviewers`: `security`, `data`, `privacy`, `finance`, `compliance`, or any name a risk rule uses. A major change needs an approval from each pool its reasons name; an unbound pool falls back to `security`. |
| Practice skill | A hand-written skill (`aidd-team:<name>`) for one kind of work (API design, schema migration, threat modeling, test design, secure coding, and more): its standards, steps per loop step, test commands, and handoff, with a checked date. Each role lists its own; a Task names up to two in `skills`. |
| Proactive role | An agent role listed in `[agents] proactive_roles`, allowed to propose work nobody asked for, and only as a draft Spec. |
| Profile | solo, team, org, or regulated. It sets gate strictness. |
| Proposal | A case put to someone outside the team who decides, before any code: a bid or pitch to a client, or a change put to the company's leadership. It holds the needs and how each is answered, options, a range estimate, assumptions, exclusions, risks, and questions; accepted, it becomes an Initiative ([METHOD.md §4.7](METHOD.md#47-proposal)). |
| Protected path | A path whose change is always major: aidd's config, CI, CODEOWNERS, agent instructions and skills, MCP config. |
| Red-then-green | A new-behavior test fails on the base commit and passes on head. |
| Relation | A typed link from a Spec, Epic, or Initiative to another (`blocks`, `blocked_by`, `duplicates`, `relates_to`, `implements`). `aidd validate` checks the target exists and that blocks form no cycle; `aidd next` shows work blocked_by unfinished work as blocked. The gate never reads it. *Avoid:* confusing it with a Task's `depends_on`, which orders Tasks inside one Spec. |
| Retrospective | The Learn step on a cadence: the loop inspects its own metrics and proposes at most three measured improvements, each re-entering the loop at Plan as a new change ([METHOD.md §12](METHOD.md#12-ship-and-learn)). |
| Review | The loop step between Implement and Merge approval: the PR/MR is ready and findings, human or agent, are answered. |
| Role eval | A scenario with a seeded defect sent to one team role (`aidd eval roles`), scored on what the role must find and must not do. |
| Route | standard, minor, normal, major, or emergency: how much control a change gets, computed from its paths, type, and risk; the lane follows from it. Every change starts with `aidd next`, the loop's entry rule, not a step: it computes the minimum route (before any code, `aidd new spec --paths` does), and the gate recomputes it from the real diff and can only raise it. The names follow ITIL change types. |
| Scope | The globs a Task's diff may change (`tasks[].scope`, or `scope` in an inline block). |
| Separation of duties | The rule that authors and agents cannot approve their own change. Waived and recorded under solo, where the Approver must still be in `owners.approvers`. |
| Ship | The loop step after Merge approval: merge, release, and the observe window, ending when it passes or the rollback trigger fires. |
| Sign-off | The second human decision on a Proposal: it may be sent, with its price, commitments, assumptions, and exclusions. *Avoid:* "sign-off" for a Spec or a merge. It belongs to a Proposal only; say Spec approval or Merge approval. |
| Signer workflow | `evidence.signer_workflow`: the central test workflow whose artifact attestation the gate requires on evidence. |
| Skill | A folder in the Agent Skills format (a `SKILL.md` and its references) that an agent loads by name. The `aidd` skill (`.agents/skills/aidd/`) tells any coding agent how to work in the loop; the delivery team adds domain packs and practice skills. |
| Spec | `specs/<ID>.md`: what, why, scope, acceptance, tests, rollback. |
| Spec approval | A human's approval of what will be built: the Spec with its frozen test and design files, bound to their hash. Posted as `/aidd approve-spec <ID> <hash> [<commit>]`; the commit is required under `spec_approval_proof = require` (regulated). Rule `spec_approval`. *Avoid:* "sign-off", "design approval", or "the design gate". The design files are approved only as part of Spec approval, and a person approves; the gate only checks that it happened. |
| Spec hash | A 32-hex (128-bit) SHA-256 prefix over one canonical JSON document of the Spec's stable fields, its body, and the blobs of its test and design files. The Spec approval covers exactly this. |
| Specialist reviewer | A person in a pool in `owners.reviewers` (security, privacy, data, or a domain expert's pool), whose approval a major change needs from the team profile up. *Avoid:* confusing them with the reviewer role, an agent that writes findings and never approves. |
| Specify | The loop step that writes the Spec and its tests before any code exists. It ends at Spec approval. |
| Standard change | A pre-approved change class (such as a bot patch bump) that merges on green tests with no human approval. |
| Standards registry | Every standard a role or a domain pack applies, with its edition, the date it was last checked, and its source, in `schemas/roles.json`. `aidd eval standards` fails on an entry older than a year. |
| Status group | One of five groups every status falls into (backlog, unstarted, started, completed, cancelled), the same for Specs, Epics, Initiatives, and proposals, so a board or a tracker mirrors any object by its group ([METHOD.md §5.1](METHOD.md#51-status)). |
| Task | A slice of a Spec with its own `scope`. |
| Tenant | `tenant` in the config: the company, or an agency's client, a repository belongs to. An org preset sets it and may lock it; it is stamped on every gate record, event, and change record, and an approval by another tenant's identity (`<tenant>:<login>`) never counts ([Enterprise readiness §13](ENTERPRISE.md#13-multi-tenancy)). |
| Test runner | The `aidd-tests` job: runs the tests on head (green) and base (red) and uploads the evidence. It runs the change's code, so it has no secrets. |
| Tests | The commands whose exit code proves acceptance (`tests.commands`) and the files they run through (`tests.files`). Written before Implement, frozen by the Spec hash. |
| `toml aidd` block | The one fenced block in a PR/MR description that tells the gate about the change. On normal and major it names the Spec (`spec = "specs/<ID>.md"`), which supplies the rest; a minor, standard, or emergency change declares inline its `route`, `type`, `assisted_by`, and, when it wants one, its `scope`. `aidd change` prints one. The gate recomputes the route from the diff and can only raise it. |
| `trace_id` | An identifier shared by every Spec, PR/MR, and event of one piece of work, across repositories. |
| Triage | A person's decision on work an agent proposed on its own (`proposed_by = "agent:<role>"`): accepted, declined, duplicate, or snoozed until a date, recorded as `triage` in the Spec. Until then the Spec stays a draft; `aidd validate` fails one past draft without it, or with a triage an agent recorded. |
| Type | The kind of change, in Conventional Commits vocabulary: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `deps`, `infra`, `data`, `security`, `compliance`. |
| Unlinked author | A commit author the platform cannot map to an account (`email:`); it might be an Approver, so the gate warns or fails. |
| Verifier | `aidd gate`: a pure function from context to pass, pending, or fail. Not to be confused with the `verifier` role of the delivery team, an agent that acts in Verify and whose report is never evidence. |
| Verify | The loop step after Implement: the Spec's tests run again on the exact head, and the built change is exercised against each Acceptance line. Its report starts with the head SHA it checked; a new push makes it stale, and a failure returns to Implement. |
| Walking skeleton | The smallest end-to-end slice of a new system, usually the first Spec of a greenfield project. |
| WIP limit | The cap on open changes waiting on one Approver (three is a good default). It limits humans, never agents, which run every Task whose scope is disjoint. |
