# Glossary

These are the approved terms, one meaning each: the `instruction` writing level of the [plain-language skill](../plugins/aidd-team/skills/plain-language/SKILL.md), for rules, steps, and messages, uses them. Each section holds the terms you meet in one place, in alphabetical order.

A word in double quotes in an *Avoid* line is a word aidd's pages do not use; `tests/test_glossary.py` reads these lines and fails on one. A quoted word followed by "for" is wrong only for that term, so the test leaves it.

## Your first hour

Five terms carry your first hour. The rest can wait until you meet them.

| Term | Meaning |
| --- | --- |
| Level | What an agent does at an action: `allow` (act), `report` (act, then say what it did), or `ask` (wait for the person's yes, then act), from lowest to highest. A risk rule sets it. |
| Merge approval | A person's yes to the finished change before it reaches the default branch: the `pr.merge` ask. On a local trunk, and on a platform under `solo`, the agent asks in the chat, then merges. On a platform under `team`, it is the platform's PR/MR review: the agent opens the PR/MR and stops. *Avoid:* "sign-off" for it, and calling the reviewer role's findings an approval. |
| Route | Advice on how much of the loop a change needs: `minor`, `normal`, `major`, or `emergency`. `aidd risk --paths` computes it from the planned paths, and an area can raise it. The author may declare a higher one, and only a person declares `emergency`. Whether a Spec comes first follows from it, and `loop.routes` in `schemas/roles.json` holds the steps each route runs. As a person reads them, <!-- aidd:gen list:route-words -->`minor` reads "no Spec", `normal` and `major` read "Spec first", and `emergency` reads "repair first"<!-- aidd:end -->. *Avoid:* saying aidd enforces the route: it advises. |
| Spec | `specs/<ID>.md`: what, why, scope, Acceptance, tests, and rollback, with its status in its front matter. Its `## Request` quotes the person's own words. |
| Spec approval | A person's yes to a Spec before it is built: the `spec.approve` ask. The agent asks with what the Spec covers, and on the yes sets `status: approved`, `approved_by`, and `approved_at`, and commits with an `Approved-by:` trailer of the same value, in the form [`approved_by`](../.agents/skills/aidd/references/spec.md) takes. It is a note the agent wrote, not proof. A later edit of the tests, Acceptance, or Design is `spec.revise`. *Avoid:* "sign-off" and "design approval". |

## The loop and the risk rules

You meet these on every change: the loop's steps, the routes, and what an agent may do.

| Term | Meaning |
| --- | --- |
| Action | What an agent does that a risk rule can govern, named `resource.verb` in lowercase with snake_case words, such as `pr.open` or `git.push.force`. A dot makes a narrower action. Each names the shell patterns and harness tools that are it, and [METHOD.md](METHOD.md#61-actions) lists its fields. `schemas/risks.json` holds the built-in ones, and a config adds its own under `risks.actions`. *Avoid:* "permission" and "operation" for it. |
| Agent | An AI system that does work in the repository: plans, Specs, designs, code, and reviews. It runs in a harness. It does the work, and never decides a risky step for a person. |
| aidd | The software: the CLI and Python package, the skill, the plugins, and the `.aidd/` directory. What it is: a governance layer, as that entry says. The method it runs is [METHOD.md](METHOD.md), under the same name. Write it in lowercase always, even at the start of a sentence. |
| Allow | The lowest level: the agent acts. With no rule matching an action, its level is `allow`. |
| Approver | A person in `owners.approvers`, whom an agent asks for a decision, first to last. Empty, the agent asks whoever directs it. *Avoid:* "reviewer" for an Approver. The reviewer role is an agent that writes findings and never approves. |
| Area | A named set of path globs, such as `payments` or `ci`, with an optional `exclude` list. A rule can narrow an action to an area, and an area can name the least `route` a change that touches it needs. `schemas/risks.json` holds the built-in ones, and a config adds its own under `risks.areas`. *Avoid:* "protected path" and "zone". |
| Ask | The highest level: the agent asks the person a plain question, waits for their yes, then acts. In a headless run, it stops and hands back. *Avoid:* "deny" and "block": an ask waits for a person, and the person's yes lets the agent act. |
| Author | The person who directs the agents on a change and answers its asks. |
| Blast radius | Who or what behaves differently if the change is wrong. Recorded as `risk.summary` and `risk.dimensions`. |
| Branch protection | The platform's own rule that guards a branch or a repository: a required review, a required check, no force push or deletion, set as a protection rule or a ruleset. It is the one control that holds whatever an agent runs, so `branch_protection.change` asks before an agent deletes or changes one. aidd never sets it for you. |
| Change type | A Spec's `change_type`: the kind of change, in Conventional Commits vocabulary: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`. It never raises the route; a risk dimension does. |
| Confidence | A Spec's `confidence`: `high` when every fact that could change the route is known, `medium` when some are missing but none could change it, and `low` when one could. At `low` the agent stops and asks for the fact. |
| Delegate answer | The delegate's answer to a delegated ask, accept or defer, as a `delegate_answer` record its MCP tool writes after the delegate check passes again. A defer is final for that tree. A delegated yes writes the `Decided-by`, `On-behalf-of`, and `Delegation` trailers, never `Approved-by`. |
| Delegate check | `aidd delegate check`: whether a delegated ask may go to the delegate. It recomputes every check each time, from git, the delegation at the default branch's tip, and, where a remote exists, the platform's own check run and branch rules, and gives `eligible` or `defer` with a reason. The hook runs it again on the exact command before Claude Code lets the command run. |
| Delegation | A standing delegation: the config's `delegation` block, in which a person names the asks the delegate answers for them, inside limits. It takes effect only from the default branch's tip, and a parent preset can only narrow it. Claude Code is the one harness that answers one in this version. |
| Digest | What `aidd status` shows of a delegation: what was decided for you since it was set, each delegate answer and each merge on the default branch, with any doctor finding first. |
| Dimension | A kind of blast radius in words any role uses: `data`, `security`, `privacy`, `financial`, `compliance`, `availability`, `third_party`, `cost`, `performance`. An area names the dimensions a change in it has, and they name its specialists. |
| Done when | What finishes a loop step, written under each step of the loop ([the skill's loop](../.agents/skills/aidd/references/loop.md)). Finish the open step before the next one. |
| Emergency | The route for a production repair, which only a person declares. It names a human incident commander, runs the smoke tests, and has its Spec and post-incident review by `backfill_due`. |
| Evidence | `.aidd/evidence/evidence.json`, which `aidd test` writes: the exit code of each command on the head, and of each new-behavior command on the base, bound to the head commit. *Avoid:* calling a pasted log, a screenshot, or an agent's statement evidence. |
| Gate | A fixed point where a person decides: Intent agreement, Spec approval, Merge approval, and Production release (`deploy.run`). Each is an `ask`. |
| Governance layer | What aidd is: a governance layer for AI coding agents, on the AI-native development loop of six stages: Plan, Design, Build, Test, Deploy, Maintain. It advises how much process each change needs, meaning which steps of the loop it runs, and which of them wait for a person's yes. It keeps the evidence and the records. It enforces nothing, because the harness's ask rules and the platform's branch protection do. Its core is the method, the risk rules, delegation, evidence, the records, and the work items, with the CLI, the skill, and the MCP tools that serve them. The delivery team, the practice skills and packs, the standards library, the design tools, and the work-item pages are optional parts. |
| Harness | The program that runs a coding agent and its tools: Claude Code, Codex, Cursor, GitHub Copilot, and the others `aidd init` wires ([GUIDE.md](GUIDE.md#every-coding-agent)). An `Assisted-by:` trailer names it with the model, as `harness/model`. |
| Harness ask rule | A harness's own rule that makes it ask the person before a command runs, which `aidd init` and `aidd upgrade` write from each `ask` rule's commands. In Claude Code it is a `permissions.ask` entry, in OpenCode v2 a `permissions` rule, and in Codex a `prefix_rule` with `decision="prompt"`. Three more harnesses get one in their own format. aidd changes only the entries it lists in `.aidd/harness-rules.json`. A pattern is a net, not a control. |
| Head SHA | The commit at the tip of the change. Evidence binds to it. |
| Headless run | A session with nobody at the prompt, such as CI, a cloud session, or a scheduled run. In one, `ask` means stop: the agent hands back with a handoff note. Silence is never a yes. |
| Human | A person, not an agent. Say "human" in contrast with agents: human approval, humans decide the risky steps. Say "a person" for the one who acts in a step: a person approves the Spec, a person runs the rollback. In a guide, say "you" to the reader who acts. *Avoid:* "people" for Approvers or for the ones who decide, and "user" for an Approver. |
| Human feedback | The paths on which a person sends work back. Spec approval with changes asked for goes to Specify. Merge approval with changes asked for, or a review comment, goes to Implement. Roll out's incident, rollback, or missed hypothesis goes to Learn. Learn's lesson goes to Plan as a new change. |
| Implement | The loop step where the change is built, one Task at a time, inside its scope. It loops with Verify until the head is green. |
| Incident commander | The person named in an emergency block who runs the incident and answers the repair's asks. |
| Inner loop | The agents' part of the loop: Specify, Implement and Verify (repeated until green), and Review. The agent drafts the Spec, and after Spec approval works inside it, bounded by the Task's scope, red before green, and three retries. |
| Learn | The loop step after Roll out. It runs on a signal (a Merge approval sent back, a rollback, an incident, a Task out of retries) and on a cadence (the retrospective). Each lesson becomes a change to tests, rules, or agent instructions, linked in `outcome.learn_ref`. |
| Lifecycle | The four facts of a thing that can be open: who opens it, what closes it, who may close it, and what finds one left open. `schemas/lifecycles.json` holds one row for each thing, in three classes: a work item with a status, a thing with an end date or a release, and a thing a run opens on the machine. A record or a commit is written once and has none. |
| Limit | A named number that changes what aidd decides or shows, such as the retries a Task gets or the paths an answer lists. Its default, range, and direction live in `schemas/config.schema.json`, `limits`. A limit that guards a control can only be lowered, and the ceiling is aidd's own. A limit of the delegate's packet is aidd's data and no config sets it. |
| Loop | Every change runs the one loop: Plan, Specify, Implement, Verify, Review, Merge, Roll out, and Learn, grouped into six stages ([METHOD.md](METHOD.md#3-the-loop)). A person decides at its gates: Intent agreement, Spec approval, Merge approval, and Production release. |
| Major | The route for a change that touches an area such as `auth` or `payments`, has a major dimension, or cannot be reverted. Its Spec comes first, with more: a tech spec, a threat model when its risk names security, privacy, or data, and a rollout plan. |
| MCP server | `aidd mcp`: aidd as agent tools over the Model Context Protocol: <!-- aidd:gen mcp:tools -->`risk`, `status`, `recall`, `record`, `validate`, `delegate_check`, `delegate_packet`, and `delegate_answer`<!-- aidd:end -->. |
| Minor | The route for a small, reversible change with no Spec file, no risk dimension, and no area that raises it. |
| Normal | The route for a change that needs a Spec but nothing major. Its Spec comes first. Under `team` the agent asks for Spec approval; under `solo` it writes the Spec and says it goes on. |
| Org preset | A config an organization owns, which each repository names first in `extends`. A child changes only what it names: a mapping merges member by member and keeps every map entry, a list of named things merges by name, and any other list or value replaces. A preset keeps what it must with `locks`, naming a key or one member of it, and with a risk rule marked `locked: true`. |
| Outer loop | The person's part of the loop: Plan, the gates, Roll out, and Learn. An agent drafts all of it and decides none of it. |
| Plan | The optional step before the loop, for work bigger than one Spec: an Intent of ranked slices that a person agrees to. *Avoid:* "approve the plan": a person agrees to it. aidd keeps "approval" for Spec approval and Merge approval. |
| Profile | `solo` or `team`, in `schemas/profiles.json`: a set of risk rule overrides on top of the built-in rules, which decide the routes on which an agent asks for Spec approval. `solo` asks on major, and asks in the chat before a merge. `team` asks on normal and major, and its Merge approval is the platform's review. |
| Question type | A decision record's `question.type`: `yes_no` (yes or no to an action), `choice` (a pick from its options), or `text` (an open question). A record from an older aidd says `approval` for `yes_no`, and a reader reads it as `yes_no`. The record's types are in `schemas/records.json`. |
| Read form | A command that provably writes nothing, listed in `read_forms` or `help_forms` of `schemas/risks.json`: a tag listing, a `--dry-run=client` of `kubectl apply` or `kubectl delete`, `aws s3 rm --dryrun`, or a request for help. `aidd risk --command` reads it as `allow` when the command is typed as it runs, with only words the form lists. A harness's ask rule may still ask. |
| Record | One immutable file of history in `.git/aidd/records/`, which the agent writes after it acts with `aidd records add` or the MCP `record` tool: a `decision` (a question a person answered, word for word) or a `report` (an action it took at `report`). Under a delegation, aidd itself writes a `delegate_check` (one run of the delegate check) and a `delegate_answer` (the delegate's answer), which `aidd records add` refuses. `aidd records` lists them, and names a record it reads only in part, such as one a newer aidd wrote. A record is the agent's account, never a yes and never evidence; only a delegate's own answers change a delegation check, and only when they are today's shape in full. Its types are in `schemas/records.json`. |
| Red before green | A test for new or fixed behavior fails on the base commit and passes on the head. `aidd test` runs each `new_behavior` command on both. |
| Release | A version people can use: a deploy, a tag, or a published package. `deploy.run`, `git.tag.create`, and `release.publish` are `ask`. |
| Report | The middle level: the agent acts, then says what it did in one line. |
| Repository settings | A repository's own settings on the platform: its visibility, name, default branch, and archive state. Making a repository public exposes its code, and archiving or renaming it is hard to undo, so `repo.settings.change` asks before an agent changes one. Your own profile is no repository setting. |
| Reserved action | An action a delegation never covers, so it is always the person's, such as a deploy, a migration, a new dependency, or a secret. So is a change to what decides, anything on the emergency route, and every action outside the four delegable ones. |
| Retired name | A key, a value, or a library standard id that aidd renamed or cut, listed in `schemas/retired-names.json` with what replaced it. `aidd upgrade --yes` moves a file that still holds one, with a line for each change, and an error for an old name says what replaced it. A record is never rewritten, so a reader reads its old name as the new one. Add a row there whenever a name a person writes changes. |
| Retrospective | The Learn step on a cadence. The loop inspects its own results and proposes at most three measured improvements. Each re-enters the loop at Plan as a new change ([METHOD.md](METHOD.md#9-roll-out-and-learn)). `/aidd-team:retro` runs it with the SRE and the `retrospective` practice skill, then the product manager, who drafts the suggested Specs. Its Upkeep mode routes the upkeep that is due. |
| Review | The loop step between Implement and Merge approval, run beside Verify on one head: the findings, human or agent, are answered. |
| Rework | The return to Implement after a built head came back: a failed Verify or Review report, a person's requested changes, an open review comment, or a failing check. `/aidd-team:implement rework` makes one fix per item on the same branch, and `/aidd-team:review` verifies the new head. *Avoid:* confusing it with `spec.revise`, or DORA's deployment rework rate. |
| Risk rule | A rule that sets the level of an action, narrowed by an area, a branch (`own`, `default`, `shared`), a role, an environment, or whether that environment is shared (`environment_shared`); `spec.approve` also takes the route of the change (`route`). Of the rules that match, the most specific wins, then the higher level. `schemas/risks.json` holds the built-in ones, a profile and a config's `risks.rules` replace them by selector, and `aidd risk --list` prints what is in force ([METHOD.md](METHOD.md#6-risk-rules)). |
| Roll out | The loop step after Merge: the deploy, the release to users, and the observe window. It ends when the window passes or the rollback trigger fires. `/aidd-team:rollout` runs it. *Avoid:* "ship". |
| Session override | A person's words that lower a rule for one session, such as "don't ask about pushes today". It lasts the session, goes into the config only when the person says so, and never lowers a level below a locked rule, which is a floor. |
| Severity | An incident's `severity` in the emergency block: sev1, sev2, or sev3. sev1 means a critical journey is down, data is lost, or a breach touches many users. sev2 means a critical journey is degraded for many users, and sev3 a minor feature degraded with a workaround. When unsure, declare the higher one. A postmortem is due for sev1 and sev2, and by default when an incident uses more than 25% of an error budget. *Avoid:* confusing it with a vulnerability's CVSS severity. |
| Skill | A folder in the Agent Skills format (a `SKILL.md` and its references) that an agent loads by name. The `aidd` skill (`.agents/skills/aidd/`) tells any coding agent how to work in the loop; the delivery team adds domain packs and practice skills. |
| Specialist | A person in a pool in `owners.specialists`, such as `security`, `privacy`, or `finance`, whom the agent names when a change's dimension calls for one. *Avoid:* confusing them with the reviewer role, an agent that writes findings. |
| Specify | The loop step that writes the Spec and its acceptance tests before any code exists. It ends at Spec approval. |
| Stable branch | aidd's `stable` branch, the Claude Code plugins' release channel. The release job moves it to each release's commit, fast-forward only, and the first release makes it. `thaithienvanid/aidd#stable` adds the marketplace there, and until the first release the marketplace follows `main`. |
| Stage | Where a change stands: Plan, Design, Build, Test, Deploy, or Maintain, each a group of the loop's steps. *Avoid:* phase. |
| Stop rule | One condition in the aidd skill's Stop and hand back list, such as an `ask` that waits for the person or a third failed retry. Each names its stop code. |
| Trailer | A `Name: value` line at the end of a commit message that records who decided or helped: `Assisted-by:`, `Approved-by:`, `Agreed-by:`, and, under a delegation, `Decided-by:`, `On-behalf-of:`, and `Delegation:`. |
| Verify | The loop step after Implement, run beside Review on one head: the verifier runs the Spec's tests on the exact head, and exercises the built change against each Acceptance line. A failure returns to Implement. |

## Work items, tests, and records

You meet these when you write a Spec or an Intent, run its tests, or look up the open work.

| Term | Meaning |
| --- | --- |
| Acceptance test | A black-box test at the public edge (HTTP, the CLI, a UI route): at most one per Acceptance item, and one per authorization matrix cell and abuse case. The verifier writes it in Specify, red on base, and Spec approval freezes it. Unit tests come with the code. *Avoid:* confusing it with UAT, the client's user acceptance test. |
| Backfill Spec | The Spec of an emergency repair, committed in the repair's own change: `aidd new spec INC-<n>` with route `emergency`. It holds the regression test, and its post-incident review is due by `backfill_due`. |
| Blocked | A flag on open work, never a Spec status. Work is blocked when `waiting_on` names a wait, or when a Task used all its retries. A `blocked_by` item that is not done blocks Implement, never Specify. A draft or ready Spec keeps its step and a note, such as "Implement waits for SPEC-1". An approved Spec is blocked. `aidd status` shows the reason. |
| Brownfield | Adopting aidd in an existing codebase: the real layout mapped into areas, and characterization where tests are thin. |
| Characterization | Pinning today's behavior with a test before changing code that has none. |
| Concern | One line of a Spec's `## Concerns`: a risk by area, with the specialist who owns it. In Specify, a specialist starts only for a concern in its area, or a document the risk requires. |
| Cost estimate | What a change will cost to run, in its Spec (`risk.cost_estimate`): monthly at today's load and at 10x, with its source. The architect gives it in Specify, and `aidd validate` warns when infrastructure code or a cost risk has none, or when it is above `project.budget.max_infra_per_month`. |
| Day 0 | A new repository's first commit: the aidd setup and the project scaffold, committed straight to the default branch. Every later change starts from it. |
| Deprecation calendar | Each Spec's `deprecations`: what is deprecated, the day consumers were told (`announced_on`), the day it stops working (`sunset`), and what replaces it. The Spec that removes one lists it in `removes_deprecations`. A passed sunset warns in `aidd validate`. |
| Dirty tree | A working tree that holds what the head commit does not: uncommitted changes, or untracked files no `.gitignore` ignores. Tests that ran in one prove nothing about the head, so the evidence records it as `dirty_tree`. |
| Environment | A place a team deploys to, named in the config's `environments` with the branch and tag globs whose push deploys there, such as `production` from `prod` and `v*`. A push there is `deploy.run` to that environment, and a rule's `environment` sets its level. An environment is shared unless the config marks it `shared: false`, as the developer's own, where a deploy reports. An empty list, `environments: []`, says nothing deploys from a push, and a delegated merge reads the list: unset, it defers. `aidd init` reads the deploying workflows into the list when one names the default branch, and a person's `--environment none` is the only way it says nothing deploys. Under a delegation, a deploy to the developer's own environment still reports. *Avoid:* calling an environment a shared branch. |
| Experiment | The A/B test that decides a Spec's hypothesis, planned in its tracking plan before launch, with its variants, one primary metric, guardrails, a minimum sample or a duration, and the decision rule. A sample ratio mismatch or a guardrail breach stops it. |
| Finding code | A stable code that a check gives and a script matches, such as `delegation_review_due`, the reason `aidd delegate check` defers for. `schemas/findings.json` lists each code with its severity, title, why it comes, and next step, in one group for each owner, so a code is defined once. A full code is `<group>.<code>`. A `--json` command prints each problem it finds as a finding with its code, and prints an error object on stdout when it stops with exit 2. `aidd explain <code>` says what a code means. |
| Frozen test | A test that Spec approval froze: an acceptance test, or a test file listed in the Spec's `tests.files`. The builder never edits it, and a change to it is `spec.revise`. Where an agent has a file-edit rule, `aidd upgrade --yes` writes an ask before its edit tool changes one, and a delegated merge's check compares it with the approval commit. |
| Greenfield | Adopting aidd in a new repository: Day 0, then a first Spec that brings the test runner and the first test. |
| Hypothesis | A Spec field: the metric a change should move, its baseline, the expected move, and by when. It can add a kill criterion, the result that stops the work, such as "stop if under 2% of trials export by June". Learn records `outcome.result` against it; a miss is a product decision, not a rollback. |
| Index | `.git/aidd/index.sqlite`: a cache of a clone's files in SQLite. It holds the work items in every worktree and branch, which `aidd status --all-branches` reads, and the lines `aidd recall` searches. It reads a place again only when the place changed, and it is never the truth: the files are. |
| Intent | The work item for one goal bigger than one Spec, `specs/INTENT-<n>.md`: the problem, the outcome, the constraints, and phases of slices, which the team writes from a request and a person agrees to. Each goal of a request bigger than one Spec gets its own Intent, and one yes agrees to them all; a one-change goal gets its own Spec instead. *Avoid:* the request itself; `intent.md` as a file name. |
| Intent agreement | A person's yes to an Intent before its Specs start: the `intent.agree` ask, recorded in `agreed_by`, `agreed_at`, and an `Agreed-by:` trailer. *Avoid:* "approve the plan". |
| Interface | A stable name for an API, an event, or a schema that one Spec `provides` and others `consumes`. When the provider is revised, `aidd status` names the open consumers, so their owners hear first. It advises and blocks nothing. *Avoid:* contract, which means the client contract (SOW). |
| Launch | The merge of the Spec for the last slice of the last phase of a `flagged` Intent, which turns the feature on for users. Its Merge approval stays a person's. |
| Living doc | A linked document kept current after the merge (`frozen: false`) instead of frozen at Spec approval: the data map, the threat model, the vendor register, or a runbook. |
| Local trunk | The default branch on this machine, when no platform holds the shared one. The agent asks before it merges or pushes there. |
| Observe window | `observe.window` in a Spec: how long after release the change is watched, with the command or signals that judge it and the `rollback_trigger`. A major Spec has one. |
| Output folders | The folders aidd writes into `.aidd/`: `evidence/` (the evidence), `returns/` (the edits a role proposes, as diffs a person applies), and `views/` (the pages `aidd explore` and `aidd prototype` write). git ignores them, and aidd writes them again on each run; only files directly in `.aidd/` are committed. *Avoid:* committing anything in them. |
| Owner | The person who answers for a thing. On a Spec or an Intent, `owner` is the person driving the work, never an agent, and it decides nothing by itself. The config's `owners` group holds the repository's Approvers and Specialists. |
| Phase | An ordered group of an Intent's slices, with a `due` date only when a person names one. A client's invoicing hook is a phase too, and the end of a phase is what a plan or a contract calls a milestone. *Avoid:* stage. |
| Priority | `priority` on a Spec or an Intent: urgent, high, medium, or low. When unset, it is inherited from the parent; an emergency is urgent. It orders `aidd status`. |
| Product defaults | `project.defaults` in the config: what every product gets unless a person turns it off with the reason. They cover light and dark themes, responsive layouts, i18n-ready strings, a performance budget, the public-page basics, and API and data conventions. They also cover operability, security headers, legal placeholders a person writes, transactional email, the developer basics, a latency budget, bounded retries, an SLO, a tested restore, and request limits. *Avoid:* "optional features": each is on until a person says why not. |
| Project template | A team's own template for one `aidd new` type, `docs/templates/<type>.md` (under `docs.dir`), which `aidd new` reads before aidd's. `aidd validate` checks what it writes, so it may add sections but never drop a required one. A template that leads outside that folder is refused. |
| Reaches | `reaches` on an Intent: how its work reaches users. `incremental`, the default: each Spec merges by itself. `flagged`: each Spec merges behind a feature flag that stays off until the Spec for the last slice of the last phase. `batched`: the Specs collect on the branch `intent/<ID>`, which merges once. |
| Recall | A search of what the team already wrote: the records, the Specs, the ADRs, the glossary, the product brief, the improvement log, and the commit subjects. `aidd recall <words>` and the MCP `recall` tool give each line that holds every word, with its file and line, a record's id, or a commit's short sha. It reads through the index with SQLite's full-text search, and no model. A match is never a source of truth, never evidence, and never a yes. *Avoid:* "knowledge graph", and "memory" for it. |
| Request | A person's own words for what they want, from a chat message or a file. aidd never rewrites it. Each goal in it is sorted by size. A minor fix gets no Spec, and a one-change goal its own Spec, whose `## Request` quotes it. A goal bigger than one Spec gets an Intent, which names it in `request`. A chat request that becomes Intents is saved first, to `specs/requests/<yyyy-mm-dd>-<slug>.md`, leaving out secrets, credentials, and other people's personal data, each marked in place. That file is never a work item. *Avoid:* "ask", which is a level; "user request", since a rule says person; confusing it with the product brief. It is not a pull or merge request (PR/MR), nor a change request, the formal change record of regulated change management. |
| Request coverage | An Intent's `## Request coverage` table: one row for each success criterion and hard constraint of the whole request. Each row names its proof, a slice's acceptance line (`SPEC-1 A3`) or a phase's exit criterion (`exit: P1`). Or it names another work item that covers it, such as another goal's Intent (`INTENT-2`), `deferred, asked` with the question put to the person, or `the request's non-goal`. `aidd validate` checks each row, and that Intents which name each other for an item reach a proof. *Avoid:* confusing it with test coverage. |
| Scope | The globs a Task's diff may change (`tasks[].scope`). |
| Slice | A planned Spec: one line in a phase of an Intent, until its work starts and `aidd new spec <ID>` writes its Spec. *Avoid:* slice for a Task. |
| Spec status | A Spec's `status`, which the agent sets: `draft`, `ready`, `approved`, `in_progress`, `in_review`, `done`, `rolled_back`, or `cancelled` ([METHOD.md](METHOD.md#44-spec-status)). |
| Status group | One of five groups that every work item's status falls into: `backlog`, `unstarted`, `started`, `completed`, and `cancelled`. They are the same for Specs, Intents, and proposals, so a board or a tracker mirrors any item by its group. |
| Status transition | One move of a work item's status to another, a row of `x-transitions` in the schema that owns the status words. A row names the statuses it leaves (`from`), the status it reaches (`to`), who moves it (`by`: an `agent`, or a `person` whose yes the agent records), what moves it (`when`), and the fields it leaves set (`requires`). A pair with no row is no move. The aidd skill's `references/state.md` is generated from these rows. *Avoid:* "state machine" for the data. |
| Support period | `project.compliance.support_period`: the last day (`ends_on`, `YYYY-MM-DD`) on which the product gets security updates. The `cra` target needs it: at least five years, unless people use the product for less time (CRA Art. 13(8)). `aidd validate` fails a `cra` config without one. |
| Task | A part of a Spec's work with its own `scope`. *Avoid:* slice, a planned Spec. |
| Test report | The JUnit XML file a test command writes, named by its `report` key. `aidd test` records which test cases failed, beside the exit code. It adds detail to the exit code and never replaces it. |
| Test runner | The CI job that `aidd init --ci` writes, `aidd-tests` on GitHub: it runs `aidd test` on each PR/MR and keeps the evidence. It runs the change's code, so it gets no secrets. |
| Tests | The commands whose exit code proves Acceptance (`tests.commands`) and the files they run through (`tests.files`). Written before Implement. |
| Trace | What stands behind a path or a work item: its Specs and its Intent, the open Specs whose scope overlaps it, their tests, docs, and interfaces, the route, and the last commits. For a work item it also lists the work that shares its `trace_id`, one piece of work across teams or repositories. `aidd status <path or id>` reads it from git and aidd's files on demand and stores nothing. *Avoid:* "change graph" and "code graph". |
| `trace_id` | An identifier shared by every Spec and PR/MR of one piece of work, across repositories. |
| Trunk-based flow | The default branch is the one trunk: few branches, each short-lived and merged often. Unfinished work merges behind a flag rather than waiting on a branch. |
| Type | The top-level `type` field of the front matter of a work item or a typed document, which aidd finds its files by: `spec`, `intent`, `proposal`, `runbook`, `postmortem`, `exploration`, or `feedback`. A linked document's `docs` entry has its own `type`, such as `tech-spec`. |
| Typed document | A file of aidd, other than a work item, whose front matter has a `type`: `runbook`, `postmortem`, `exploration`, and `feedback`. It has no status group and no next step in `aidd status`. |
| Verification report | The verifier's report from Verify. It starts with the head it checked, says what ran and what the change did, and records any drift from the Spec. It is never evidence, and a new push makes it stale. |
| Walking skeleton | The smallest end-to-end slice of a new system, usually the first Spec of a greenfield project: every layer wired, one happy path, a term from Alistair Cockburn. Its Task (`skeleton: true`) builds the structure, the contracts, the test runner, and CI. |
| WIP limit | The cap on open changes waiting on one person, three by default as a practice. It limits humans, never agents, which run every Task whose scope is disjoint. |
| Work item | A Spec, an Intent, or a proposal (`spec`, `intent`, `proposal`): a file with a status group and a next step in `aidd status`. Every other file with a front matter `type` is a typed document. Each type aidd tracks or writes, a work item or a document, is one row of `schemas/item-types.json`. *Avoid:* "aidd object". |
| Work item folder | The folder beside a work item's file, named by its id: `specs/SPEC-12.md` keeps everything about it in `specs/SPEC-12/`. It holds the documents the item links, its design files (`design/`), and its explorations (`explore/<slug>/`). `docs/` holds the project's official docs instead: ADRs, the architecture overview, runbooks, the glossary. |
| Work-item page | The open work as one static page, which `aidd status --html` writes to `.aidd/views/status-work.html`. It has Needs you, a Board by stage or status group, a Tree, search, and a page for each item, with a banner for an open emergency. Each item has its next step and the words to copy. It only reads: the state stays in front matter, and a decision stays in the chat. |

## The delivery team

You meet these when you run the aidd-team plugin: its roles, its flows, and the docs the roles write.

| Term | Meaning |
| --- | --- |
| ADR | An architecture decision record, the `adr` doc (`aidd new adr <topic> --spec <ID>`), in `docs/decisions/NNNN-<topic>.md` and in MADR's shape, which fits any significant decision. The architect writes one for each significant decision. An ADR is frozen, so a later decision gets a record of its own. A `decision` record in `.git/aidd/records/` is a different thing: a person's answer, word for word. |
| Agent role | One of the optional aidd-team roles ([TEAM.md](TEAM.md)): a subagent guided to write only its own files. It never approves. |
| AGENTS.md | The project's guide for every agent that works in the repository, the `agents` doc: one per repository, living, and kept by the architect. Each change that makes a line in it untrue updates it. aidd's own section, from its marker down, belongs to aidd. |
| aidd-team | The optional plugin that runs the loop with a delivery team of agent roles, led by a person, an agent, or both, with a person deciding the risky steps they keep ([TEAM.md](TEAM.md)). |
| API doc | The `api` doc a Spec links (`aidd new api <topic> --spec <ID>`): the contract of an endpoint or an event. Its machine-readable part is an OpenAPI file for HTTP, or an AsyncAPI file for events and messages. The architect writes it, and Spec approval freezes it. |
| Architect | The `architect` role of the delivery team. It gets the route before any code, then writes a Spec's Context, Design, and Tasks, with each Task's scope, risk, and rollback. It records each significant decision as an ADR. |
| Architecture overview | `docs/architecture/README.md` (`aidd new architecture`): the one living page of how the system is built. Its shape is arc42 cut short: the goals, stakeholders, and constraints, the context, a C4 container diagram, the key runtime flows, and deployment. It also has cross-cutting concepts, each linked to its ADR, quality targets, risks, and fitness functions. A tech spec starts from it and shows only what changes. *Avoid:* a per-Spec copy of the architecture. |
| Builder | Whoever writes a Task's change inside its scope: the person or agent role the Task's `assignee` names. Usually the developer, the SRE for infrastructure, or the technical writer for docs. Never the verifier when the Spec comes first, since whoever writes the acceptance tests never makes them pass. It writes the unit tests with the code. *Avoid:* "implementer". |
| Compliance analyst | The `compliance-analyst` role of the delivery team. It maps a change to its legal and control obligations, plans the DPIAs, and turns the change's record in git into audit evidence. It never signs off: a person does. |
| Delegate | The `delegate` role of the delivery team, `aidd-team:delegate`. Under a delegation, it answers a delegated ask for the person from the packet the delegate check builds: accept on an eligible check, or defer for any doubt. Its only tools read the packet and record its answer. *Avoid:* "approver" for it: its accept is the person's delegated yes, never a person's own. |
| Delivery manager | The `delivery-manager` role of the delivery team, for a client engagement. It qualifies the request, keeps the RAID log and the phases, and reports status. It drafts the contract base and the change orders, coordinates the client's acceptance, and runs the handover. |
| Delivery team | One set of the aidd-team roles, run in one harness by its approvers; a repository may have several. The roles cover product, design, architecture, security, compliance, testing, software, documentation, verification, review, reliability, and process improvement. Each is an agent limited to its own files; humans hold every decision. The config's `delivery_teams` names each team with its approvers, its areas, its harness, its models, and its effort, and an Intent, a slice, or a Spec names its team in `delivery_team`, and `aidd status --delivery-team <name>` shows its work. *Avoid:* confusing it with the `team` profile. |
| Developer | The `developer` role of the delivery team. It implements one Task inside its scope until the tests pass. When the Spec comes first it never edits the tests that Spec approval froze. With no Spec it writes the regression test with the fix. On the emergency route it restores service first, and the backfill Spec holds the test. |
| Domain expert | A person who knows one business area deeply (payments, clinical safety, tax, a regulator's rules). In aidd, a person the agent names when a change touches that area. No agent role stands in for one: the role that asks loads the area's business pack, and the person decides. |
| Domain pack | A skill (`aidd-packs:<pack>`) of the optional aidd-packs plugin, generated from `schemas/packs.json` for one domain. It holds its standards with editions and checked dates, a checklist per loop step, and test commands for the Spec's tests. A role loads it by name, on top of its own work, for every domain that a change touches. |
| Enabled | An extension (a plugin, an MCP server, or a skill) that the repository's own committed settings turn on, such as Claude Code's `.claude/settings.json` (`enabledPlugins`) and `.mcp.json`. A tool installed for a whole machine is not enabled for a project. A role uses a service or a toolset only when it is enabled. *Avoid:* connected, installed. |
| Extension | A skill, plugin, MCP server, or tool that a team role loads on top of its packs. `schemas/roles.json` lists them per role as starting points. Each is verified and pinned, and installed through a change. |
| Feedback log | The living `feedback` doc, `docs/feedback/<topic>.md`, with one row per piece of post-launch feedback. Each row gives its date, channel, customer or segment, quote, theme, severity, an optional 0-10 score, and the Spec or hypothesis it concerns. The product manager reads it at Learn. |
| Fitness function | An architectural rule that a machine checks, run as an ordinary test command. It is a layering rule that the architecture overview declares, checked by the stack's boundary checker (`aidd standard list`). So a change that breaks a layer turns the tests red. |
| Flow | The roles a team command runs, in order, with the groups that run in parallel and the ask it stops at. A person types the team command (`/aidd-<flow>`), and the flow is its steps. The data is in `schemas/roles.json`. *Avoid:* "workflow" (a CI workflow), "program", or "playbook" for a team command. |
| Glossary | The repository's one `glossary` doc, `docs/GLOSSARY.md` (`aidd new glossary`): the project's terms, one meaning each, with the words to avoid. It is living: Clarify adds a term once the author settles it. This page is aidd's own glossary. |
| Handoff note | What every team role ends a run with, in one form: a fenced `aidd-handoff` block of YAML in the Spec or the PR/MR (`done`, `next_role`, `needs`, `stopped_at`, optional `by` and `spend`). The next role reads it before the file. A role may add `open_decisions`: each risk or choice it leaves for the lead to settle, with an `id`, its options, and what each blocks. The lead answers each on a later note's `answered`, by its `id` and one of its choices. Any role lists in `run.opened` what it opened and whether it closed it, with why and who closes one left open. The lead's `run` block also holds the counts, the spend, and the wake time of a long run, so another session goes on from the note. An agent's `by` is `agent:<harness id>/<model>`, as its commits' `Assisted-by`. A headless run that reaches an ask ends with one. Never evidence. Its keys are in `schemas/handoff.schema.json`. |
| Improvement log | The retrospective's living file of improvements, which the SRE keeps, each with the metric it should move and a check date, `docs/retros/improvement-log.md` (`aidd new improvement-log`). `aidd validate` warns when a check date passes with no result. *Avoid:* "improvement ledger". |
| Independent review | The verifier and the reviewer run on a provider other than the developer's, so a model never checks its own work. It is opt-in, with `agents.independent_review`, and `aidd init --aidd-team` warns when the models fall short. |
| Lead | The session that runs the team. It decides who does what, sends work back, and takes a Task in, each on its evidence. It never answers an ask for the person. |
| Metrics dictionary | The product's one list of metrics and events, each named once, `docs/product/metrics.md` (`aidd new metrics-dictionary`). Each Spec's tracking plan folds into it, and `aidd validate` warns about an event it does not name. |
| Migration plan | The `migration-plan` doc a Spec links (`aidd new migration-plan <topic> --spec <ID>`): the steps that move a schema or data without downtime, each a separate deploy. The architect writes it, and Spec approval freezes it. |
| Open choice | A decision that a domain pack or a practice skill leaves to the team, such as `ci-pipeline:linter`. It is data in `schemas/packs.json` or `schemas/roles.json`, with aidd's default answer. An opinionated standard fills it (`fills`). `aidd standard` lists them. |
| Orca payload | The JSON a worker passes to Orca's `--payload`: its `type` (question, blocked, done), item, head, handoff path, role, harness, and model. It is data, and the lead acts only on one that `aidd validate` passes. |
| Practice skill | A hand-written skill (`aidd-team:<name>`) for one kind of work: schema migration, threat modeling, test design, secure coding, and more. It holds its standards, steps per loop step, test commands, and handoff, with a checked date. Each role lists its own; a Task names up to two in `skills`. |
| Proactive role | An agent role listed in `agents.proactive_roles`, allowed to suggest work nobody asked for, and only as a draft Spec. |
| Product brief | The product manager's living file of the problem, the users, the outcomes, and the roadmap, `docs/product/brief.md` (`aidd new product-brief`). Each Intent that changes one updates it. *Avoid:* confusing it with a request, one person's own words. |
| Product designer | The `product-designer` role of the delivery team. It builds the interactive prototype a person approves at Spec approval, after rough directions when the approach is open. It owns the design system, and it reviews the built UI against the prototype. |
| Product manager | The `product-manager` role of the delivery team. It sorts each goal of a request by size, and turns each goal bigger than one Spec into an Intent of slices, each slice with an outcome, an owner, and a priority. After launch, it triages incoming issues into suggested Specs and keeps the feedback log. |
| Product-level work | A body of work a role keeps across changes, such as the architecture overview or the product prototype, as opposed to a file that belongs to one Spec. The team registry's `loop.documents` marks each type's `belongs_to`, and which per-change kind feeds it. Each change that alters a feeding kind brings it in line in the same change. *Avoid:* "living body of work". |
| Release notes | The notes for a release, from the skill's `release-notes.md` template: every change merged since the last tag, a Spec or not, grouped as Keep a Changelog's Added, Changed, Deprecated, Removed, Fixed, and Security. The tech writer edits the words, never the facts. |
| Reviewer | The `reviewer` role of the delivery team. It reviews the diff against the Spec adversarially, as the repository's REVIEW.md says, and reports ranked findings to the person who decides Merge approval. It never approves or edits. |
| Role operation | A role at one loop step it works in, from the `steps` of each role in `schemas/roles.json`. Each role eval case names its `step`, and the table in `evals/roles/README.md` counts the cases per operation. An operation with no case is a gap. |
| Role placement | Where a role runs for one step: in the lead's own session, as a subagent the lead starts, or in a session of its own. The lead plays a role only for a small step that adds a view to its own work. A role that checks, tests, or reviews work never runs in the session that wrote it. |
| Runbook | A living doc of type `runbook`: the standing on-call procedure for one service, written before it is needed and tested on a schedule. One change's rollout plan is the Spec's `## Rollout`, and the rota is the service card's. `aidd new runbook` writes it in `docs/runbooks/`, and `aidd validate` checks it against its schema. *Avoid:* "runbook" for the install steps in `llms-install.md`. |
| Security engineer | The `security-engineer` role of the delivery team. It threat-models a risky Spec, names the security tests the verifier writes, and reviews the diff for vulnerabilities. It never approves. |
| Service card | One service's living page in `docs/services/<name>.md` (`aidd new service-card <name>`): its SLOs, on-call rota, runbooks, alerts, and owner. The cards together are the service catalog, and the SRE folds each Spec's approved SLO delta into its service's card. |
| SLO | A service level objective, in the `slo` doc a Spec links (`aidd new slo <topic> --spec <ID>`): one objective per row, each measured from what users see. The doc is a delta: it is frozen with its Spec and holds only what the change moves. The service card holds the current objectives, and the SRE folds each approved delta into it. |
| Spend cap | `agents.max_tokens_per_run`: the most tokens one `/aidd-team:autopilot` run spends before it stops and asks once to go on. The lead sums each step's token count from the harness, never an estimate. Where the harness gives no count for each step, autopilot says so once at launch, and the cap can't stop that run. It has a default ([CONFIG.md](CONFIG.md#agents)), so an unattended run never spends without a bound. |
| SRE | The `sre` role of the delivery team, for site reliability. It plans observe and rollback before Spec approval, watches the observe window, and writes postmortems and runbooks. It also builds the CI/CD and the infrastructure it runs, inside its Tasks' scope. |
| Stop code | The first word of a handoff note's `stopped_at`, which says why the run stopped, such as `none`, `ask`, or `retries`, alone or with `: ` and a detail. The common schema's `stop_code` holds the list, and each of the aidd skill's stop rules names its code. `aidd validate` warns about a note that starts with none of them. |
| Tech spec | The `tech-spec` doc a Spec links (`aidd new tech-spec <topic> --spec <ID>`): the detail behind the Spec's design, for a reader who must judge it. The architect writes it in Specify, and Spec approval freezes it. A drift found later goes in the verification report. |
| Tech writer | The `tech-writer` role of the delivery team. It writes the user-facing docs, the changelog, and the migration notes a change needs, inside a documentation Task's scope. It also writes the knowledge-base articles that answer a repeated support question. |
| Toolset | A named bundle of a role's extensions in the team registry (`toolsets` in `schemas/roles.json`), such as the product designer's `ai-design`. A person picks one by enabling its extensions in the project. |
| Tracking plan | The `tracking-plan` doc a Spec links (`aidd new tracking-plan <topic> --spec <ID>`): the events that measure the Spec's hypothesis, written before the code that sends them. The product manager writes it, and Spec approval freezes it. Its new metrics and events fold into the metrics dictionary. |
| Triage | A person's decision on work that an agent suggested on its own (`suggested_by: role:<role>`). It is accepted, declined (the Spec is cancelled), or snoozed until a date, recorded as `triage` in the Spec. Until then the Spec stays a draft. |
| Verifier | The `verifier` role of the delivery team, the one QA role. In Specify it writes the Spec's acceptance tests, which fail on base before any code exists. In Verify, a fresh session, it runs the Spec's tests on the exact head and exercises the built change. Its report is never evidence, and it never writes the code. |

## Design

You meet these when a change has a screen: prototypes, rounds, and the design files.

| Term | Meaning |
| --- | --- |
| Agent round | A round of a design whose comments agents wrote, before Spec approval and before a person looks. The designer starts reviewers, merges their items into the round's one file with `by`, and answers them in the next round. The designer stops for a person after the third agent round, at a pass with no comment, at the timebox, or at a comment only a person can settle. It never marks a state seen and never approves. |
| Comfort check | A check that a screen stays comfortable to read for hours, above the WCAG 2.2 AA floor. Text sits in its contrast bands, large fills stay calm, no text is drawn with opacity, and prose runs 80 characters a line or fewer. It runs from the tokens by script and as a probe per state, in both themes, as `aidd-team:accessible-ui` says. *Avoid:* calling it an accessibility check, which is the floor beneath it. |
| Comment | A person's or an agent's remark on one element of a prototype. A person makes it in the prototype viewer with Add a comment, and an agent's item names its writer in `by`, so an item without `by` is a person's. It names its screen, state, and element, and its type says what to do: change, remove, add, or a question. A round's comments are `rounds/<N>/comments.json`, or in an exploration one `comments-<direction>.json` per direction, whose ids start with its name. A later round's `changes.json` answers each one; until then it stays open. *Avoid:* "note" or "feedback" for it, and confusing it with a review comment on a pull request. |
| Component spec | A row and a subsection in `DESIGN.md`'s Components section. It is written only when a component is new or changed, as its own design-system change. It gives the component's purpose, anatomy, props and variants, every state, and accessibility. It also gives the tokens it uses by name from `design/tokens.json`, and its test ids. |
| Decision card | An exploration with no visuals (`aidd new exploration`) for one choice that a person must make. It gives the question, the options as directions with their trade-offs, and the agent's recommendation. A handoff note's Needs line names its path; the person decides, never the card. |
| Deep link | The address of one view of a prototype: `#<screen>/<state>?theme=dark&frame=ios&round=2` on the page `aidd prototype` writes, each key optional. Opening it restores that screen, state, theme, and frame. Screenshots, tests, review comments, and a prototype's comments point at a view with it. |
| Design direction | One of two or three rough, low-fidelity takes on the same request that the product designer offers before any detailed prototype. A person picks one, and the Spec's `## Design` section records the pick with who, when, and why. *Avoid:* "approving" a direction: the design is approved only with the Spec. |
| Design files | The `design-files` entries of a Spec's `docs`: the prototype, the design spec, the flow diagram, and the rough directions, never a copy of the design system. Spec approval covers them with the tests. They are never a Task's scope, and product code never imports them. *Avoid:* "mockups" for the whole set. |
| Design spec | The `design-spec` doc a Spec links (`aidd new design-spec <topic> --spec <ID>`): the context of use, the screens by state and by target, the flows, the copy, the accessibility, and the usability test, next to the HTML prototype (`--prototype`). The product designer writes it before Spec approval. It uses the repository's one design system (`DESIGN.md`) and never copies it. |
| Design system | The repository's one `design/tokens.json` and `DESIGN.md`, written with `aidd new design-system`. `design/tokens.json` is the one source, in the Design Tokens format; `DESIGN.md` (in Google Labs' design.md format) gives principles, color roles, themes, type, layout, motion, components and states, patterns, and accessibility. The product ships its tokens, so only a Task's scope changes it. aidd's own pages keep their system apart, in `src/aidd/views/design/`, so a project's `design/tokens.json` never changes aidd's look. |
| Exploration | Two or three divergent directions for one question, in a folder with `exploration.md` (`aidd new exploration`). The folder sits in the work item folder of the item it informs, `specs/<ID>/explore/<slug>/`, or in `specs/explore/<topic>/` while no work item exists yet. `aidd explore` renders it as one comparison page for a person to pick from (`/aidd-team:specify explore`). The owning role records the pick and why in the Spec's Design section, `DESIGN.md`, or an ADR. *Avoid:* an agent picking the direction. |
| Fidelity pass | A check of how a screen looks, before any person sees it: screenshots read for defects, and axe. Done means no Fix point is open. The product designer runs it on a new or reshaped screen or flow, a change to a component's look or states, or a new or redrawn diagram or picture in a document. Its author runs a quick pass on any other UI change. Its views follow the change, and `aidd prototype --shots` lists them. A new screen takes every state at 320, a phone, and 1024, in both themes, then 200% text and right to left. A changed component takes the screens it appears on first, as a person sees them, then its states on each variant. *Avoid:* calling a passing screenshot test a fidelity pass. |
| Journey map | The `## Map` of an Intent, for discovery. It gives one persona's journey, part by part, by goals, actions, touchpoints, thoughts, pain points, and opportunities, with a service blueprint. The product manager or the product designer keeps it; it never holds the solution. |
| Mockup | A static picture of a screen, such as a frame exported from a design tool into a `design-files` doc. Not an aidd artifact: aidd's is the prototype, which responds to input. *Avoid:* "mock" for the prototype. |
| Product prototype | The product designer's product-level work in `docs/design/app/` (`aidd new product-prototype`): the whole product, clickable. `sitemap.json` defines the navigation once, `shell.html` holds the product's tokens, styles, and chrome, and `flows/` holds one file per flow. `aidd prototype` assembles them into one page in `.aidd/views/` and checks every link and screen. |
| Prototype | `prototype.html` in a Spec's design folder (`aidd new design-spec --prototype`): the design of one Spec's flow, with every screen of it in every state. aidd-team's prototype tool (`aidd prototype <file>`) shows it in the viewer, with the states seen, device frames, a Board of screens by states, comments, and deep links. With the design spec, it is the design source of truth. |
| Prototype tool | aidd-team's built-in tool for the product designer's prototypes, `plugins/aidd-team/tools/prototype/`. It shows a design in the prototype viewer, checks it, prints its component contract, and checks Storybook's stories against that contract. It is one standard-library file; `aidd prototype` runs it. |
| Round | One pass of a design that a person or agents review. Its folder, `rounds/<N>/`, holds its screenshots and the reviewer's `comments.json`, from the prototype viewer or an agent round, or in an exploration one `comments-<direction>.json` per direction. Each comment names its screen and state. The next round's `changes.json` names the comments each change answers. |
| Taste pick | A choice among two or three sound looks of one thing, such as a width or a color, which a person makes by eye. The role shows the options side by side in one screenshot and asks one question, or puts them in a decision card with `taste_pick: true`. Its options may differ only in color, size, or spacing. *Avoid:* asking it about a rule, such as text at 200%, which is built in. |
| Usability test | The design spec's `## Usability test`, before launch. It gives goals, participants and recruiting, tasks with success criteria, the script, findings with severity and evidence, and the decisions a person makes. After launch, the feedback log. |
| User flows | The design spec's `## Flows`: the sitemap and each main journey as Mermaid diagrams, with entry, exit, and error paths, naming the screens its Screen inventory lists. |

## Client work

You meet these when the team works for a client: proposals, contracts, and the handover.

| Term | Meaning |
| --- | --- |
| Acceptance record | The `acceptance` doc a Spec links when a person accepts the work by hand (the Spec's `manual_acceptance: true`): a client, or with no client the product owner or QA owner. People fill it in after Spec approval: the environment and build accepted, the acceptance, the open defects, and each sign-off, such as the user acceptance and the DPO's decision. It stays living. |
| Change order | A change to an accepted proposal's scope, price, or time, in `change-orders/CO-<n>.md` beside its contract. The Spec then changes to match, which is `spec.revise`. A person's direct request that changes the scope, the Acceptance, or the tests is one, never a quiet addition. |
| Contract (SOW) | The `contract` doc in an accepted proposal's folder, from the skill's contract template. It is a statement-of-work base for a client engagement. It gives the scope by Acceptance ids, the deliverables, and the proposal's phases and assumptions by id. It also gives change control, the AI-use questions, support levels, the acceptance period, the warranty, and the clauses marked for a person or a lawyer. Living; a base to review, never legal advice. |
| Go/no-go | The first human decision on a Proposal: pursue it or not, recorded in `go_no_go` before the team drafts. |
| Handover | Passing a client's product to the client's team (`/aidd-team:handover`). The acceptance record's `## Handover` section is the one list of what passes to the client. It holds the repository, the docs index, the licences, the vendor accounts, and the credentials transfer log (never a secret). It also holds training, open issues, the warranty start, the client's data, the agent setup, and who decides after handover. *Avoid:* confusing it with a handoff note between roles. |
| Proposal | A case put to someone outside the team who decides, before any code. It is a bid or pitch to a client, or a change put to the company's leadership. It holds the needs and how each is answered, options, a range estimate, assumptions, exclusions, risks, and questions. Accepted, it becomes an Intent. |
| Qualification | The delivery manager's `qualification` in a proposal before any drafting: fit, budget, authority, and decision process, with a recommendation (go, no_go, or questions_first). It advises the go/no-go, which a person records. |
| RAID log | Risks, assumptions, issues, and dependencies: the `risks`, `assumptions`, `issues`, and `dependencies` of the proposal, then of its Intent. They share one item shape, with an owner and a status (open, resolved, accepted, invalid). *Avoid:* a separate tracker for them. |
| Sign-off | The second human decision on a Proposal: it may be sent, with its price, commitments, assumptions, and exclusions. *Avoid:* "sign-off" for a Spec or a merge. |
| Support SLA | The contract's Support and service levels schedule. It sets the support tiers, channels and hours, and response and resolution targets by severity (S1 to S4). It also sets escalation, maintenance windows, exclusions, and reporting. *Avoid:* confusing it with an SLO, the system's reliability target. |

## Security and compliance

You meet these when a change touches security, personal data, or a regulation.

| Term | Meaning |
| --- | --- |
| Authorization matrix | The `authz-matrix` doc that a Spec links (`aidd new authz-matrix`). It has a row for each subject and action on each resource or endpoint. Each row gives the row-level condition, the expected allow or deny, and the test that proves it. The security engineer writes it; the verifier writes one test per row. |
| Compliance record | The `compliance-record` doc a Spec links (`aidd new compliance-record <topic> --spec <ID>`): what binds the change, and how the change meets each obligation. The compliance analyst writes it, and Spec approval freezes it. Its controls fold into the control register. |
| Control register | The compliance analyst's living file of controls and their evidence, `docs/compliance/control-register.md` (`aidd new control-register`). Each Spec's compliance record folds into it. |
| Data map | The repository's one living `data-map` doc, `docs/data-map.md` (`aidd new data-map`), linked by each Spec that touches personal data. It has one row per personal-data item and purpose. Each row gives the category, lawful basis, source, stores, processors, retention, deletion method, transfers, and owner. It is both the inventory and the records of processing, with a processor's own record of the processing it does for others (Art. 30(2)). *Avoid:* copying real values into it: it describes the data. |
| Data-subject rights | What a person may ask of the data about them under GDPR Art. 15-22: access, rectification, erasure, restriction, portability, objection, and a person behind an automated decision. Each one that a change touches is an endpoint, an Acceptance item, and a test that the verifier writes. The `privacy-by-default` pack lists them. CCPA/CPRA grants comparable rights in California. |
| DORA (EU) 2022/2554 | The EU Digital Operational Resilience Act, Regulation (EU) 2022/2554, applied from 2025-01-17. It sets ICT risk, incident reporting, resilience testing, and third-party risk rules for banks, insurers, investment firms, and other financial entities. *Avoid:* "DORA" alone where the delivery metrics could be meant. |
| Records of processing | The register GDPR Art. 30 asks a controller to keep: purposes, categories of people and data, recipients, transfers, retention, and security measures. In aidd it is the data map, never a second file. |
| Release cooldown | The days a new release waits before a project's update bot moves its lockfile to it: 3 after a patch, and 7 after a minor or a major. Dependabot calls it `cooldown`, and Renovate `minimumReleaseAge`. A security release skips the wait. |
| SRS | A software requirements specification in ISO/IEC/IEEE 29148's outline, generated by `aidd new srs <INTENT-ID\|product>` from the approved Specs' Acceptance, each requirement with its test and commit. It is an export, never hand-kept, and never a Spec. |
| Test plan | The `test-plan` doc, in ISO/IEC/IEEE 29119-3's information items. The verifier writes it at two scopes. A Spec's plan (`aidd new test-plan <topic> --spec <ID>`) says how each Acceptance id is tested, and Spec approval freezes it with the tests. A component's plan (`--living`, in `docs/testing/test-plans/<component>.md`) is living: its strategy, environments, risk register, and test catalog, with a link to the generated trace. |
| Threat model | The `threat-model` doc of one component, in `docs/security/threat-models/<component>.md` (`aidd new threat-model <component> --spec <ID>`). The security engineer keeps it, and it stays living. Each Spec that changes the component updates it, and the Spec freezes only its own part. |
| Vendor register | The repository's one `vendors` doc, `docs/vendors.md` (`aidd new vendors`). It gives each third party's service, the data shared, its risk tier, the assurance seen, its SLA, its exit plan, the renewal date, and the owner. The data map holds its Art. 28 contract. `aidd validate` warns 30 days before a renewal. |
| Vulnerability policy | The repository's one `vulnerability-policy` doc, `docs/security/vulnerability-policy.md` (`aidd new vulnerability-policy`), which the security engineer keeps. It says how to report a vulnerability (a `security.txt` with `Contact` and `Expires`), the triage, the fix times, the advisories and VEX, the weekly rescan, and, with the `cra` target, the CRA support period and reporting. |

## Standards and evals

You meet these when you keep the standards current or measure the team.

| Term | Meaning |
| --- | --- |
| Citation | The `citation` of a standard: the page it was read on, `citation.url`, and the words copied from that page, `citation.quote`. The registry, an extension, and a library standard hold one in the same shape. It makes a `checked` date a check, and `aidd eval standards --online` fetches the page again to find the words. It is never evidence, which is a runner's exit code. |
| Cost per pass | What an eval run spent for each trial that passed: the dollars of every trial, failed ones too, divided by the passes. `aidd eval routing`, `roles`, and `tasks` report it when the agent command emits `stream-json`, and a trial with no reported cost leaves it blank. |
| DORA metrics | The software delivery measures from the DORA research program: change lead time, deployment frequency, failed deployment recovery time, change fail rate, and deployment rework rate. *Avoid:* "DORA" alone where the EU regulation could be meant. |
| Held-out case | An eval case that no one tunes against, about one in five: its `tier` says `held-out`, and `evals/held-out.lock.json` holds a hash of its content and the date its score was first read. `aidd eval routing`, `roles`, and `tasks` score the held-out cases apart from the development cases, so a gain on one set that the other does not share shows as overfitting. A test fails on a case edited after that date, and on a skill, a role, a doc, or another case that quotes one. An edited case becomes a development case, and a new case is written blind for the held-out set. |
| Industry standard | A standard of type `industry`: what the field agrees on, such as WCAG, SLSA, or a law. It lives only in the standards registry, never in a project's `standards`, and the packs and practice skills cite it. A project only waives it, with a reason and an expiry. |
| Loop version | `loop.version` in `schemas/roles.json`, in semantic versioning. Adding, removing, or reordering a step, an ask, or a route bumps the major number. |
| Maturity | `established` (the default) or `emerging`, on every standard and extension in the registry. Emerging means a draft, a first edition, a pre-1.0 release, a community extension, or a practice adopted by few. A role applies an emerging one only when the change clearly needs it, and says so in the Spec. |
| Method | How aidd works: the loop, the routes, the risk rules, Conventional Commits types, and `Assisted-by:`. It is never a standard of either type, and never an open choice. |
| Opinionated standard | A standard of type `opinionated`: one choice that a team or a company commits to, with its why. It applies only where a project adopts it, and a company can require, exclude, or replace it (`standards_policy`). aidd's library holds the proven ones ([STANDARDS.md](STANDARDS.md)). *Avoid:* "house standard". |
| Project shape | The type, stage, team, and regulation of the project an eval case or a core test fixture shows, as `type/stage/team/regulation` from the axes in `evals/shapes.json`, such as `cli/greenfield/solo/unregulated`. A type of `any` says the case holds whatever the project builds. `evals/README.md` counts each type against each value of the other axes, so a pair no case covers shows as a case to write. |
| Role eval | A scenario with a seeded defect sent to one team role (`aidd eval roles`), scored on what the role must find and must not do. |
| Stack | A set of opinionated standards that go together, plus entries for `project.stack`, such as `python-cli`. It holds no rule text, and it extends at most one other stack. `aidd standard add --stack` adopts one. |
| Standard | A rule that agents read before a step: an industry standard in the standards registry, or an opinionated standard in a `standards` entry of the config. A copy of a library standard records its id, aidd's version, and its hash. |
| Standards registry | Every standard a role, a domain pack, or a practice skill applies, in `schemas/industry-standards.json`. Each records its source and, where one is published, a `citation` with a quoted sentence, its edition where it has one, and a `checked` date. `aidd eval standards` fails on a stale date and on unconfirmed or unsourced entries. |
| Transcript | A harness's recorded event stream for one run, read as the files it opened, its tool calls, and its usage, with no model. `aidd eval transcript` prints it. |
| Work history | What a repository's own commits, files, and records say about how its work went, read with no model by `aidd eval work`. It gives four baselines: flow efficiency, suite runs per head, decisions per change, and the wait for Spec approval. It also gives signals by role step, harness, and model: the Verify reject rate, rework loops, spend, and reverts. Each figure shows its case count and says "too little data" below five. It also gives a stall reading: the Specs by furthest step across every worktree and branch (stub, filled, tests written, ready, approved), and the days since the last commit in their scope. |
| World | The programming language and the business domain a live eval case's project is set in, such as `python-commerce`, from the list in `evals/worlds.json`. Each world has a small seed project that a test builds and checks. No world, language, or domain may have more than 40% of the live cases, except what `over_cap` lists at its count, and a count may only fall. A project shape says what kind of project a case shows, and a world says which one. |
| Writing level | How a text is written, set by what the text does: `instruction`, `plain`, or `controlled`. `instruction` follows the writing rules of ASD-STE100 Simplified Technical English without its dictionary, and fits steps, rules, and messages inside the team. `plain` follows ISO 24495-1, and fits text that explains or that people outside the team read. `controlled` follows all of ASD-STE100, dictionary included, for the doc types a project lists in `project.writing.controlled`. The ids are aidd's own names, not ASD-STE100's. It is not the Level of an action. |
