# Glossary

These are the approved terms, one meaning each: the `ste-80` level of the [plain-language skill](../plugins/aidd-team/skills/plain-language/SKILL.md) uses them.

**New to aidd?** These carry your first hour: Four decisions, Spec, Spec approval, Merge approval, Land, Publish, Loop, Route, Profile, Guard, Gate, Evidence, and Always-on rules. The rest can wait until you meet them.

| Term | Meaning |
| --- | --- |
| Advisory mode | `mode: advisory` in the config, the default of the solo and team profiles when the config sets no mode (or the gate workflow's input). The guard notes, and lets through, an edit the rules forbid, and the gate posts its verdict on `aidd/gate (advisory)`, which never blocks a merge. The always-on rules still hold. |
| Agent | An AI system that does work in the repository: plans, Specs, designs, code, and reviews. It runs in a harness. An implementer, never an Approver. |
| Agent role | One of the optional aidd-team roles ([TEAM.md](TEAM.md)): a subagent guided to write only its own files. Never an Approver. |
| AIDD | AI-Driven Development, the method: the loop, the routes, the four decisions, the objects, and the profiles. Write it in capitals when it means the practice: the AIDD loop, an AIDD Spec, an AIDD delivery team. |
| aidd | The software: the CLI and Python package, the `aidd` and `aidd-team` plugins, the skill, the `.aidd/` directory, the `aidd/gate` status, and the release number. Write it in lowercase always, even at the start of a sentence. |
| aidd-team | The optional plugin that runs the loop with a cross-functional delivery team of agent roles, led by humans ([TEAM.md](TEAM.md)). |
| `aidd/gate` | The required status that the gate posts. Green means that every rule holds. *Avoid:* calling a person's decision a gate. A person gives an approval; the gate checks for it but never makes it. |
| Always-on rules | What holds in every mode, advisory included. No agent approves, lands, merges, or publishes for a person, or changes their decision records. No agent loosens the config's profile, mode, or gates, changes the files that load the guard, or rewrites or deletes the default branch. *Avoid:* "the floor". |
| Approver | A person in `owners.approvers`, eligible to approve a Spec or a change. Not an author, except under solo. *Avoid:* "reviewer" for an Approver. The reviewer role is an agent that writes findings and never approves. |
| Architecture overview | `docs/architecture/README.md` (`aidd new architecture`): the one living page of how the system is built. Its shape is arc42 cut short: the context, a C4 container diagram, the key runtime flows, and deployment. It also has cross-cutting concepts, each linked to its ADR, quality targets, risks, and fitness functions. It is never frozen: a tech spec starts from it and shows only what changes. After Roll out, the approved design is folded back into it. *Avoid:* a per-Spec copy of the architecture. |
| `assisted_by` | The `harness/model` values of every agent that wrote code or tests. It must be non-empty whenever a commit names an agent: an `Assisted-by:` trailer, a `Co-authored-by:` agent, or a bot author. Under audited, every commit carries a trailer (`Assisted-by: none` when no agent wrote it). |
| Author | The people accountable for a change: the PR/MR author plus every commit author and committer. They cannot approve their own change, except under solo. |
| Authorization matrix | The `authz` doc that a Spec links (`aidd new authz`). It has a row for each subject and action on each resource or endpoint. Each row gives the row-level condition, the expected allow or deny, and the test that proves it. The security engineer writes it; the verifier writes one test per row. |
| Autonomy stage | What `aidd metrics --autonomy` suggests for an agent and a kind of change, from its gate events: review every change, review the trade-offs, or candidate standard change. A person decides whether to act on it. |
| Big goal | An ask that takes more than one Spec, written as an Initiative of small goals. It is done when every small goal is released, any launch is done, and its outcome is measured. |
| Blast radius | Who or what behaves differently if the change is wrong. Recorded as `risk.summary` and `risk.dimensions`. |
| Blocked | A flag on open work, never a Spec status (a Task's derived status may be `blocked`). Work is blocked when `blockers` names a wait, when an item it is `blocked_by` has not landed, or when a Task used its 3 retries. `aidd list` shows it with the reason, and `aidd list --blocked` lists every one. |
| Brownfield | Adopting aidd in an existing codebase: advisory mode first, the real layout mapped, and characterization where tests are thin. |
| Change order | A change to an approved Spec: `aidd revise <ID> "<why>"` reopens it, and Spec approval comes again. A person's direct ask that changes the scope, the Acceptance, or the tests is one, never a quiet addition. |
| Change Request | The PR/MR. Its description may hold one Change Request block (see that row). *Avoid:* "PR" alone in text meant for every platform: say PR/MR. |
| Change Request block | The optional fenced block (```` ```yaml aidd ````) in a PR/MR description that tells the gate about the change. A change needs one only to raise its route, declare a risk or a scope, claim a standard change, carry an emergency, or name its Spec when the diff carries several. A block that names a Spec (`spec: specs/<ID>.md`) holds nothing else. An inline one declares its `route`, and may add `type`, `risk`, `scope`, and `assisted_by`. With no block, the gate derives the declaration from the diff and its commits. `aidd describe` prints one. The gate recomputes the route from the diff and can only raise it. *Avoid:* "toml aidd block", "change block", "inline block". |
| Changed-line limit | The most changed lines that a route allows (`max_changed_lines`, per profile in [METHOD.md §9](METHOD.md#9-profiles)), checked by the gate's `changed_lines` rule. It excludes `changed_lines_exclude_paths`. For a Spec, it also excludes the Spec and the files that Spec approval froze. *Avoid:* "budget" for it, which names what the project may spend (`project.budget`). |
| Change record | `change-record.intoto.json`, which `aidd gate --record` writes beside the gate record. It is an in-toto statement of the decision, and its subject is the head commit. It holds the tenant, the route, each approval, the red and green exit codes, and the finding codes ([METHOD.md §7](METHOD.md#change-record)). It is unsigned unless the gate workflow signs it; `aidd record verify` checks it. *Avoid:* confusing it with the gate record (`aidd-record.json`), which holds every rule's result. |
| Characterization | Pinning today's behavior with a test before changing code that has none. |
| Component spec | A row and a subsection in `DESIGN.md`'s Components section. It is written only when a component is new or changed, as its own design-system change. It gives the component's purpose, anatomy, props and variants, every state, and accessibility. It also gives the tokens it uses by name from `design/tokens.json`, and its test ids. Frozen with the Spec. |
| Context (gate) | The facts an adapter collects for the gate: diff, commits, reviews, comments, evidence, policy. |
| Contract (SOW) | The `contract` doc in an accepted proposal's folder (`aidd new contract <proposal id>`; each later call writes the next change order, `change-orders/CO-<n>.md`). It is a statement-of-work base for a client engagement. It gives the scope by Acceptance ids, the deliverables, and the proposal's milestones and assumptions by id. It also gives change control, support levels, the acceptance period, the warranty, and the clauses marked for a person or a lawyer. Living; a base to review, never legal advice. |
| Control band | The range `aidd observe --band` expects a metric in: its recent baseline plus or minus a number of standard deviations. 2 lets an agent diagnose read-only, and 3 lets it suggest a change as a draft Spec. Set per metric in `observe.bands`. |
| Cost estimate | What a change will cost to run, in its Spec (`cost_estimate`): monthly at today's load and at 10x, with its source. The architect gives it in Specify, and `aidd validate` warns when infrastructure code or a cost risk has none, or when it is above `project.budget.max_infra_per_month`. *Avoid:* calling the changed-line limit of a diff a budget; the project's ceiling is `project.budget`. |
| Data map | The repository's one living `data-map` doc, `docs/data-map.md` (`aidd new data-map`), linked by each Spec that touches personal data. It has one row per personal-data item and purpose. Each row gives the category, lawful basis, source, stores, processors, retention, deletion method, transfers, and owner. It is one file per product, not per Spec, and it is both the inventory and the records of processing. Each Spec that touches personal data revises it in its own diff, and the erasure and export tests read it. *Avoid:* copying real values into it: it describes the data. |
| Data-subject rights | What a person may ask of the data about them under GDPR Art. 15-22: access, rectification, erasure, restriction, portability, objection, and a person behind an automated decision. Each one that a change touches is an endpoint, an Acceptance item, and a test that the verifier writes. The `privacy-by-default` pack lists them. CCPA/CPRA grants comparable rights in California. |
| Day 0 | A new repository's first commit: the aidd setup and the project scaffold. It is committed straight to the default branch, as the baseline that every later change is gated against. |
| Decision card | An exploration with no visuals (`aidd new exploration`) for one choice that a person must make. It gives the question, the options as directions with their trade-offs, and the agent's recommendation. A handoff note's Needs line names its path; the person decides, never the card. |
| Decision records | The commits on the private ref `refs/aidd/decisions` where aidd records each decision a person makes on this machine: a Spec approval, a Merge approval, a typed `land it` or `publish`, and a standing approval. Each names the person's git identity, and under `gates.local_approvals: signed` only a listed signer's counts. `aidd publish` pushes them with the work, unless `--no-records`. *Avoid:* "ledger", "approvals ref", and "approval record" for them, and confusing them with the gate record. |
| Deep link | The address of one view of a prototype: `prototype.html#<screen>/<state>?theme=dark&frame=ios&mode=wireframe&round=2`, each key optional. Opening it restores that screen, state, theme, frame, and fidelity; every switch in the prototype updates it. Screenshots, tests, review comments, and feedback notes point at a view with it. |
| Delivery team | The aidd-team roles together: product, design, architecture, security, compliance, testing, software, AI, data, documentation, verification, review, delivery infrastructure and reliability, and process improvement. Each is an agent limited to its own files; humans hold every decision. |
| Deprecation calendar | Each Spec's `deprecations`: what is deprecated, the day consumers were told (`announced`), the day it stops working (`sunset`), and what replaces it. The Spec that removes one lists it in `removes_deprecations`, and the removal counts once that Spec lands. A passed sunset warns in `aidd validate`, shows in `aidd list`, and is overdue in `aidd digest`; `aidd digest --client` lists the landed ones. Never a gate rule. |
| Derived status | A Spec's status, which aidd computes from what git and the platform prove. Ready comes from a counted Spec approval of the Spec as it reads now, and in progress from commits in a Task's scope. In review comes from green evidence on head, landed from the land or the merge, and done from a healthy observe window. aidd stores only what nobody can observe: cancelled, rolled back, an Epic's done, a proposal's outcome. The `status` field is an optional cache ([METHOD.md §5.1](METHOD.md#51-status)). A Task's derived status is its own: `todo`, `in_progress`, `blocked`, `stopped`, or `done` ([ORCA.md](ORCA.md#one-agent-per-task)). *Avoid:* "set the status to ready": aidd derives it; a person approves. "A ready Task": `ready` is a Spec status; a Task an agent may start is `todo`. |
| Design direction | One of two or three rough, low-fidelity takes on the same brief that the product designer offers before any detailed prototype. A person picks one, and the Spec's `## Design` section records the pick with who, when, and why. Only then is it built in detail. *Avoid:* "approving" a direction: picking one is a recorded decision, and the design is approved only at Spec approval. |
| Design files | `design.files` in a Spec: the prototype, the design spec, the flow diagram, and the rough directions, never a copy of the design system. Spec approval freezes them with the tests. They are never implementation scope, and product code never imports them. *Avoid:* "mockups" for the whole set: a mockup is one kind of design file. |
| Design spec | The `design-spec` doc a Spec links (`aidd new design-spec <topic> --spec <ID>`): the screens by state and by target, the flows, the copy, the accessibility, and the usability test, next to the HTML prototype (`--prototype`). The product designer writes it, and Spec approval freezes it. It uses the repository's one design system (`DESIGN.md`) and never copies it. *Avoid:* "ui doc". |
| Design system | The repository's one `design/tokens.json` and `DESIGN.md`, written with `aidd new design-system`. `design/tokens.json` is the one source, in the Design Tokens format; `DESIGN.md`'s token front matter mirrors it. After that front matter, `DESIGN.md` (in Google Labs' design.md format) gives principles, color roles, themes, type, layout, motion, components and states, patterns, and accessibility. Prototypes and screens use the tokens and never copy them. A change to the design system is its own change, routed normal by `baseline:design-system`. |
| Digest | `aidd digest --since <date or tag>`: a status rollup from what aidd already knows. The team view lists what landed, what is in progress, who each open step waits on, what is blocked, and the Needs and decisions. It also lists the scope decisions reversed, the risks, the overdue flags, deprecations, outcomes, waivers, and runbook drills, the feedback themes, and the gate metrics. `--client` gives the client's view instead (see RAG status). A report for people, never evidence. *Avoid:* confusing it with the approval summaries `aidd hash --summary` prints. |
| Dimension | A kind of blast radius in words any role uses: `data`, `security`, `privacy`, `financial`, `compliance` (force major and name a pool), `availability`, `third_party`, `cost` (rule out minor). |
| Dirty tree | A working tree that holds what the head commit does not: uncommitted changes, untracked files no `.gitignore` ignores, or files git is told not to look at. Tests that ran in one prove nothing about the head, so the gate takes none of their results (`tests.dirty_tree`). The evidence records it as `dirty_tree`, and `dirty_paths` lists the first of those paths. |
| Domain pack | A skill (`aidd-team:<pack>`) generated from `schemas/packs.json` for one domain. It holds its standards with editions and checked dates, a checklist per loop step, and executable checks for the Spec's tests. It is loaded on top of a role for every domain that a change touches. |
| Domain expert | A person who knows one business area deeply (payments, clinical safety, tax, a regulator's rules). In aidd, a specialist Approver: a member of a named pool in `owners.specialists` that a risk rule sends changes to. A major change in that area then needs their approval ([Adoption](ADOPTION.md#domain-experts-as-specialist-approvers)). The `domain-expert` agent role only advises, with a perspective card, and never approves: the person decides. |
| Done when | What finishes a loop step, written under each step of the loop ([the skill's loop](../.agents/skills/aidd/references/loop.md)). Finish the open step before the next one. *Avoid:* "done-gate": the gate is `aidd/gate`, and a step's done when is a condition the agent checks. |
| DORA metrics | The software delivery measures from the DORA research program: change lead time, deployment frequency, failed deployment recovery time, change fail rate, and deployment rework rate. `aidd metrics --dora` reports proxies for them against `targets`. *Avoid:* "DORA" alone where the EU regulation could be meant. |
| DORA (EU) 2022/2554 | The EU Digital Operational Resilience Act, Regulation (EU) 2022/2554, applied from 2025-01-17. It sets ICT risk, incident reporting, resilience testing, and third-party risk rules for banks, insurers, investment firms, and other financial entities. *Avoid:* "DORA" alone where the delivery metrics could be meant. |
| Emergency | The route for a production repair. It is allowed under a freeze, and it needs smoke tests, a named human commander, a committed backfill Spec, and a review by `review_due`. |
| Enforce mode | `mode: enforce` in the config, the default of the org and audited profiles when the config sets no mode (or the gate workflow's input). The guard denies an edit the rules forbid, and the gate posts its verdict on `aidd/gate`, which blocks a merge once the platform requires it. The always-on rules hold as in every mode. |
| Epic | An optional container above Specs: a small goal. |
| Evidence | `.aidd/evidence/evidence.json`: exit codes per command and phase, bound to the head SHA. *Avoid:* calling a pasted log, a screenshot, or an agent's statement evidence. Model prose is never evidence ([METHOD.md](METHOD.md)); a log counts only as the test runner recorded it. |
| Experiment | A Spec's optional `experiment` block: the A/B test that decides its hypothesis. It is planned before launch, with its variants, one primary metric, guardrails, a minimum sample or a duration, and the decision rule. A sample ratio mismatch or a guardrail breach stops it ([spec fields](../.agents/skills/aidd/references/spec.md#experiment-experiment)). |
| Exploration | Two or three divergent directions for one question, in a folder with `exploration.md` (`aidd new exploration`). The folder sits in the work item folder of the item it informs, `specs/<ID>/explore/<slug>/`, or in `specs/explore/<topic>/` while no work item exists yet. Its front matter follows `schemas/exploration.schema.json`: the question, the owner role, a timebox, the status. Each direction then follows, with its trade-offs. `aidd explore` renders it as one comparison page for a person to pick from (`/aidd-team:explore`). The owning role records the pick and why in the Spec's Design section, `DESIGN.md`, or an ADR. A direction that needs real code to judge is built on an explore branch, which only a person starts. *Avoid:* an agent picking the direction, and calling it an explore branch, which is free work outside the loop. |
| Explore branch | `explore/<topic>`: free work, such as a spike or a prototype. The guard allows every edit there, and the gate always fails a change from it (`explore.branch`). Only a person starts one, by typing `explore branch <topic>` at the prompt: aidd records it as theirs and switches to it. A branch that only has the prefix, made with git, is ordinary. Renaming it brings the work into the loop. *Avoid:* calling it an exploration, which compares directions inside the loop, or an explore branch, its name before 1.0 (`explore/`). |
| Extension | A skill, plugin, MCP server, or tool that a team role loads on top of its packs. `schemas/roles.json` lists them per role as starting points. Each is verified and pinned, and installed through a change. |
| Fast lane | The lane of standard and minor changes, and the default: Implement ⟲ Verify, Review, Merge approval, Publish, and Roll out, with no Spec file. The gate takes the route from the diff, so the change needs no Change Request block, and one Merge approval merges it (none for a standard change). |
| Feedback log | The living `docs/feedback/<topic>.md` (`aidd new feedback <topic>`), with one row per piece of post-launch feedback. Each row gives its date, channel, customer or segment, quote, theme, severity, an optional 0-10 score, and the Spec or hypothesis it concerns. `aidd digest` counts its themes and the NPS; the product manager reads it at Learn. |
| Finding code | A gate finding's stable name, `rule.reason`, such as `scope.outside`. [ERRORS.md](ERRORS.md) lists every one with what fires it and its fix, each at its own anchor (`#scope-outside`). The same page lists the step codes, the guard's reason codes, and the exit codes. A finding can be a warning, a wait, or a failure. |
| Fitness function | An architectural rule that a machine checks, run as an ordinary test command. It is a layering rule that the architecture overview declares, checked by a tool such as import-linter, dependency-cruiser, ArchUnit, or NetArchTest. So a change that breaks a layer turns the tests red. |
| Flow | The roles a team command runs, in order, with the groups that run in parallel and the human decision it stops at. A person types the team command (`/aidd-<flow>`), and the flow is its steps. The data is in `schemas/roles.json`, and each command is tested against it. *Avoid:* "workflow" (a CI workflow), "program", or "playbook" for a team command. |
| Four decisions | What only a person decides: D1 the plan, D2 Spec approval, D3 the release, and D4 the launch. A standing approval covers D2 and D3 (publishing only as `approve all and publish`), never D1 or D4. |
| Freeze | A Policy answer that stops every route except emergency. *Avoid:* "freeze" for what Spec approval does to test and design files: say they are frozen by Spec approval, not under a freeze. |
| Gate | The check on each change before it merges: `aidd gate`, the program that decides a change, a pure function from context to pass, pending, or fail. The adapter posts its decision as the `aidd/gate` status. *Avoid:* "the verifier" for the gate: the verifier is a team role. |
| Gate record | The decision file `aidd gate --record` writes: `aidd-record.json` in CI, and `.aidd/evidence/record.json` locally (where `aidd log` reads it). It holds the decision, each rule's result, and the approvals, evidence, and agents that the gate counted. It is validated against `schemas/record.schema.json`; what each field evidences is in [CONTROLS.md](CONTROLS.md#what-the-record-evidences). |
| Glossary | The repository's one `glossary` doc, `docs/GLOSSARY.md` (`aidd new glossary`): the project's terms, one meaning each, with the words to avoid. It is living: Clarify adds a term once the author settles it. This page is aidd's own glossary. |
| Go/no-go | The first human decision on a Proposal: pursue it or not, recorded in `go_no_go` before the team drafts. |
| Goal | `goal` in the config: the team's current measurable target, one sentence the humans agree on, that every agent steers by when a choice is open. It sits under the mission and changes when the target does. Not a big or small goal: those are an Initiative and an Epic. |
| Goal branch | `goal/<EPIC>`, the branch of a small goal that reaches users `batched`. `aidd goal open` cuts it, only `aidd integrate` and `aidd sync` move it, and the small goal has one release: a person's Merge approval of the goal branch's head, then publishing it. *Avoid:* "workspace". |
| Greenfield | Adopting aidd in a new repository: Day 0, then a first Spec that brings the test runner and the first test. |
| Guard | The check on each step an agent takes: `aidd hook pre-tool` and the MCP `check_edit` tool. They allow or deny, and never prompt mid-build. They deny an edit outside the active Spec's `scope`, and an edit to a test or design file once Spec approval froze it. They also deny an edit to a protected path outside an approved scope. Each deny names its route. In advisory mode they note those edits and let them through; on an explore branch they allow every edit; the always-on rules hold in all three. A local guide; the gate decides. *Avoid:* "edit-time guard", "edit guard": it checks shell and MCP tools too. |
| Handoff note | The lines every team role ends a run with: Done, Next, Needs, Stopped at, and an optional Spend. The next role reads it before the file. It is written into the Spec or the PR/MR as a fenced `aidd-handoff` block of YAML (`done`, `next`, `needs`, `stopped_at`, optional `spend`). `aidd list` and the session hooks read it to name the role that has the work and to surface Needs to a person. Never evidence; the Spec hash leaves it out. |
| Handover | Passing a client's product to the client's team (`/aidd-team:handover`). The `## Handover` sections of the acceptance record and the runbook list the docs index, the credentials transfer log (never a secret), and training. They also list open issues and the warranty start. There is no third file. *Avoid:* confusing it with a handoff note between roles. |
| Harness | The program that runs a coding agent and its tools: Claude Code, Codex, Cursor, Copilot, and the others `aidd init` wires ([INSTALL.md](INSTALL.md#your-coding-agent)). An `Assisted-by:` trailer names it with the model, as `harness/model`. |
| Head SHA | The commit at the tip of the change. Evidence and approvals bind to it. |
| Human | A person, not an agent. Say "human" in contrast with agents: human approval, humans decide what lands and what leaves this machine, agent roles led by humans. Say "a person" for the one who acts in a step: a person approves at their own terminal, a person runs the rollback. In a guide, say "you" to the reader who acts. *Avoid:* "people" for Approvers or for the ones who decide, and "user" for an Approver. |
| Human feedback | The paths on which a person sends work back. Spec approval with changes requested goes to Specify. Merge approval with changes requested, or a review comment, goes to Implement. Roll out's incident, rollback, or missed hypothesis goes to Learn. Learn's lesson goes to Plan as a new change. Dashed in the loop diagram. |
| Hypothesis | A Spec field, frozen by Spec approval: the metric a change should move, its baseline, the expected move, and by when. Learn records `outcome.result` against it; a miss is a product decision, not a rollback. |
| Implement | The loop step where the change is built, one Task at a time, inside its scope, checked at every edit. It loops with Verify until the head is green. |
| Implementer | Whoever writes the change: usually an agent, directed by the author. Never an Approver of their own work. |
| Incident commander | The human named in an emergency block who runs the incident. They are an eligible Approver, not an author, and must approve the repair. |
| Industry standard | A standard of type `industry`: what the field agrees on, such as WCAG, SLSA, or a law. It lives only in the standards registry, never in a project's `standards`, and the packs and practice skills cite it. It applies everywhere, and a project only waives it, with a reason and an expiry. A company policy can never exclude or replace one. |
| Initiative | An optional container above Epics and their Specs: a big goal. |
| Inner loop | Autonomous agentic execution: Specify, Implement and Verify (repeated until green), Review. The agent drafts the contract in Specify, and Spec approval freezes it. The agent then works inside the contract, bounded by the Task's scope, red-then-green, and three retries. |
| Integrate | `aidd integrate`: land a Spec's branch in its goal branch. It needs the Spec's approval, its tests green on the merged tree, and a gate that waits only for the release. The team runs it, and `--undo` takes a Spec out. |
| Journey map | The `### Journey` of an Initiative's `## Brief`, for discovery. It gives one persona's stages by goals, actions, touchpoints, thoughts, pain points, and opportunities, with a service blueprint (frontstage, backstage, support processes). The product manager or the product designer keeps it; it never holds the solution. |
| Label | One of up to eight lowercase tags on a Spec, Epic, or Initiative (`labels: ["area:billing"]`), for filtering with `aidd list --label`. It never changes the route or the gate, and the Spec hash ignores it. |
| Land | Merge approval on a local trunk, and the merge it makes: the person types `land it` (or runs `aidd land`), and the change merges into the local trunk once the local gate passes. Like `merge it`, their `land it` covers a later fix of the same work while the Spec and its tests stay as approved. On a platform, only `merge it` approves the merge. *Avoid:* "ship": it named landing, publishing, and merging at once. |
| Landed | The derived status of a Spec whose approved content is on the trunk: it landed locally, or merged on the platform. Done follows once nothing is to be watched, or the observe window passed. *Avoid:* "shipped", and "released" for a landed Spec: a release reaches users. |
| Lane | The path through the loop that follows from the route: fast (minor, standard), spec (normal, major), or emergency. *Avoid:* "route" for the lane. The route is how much control a change gets; the lane is its path through the loop. |
| Launch | D4: the Merge approval of a `flagged` Epic's `launch` Spec, which turns the feature on for users. Always a person's: a standing approval never covers it. |
| Lead | The session that runs the team: autopilot, or the main session. It takes the team's decisions (who does what, sending work back, taking a Task in), each on its evidence, and never an approval: it is no second stakeholder. |
| Learn | The loop step after Roll out. It runs on a signal (a Merge approval rejection, a rollback, an incident, three failed retries) and on a cadence (the retrospective). Each lesson becomes a change to tests, rules, or agent instructions, linked in `outcome.learn_ref`. |
| Local approval | A Spec approval or Merge approval that a person records on their own machine, with no platform: `aidd approve spec` or `aidd approve merge`. It is one of their decision records. Weaker than a platform's approval ([METHOD.md §8](METHOD.md#local-approvals)). |
| Local trunk | The default branch on this machine while it holds all of the remote's branch and more: work landed here and not yet published. aidd reads it as the base. `aidd list` says how far it is ahead, and warns when its oldest unpublished commit is old. |
| Loop | Every change runs the one loop: Plan, Specify, Spec approval, Implement and Verify, Review, Merge approval, Publish, Roll out, and Learn. A person runs the outer loop and the team the inner loop. It is always on, and what is checked follows the branch. |
| Loop version | `loop.version` in `schemas/roles.json`, in semantic versioning. Adding, removing, or reordering a step, a human approval, or a lane bumps the major number. Gate events carry it as `loop_version`. |
| Major | A route computed by the gate: a protected path, a major dimension, an irreversible change, or a major type. Normal plus specialist approval, an observe block, and stricter profile gates. |
| Maturity | `established` (the default) or `emerging`, on every standard and extension in the registry. Emerging means a draft, a first edition, a pre-1.0 release, a community extension, or a practice adopted by few. A role applies an emerging one only when the change clearly needs it, and says so in the Spec. |
| MCP server | `aidd mcp`: aidd's checks as agent tools over the Model Context Protocol. |
| Merge approval | A human's approval of what was built: the exact head commit, as a platform review (solo also: `/aidd approve-merge <full head SHA>`). Rule `merge_approval`. *Avoid:* "sign-off" for it, and calling the reviewer role's findings an approval: only a person's approval of the head commit lets the change merge. |
| Merge it | The person's typed `merge it`: their Merge approval on a pull or merge request, with its auto-merge, so it merges once `aidd/gate` passes there, where the base branch requires `aidd/gate`. It covers a later fix of the same work while the Spec and its tests stay as approved. |
| Merge queue | A platform queue that tests each change merged onto what lands ahead of it, before the change reaches the base branch. It is GitHub's merge queue, or GitLab's merge train. The gate judges each entry on the commit the queue built for it, and approvals stay on the pull or merge request head. The gate's context carries it as `merge_queue`, and `aidd test --merge-queue` runs the tests there in CI. *Avoid:* "merge group" and "car" for an entry, except in GitHub's or GitLab's own words. |
| Method | How aidd works: the loop, the routes, the approvals, the gate rules, Conventional Commits types, and `Assisted-by:`. It is never a standard of either type, and never an open choice. |
| Milestone | A `milestones` entry on a proposal (as promised) or its Initiative (the delivery record). It has a `due` date and the trigger that reaches it: the client's acceptance of listed Acceptance ids, the listed Specs landed, or an event. It gets `reached_on` once a person records it (or every trigger Spec landed). It may also give the amount and currency that a person invoices. |
| Minor | A small, reversible change with no Spec file and no risk dimension. With no Change Request block, the gate takes its type from the commit subjects and `assisted_by` from the trailers. The changed paths are its scope unless a block declares one. |
| Normal | The route for a change that needs a Spec but touches nothing major. It needs Spec approval before the code, from the team profile up; under solo, only major needs it. It also needs frozen tests, red-then-green, and one Merge approval. It takes the spec lane. |
| Mission | `mission` in the config: the team's enduring purpose, set by humans, which changes rarely. The goal is the current measurable target under it. `aidd list` opens each Spec's why chain with it, and the session-start hook briefs the agent with both. |
| Mockup | A static picture of a screen, such as a frame exported from a design tool into `design.files`. Not an aidd artifact: aidd's is the prototype, which responds to input. *Avoid:* "mock" for the prototype. |
| Observe window | `observe.window` in a Spec: how long after release the change is watched, with the command or signals that judge it and the `rollback_trigger`. It is required on major, and on normal under audited. `aidd observe` runs the check once. |
| Outer loop | Human strategy and governance: Plan, Publish, Roll out, Learn, and the two approvals. An agent drafts all of it and decides none of it. |
| Outside change | A change to what the always-on rules stand on, made outside the agent's session since the person's last decision. At each decision aidd keeps the watched state, what those rules stand on, in `.git/aidd/watched-state/`. It covers the config's control keys, the guard's wiring, HEAD's branch, the decision records, the base branch, the git hooks, and the user's aidd launcher. A program the agent runs can make one. It's part of the person's next decision: a dialog lists it before they answer, and aidd's note after a typed decision lists it, with how to put each back. Claude Code shows that list to the person directly. A looser config, a rewritten history of decision records, or a signed record aidd can't verify waits for a dialog that showed it, or the person's own terminal. A change that could stop the guard itself, such as a git hook or a git config key that names a program, waits for aidd's own MCP dialog or the person's terminal. Until then the guard keeps the stricter rules. When one comes after their decision, an agent's `aidd land`, `aidd approve`, or `aidd publish` stops and names their words to say again. Ordinary work is never paused. aidd shows it, and never prevents it. *Avoid:* "tamper protection", since it only shows. |
| Owner | `owner` on a Spec, Epic, or Initiative: the person driving the work, never an agent. `aidd list --mine` finds it, and `aidd list` names them as who acts. Bookkeeping: outside the Spec hash, and it approves nothing. |
| Open choice | A decision that a domain pack or a practice skill leaves to the team, such as `ci-pipeline:linter`. It is data in `schemas/packs.json` (a pack's) or `schemas/roles.json` (a practice skill's), with aidd's default answer. An opinionated standard fills it (`fills`), so the standard never restates a pack. `aidd standard list` lists them. |
| Opinionated standard | A standard of type `opinionated`: one choice that a team or a company commits to, with its why. It applies only where a project adopts it, and a company can require, exclude, or replace it (`standards_policy`). aidd's library holds the proven ones ([STANDARDS.md](STANDARDS.md)). *Avoid:* "house standard". |
| Org preset | A config the platform team owns, applied as the root parent of every repository config (`org-preset-url` on the reusable workflow, or `AIDD_ORG_PRESET`). Repositories can only tighten it. |
| Output folders | The folders aidd writes into `.aidd/`: `evidence/` (the evidence, the gate record, and `preview/<head-sha>/`, what the verifier captured) and `views/` (the decision pages). git ignores them (`/.aidd/*/`), and aidd writes them again on each run; only files directly in `.aidd/` are committed. What every worktree shares, such as the autopilot journal and the guard's log, is in `.git/aidd/` ([Architecture](ARCHITECTURE.md#state-lives-in-git-in-files-people-can-read)). *Avoid:* committing anything in them, or reading a page there as the record. |
| Plan | The optional step before the loop, for work bigger than one Spec: an Initiative, Epics, and ranked Spec stubs that a human agrees to. *Avoid:* "approve the plan": a person agrees to it. aidd keeps "approval" for Spec approval and Merge approval. |
| Policy | An optional command, run from the base branch without tokens, that can hold or stop a change (freeze calendars, deny lists). |
| Pool | A named group of specialist Approvers in `owners.specialists`: `security`, `data`, `privacy`, `finance`, `compliance`, or any name a risk rule uses. A major change needs an approval from each pool its reasons name. An unbound pool falls back to `security`. |
| Practice skill | A hand-written skill (`aidd-team:<name>`) for one kind of work: API design, schema migration, threat modeling, test design, secure coding, and more. It holds its standards, steps per loop step, test commands, and handoff, with a checked date. Each role lists its own; a Task names up to two in `skills`. |
| Preference key | A top-level key of `.aidd/config.yaml` that only describes the project and steers no check: `mission`, `goal`, and `locale` (`config_preference_keys` in baseline.json). A change that edits only these keys in the config, read by the strict reader at base and head, does not take the major route from the file. Every other key is a control. |
| Preflight | A local `aidd gate` run on a repository whose platform gate decides (it has a remote and a CI gate). It shows whether the branch is ready. It is marked untrusted, and its hints name the platform's steps. With no platform, the local gate is the gate itself. |
| Priority | `priority` on a Spec, Epic, or Initiative: urgent, high, medium, or low. When unset, it is inherited from the parent; an emergency is urgent. It orders `aidd list` and filters it (`--priority`). Outside the Spec hash, and the gate never reads it. |
| Proactive role | An agent role listed in `agents.proactive_roles`, allowed to suggest work nobody asked for, and only as a draft Spec. |
| Profile | solo, team, org, or audited, from the loosest to the strictest. It sets gate strictness. |
| Product defaults | `project.defaults` in the config: what every product gets unless a person turns it off with the reason in `off`. The defaults are light and dark themes, responsive layouts, i18n-ready strings, a performance budget, the public-page basics, and API and data conventions. They also cover operability, security headers, legal placeholders a person writes, transactional email, and the developer basics. They are built on the MVP's Day 0, and whenever a change touches the area. The config refuses one turned off without a reason. *Avoid:* "optional features": each is on until a person says why not. |
| Proposal | A case put to someone outside the team who decides, before any code. It is a bid or pitch to a client, or a change put to the company's leadership. It holds the needs and how each is answered, options, a range estimate, assumptions, exclusions, risks, and questions. Accepted, it becomes an Initiative ([METHOD.md §4.7](METHOD.md#47-proposal)). |
| Protected path | A path whose change is always major: aidd's config, CI, CODEOWNERS, agent instructions and skills, MCP config. |
| Prototype | `prototype.html` in a Spec's design folder (`aidd new design-spec --prototype`): one self-contained, interactive HTML file per Spec or flow, with every screen of it. Each screen is there in every state, theme, and frame (web 320 to 1440, iOS, Android). It has a screen menu, navigation with history, deep links, and wireframe and feedback modes. With the design spec, it is the design source of truth; it is frozen at Spec approval. Several flows get one prototype each, listed in `docs/design/index.md`. |
| Publish | The person's step that takes work off this machine: they type `publish`, or run `aidd publish`. It pushes the branch or the local trunk with their decision records. Where a platform runs the gate, it opens the pull or merge request and carries their recorded Spec approvals there. The config's `publish` says who may publish: `person` (the default) or `agents`. `approve all and publish` lets the agents publish for the person, and a fix to a published branch follows to the same remote. |
| Qualification | The delivery manager's `qualification` in a proposal before any drafting: fit, budget, authority, and decision process, with a recommendation (go, no_go, or ask). It advises the go/no-go, which a person records. |
| RAG status | The client view's red, amber, or green in `aidd digest --client`, by three written rules printed with it. Red: a milestone is past due, or an item has been blocked for more than `--blocked-days` (5). Amber: not red, and a risk or an ask of the client is open, such as a dependency past its due date. Green: neither red nor amber. |
| RAID log | Risks, assumptions, issues, and dependencies: the `risks`, `assumptions`, `issues`, and `dependencies` of the proposal, then of its Initiative once `aidd proposal convert` moves them. They share one item shape, with an owner and a status (open, resolved, accepted, invalid; only open is open). *Avoid:* a separate tracker for them. |
| Reaches | `reaches` on an Epic: how a small goal reaches users. `incremental`, the default: each Spec merges by itself. `flagged`: each Spec merges behind a feature flag that stays off until the `launch` Spec. `batched`: the Specs collect on a goal branch, released once. |
| Records of processing | The register GDPR Art. 30 asks a controller to keep: purposes, categories of people and data, recipients, transfers, retention, and security measures. In aidd it is the data map, never a second file. |
| Red-then-green | A new-behavior test fails on the base commit and passes on head. |
| Release | D3, the release: a person's Merge approval of a head, then publishing it. A standing approval covers the Merge approval, and covers publishing only as `approve all and publish`. A small goal that is batched has one release, of its goal branch. |
| Release notes | `aidd release-notes --since <tag>`: the Specs landed since the tag, each with its title, intent, flags, and deprecations. They are grouped as Keep a Changelog: Added, Changed, Deprecated, Removed, Fixed, Security. `--audience users` keeps the changes users notice. The tech writer edits the words from the `release-notes.md` template, never the facts. |
| Release cooldown | The days a new release waits before a library standard's pin moves to it: 3 after a patch, and 7 after a minor or a major. While the pin waits out aidd's release cooldown, `cooldown_until` on the standard names the day it may move, and the standard keeps the release before it on purpose. `aidd eval standards` warns once the day passes, and fails 7 days later. A security release skips the wait. *Avoid:* `version_policy: pinned` for a cooldown, because `pinned` keeps a version for good. |
| Relation | A typed link from a Spec, Epic, or Initiative to another (`blocks`, `blocked_by`, `duplicates`, `relates_to`, `implements`). `aidd validate` checks the target exists and that blocks form no cycle. `aidd list` shows work blocked_by unfinished work as blocked. The gate never reads it. *Avoid:* confusing it with a Task's `depends_on`, which orders Tasks inside one Spec. |
| Retrospective | The Learn step on a cadence. The loop inspects its own metrics and proposes at most three measured improvements. Each re-enters the loop at Plan as a new change ([METHOD.md §12](METHOD.md#12-roll-out-and-learn)). |
| Review | The loop step between Implement and Merge approval, run beside Verify on one head: the PR/MR is ready and findings, human or agent, are answered. It counts only once Verify's report on that head is clean. |
| Role eval | A scenario with a seeded defect sent to one team role (`aidd eval roles`), scored on what the role must find and must not do. |
| Roll out | The loop step after Publish: the deploy, the release to users, and the observe window. It ends when the window passes or the rollback trigger fires. `/aidd-team:rollout` runs it. *Avoid:* "ship". |
| Round | One pass of a design that a person reviews. It holds its screenshots in `rounds/<N>/` (`<screen>-<state>-<target>-<theme>.png`), and the person's `feedback-round-<N>.json` from the prototype's feedback mode, each note naming its screen and state. It also holds the next round's `changes.json`, which names the feedback each change answers. |
| Route | standard, minor, normal, major, or emergency: how much control a change gets, computed from its paths, type, and risk. The lane follows from it. It is a property of the change. aidd computes the minimum from what it touches, the author may declare higher, and the gate enforces the higher of the two. The gate recomputes the route from the real diff. Before the first edit, the gate forecasts it from the planned paths (`aidd gate --paths`); asking for it is not a step of the loop, and Clarify comes first. *Avoid:* "entry check", and saying the check picks the lane: the lane follows from the route. ITIL 4 has three change types (standard, normal, emergency); minor and major split normal by impact. |
| Rule of Two | Meta's Agents Rule of Two (2025-10-31): a run with nobody to ask holds at most two of untrusted input, credentials, and egress that no allowlist limits. Meta names the last two as access to sensitive systems or private data, and changing state or communicating externally. `aidd doctor --autopilot` warns when it sees all three, and never fails on it ([AUTOPILOT.md](AUTOPILOT.md#credentials-for-a-run)). |
| Runbook | A living doc of kind `runbook`: the operational procedure for one service, written before it is needed and tested on a schedule. `aidd new runbook` writes it in `docs/runbooks/`, and `aidd validate` checks it against its schema. `aidd validate` warns when a major Spec links none, and `aidd doctor` warns when its `tested_on` is older than `docs.max_runbook_age_days`. *Avoid:* "runbook" for the install steps in `llms-install.md`. |
| Scope | The globs a Task's diff may change (`tasks[].scope`, or `scope` in a Change Request block). |
| Separation of duties | The rule that authors and agents cannot approve their own change. Under solo, it is waived and recorded, and the Approver must still be in `owners.approvers`. |
| Severity | An incident's `severity` in the emergency block: sev1, sev2, or sev3. By default, sev1 means a critical journey is down, data is lost, or a breach touches many users. sev2 means a critical journey is degraded for many users, and sev3 means a minor feature is degraded with a workaround. When unsure, declare the higher one. A postmortem is due for sev1 and sev2, and by default when an incident uses more than 25% of an error budget. *Avoid:* confusing it with a vulnerability's CVSS severity. |
| Sign-off | The second human decision on a Proposal: it may be sent, with its price, commitments, assumptions, and exclusions. *Avoid:* "sign-off" for a Spec or a merge. It belongs to a Proposal only; say Spec approval or Merge approval. |
| Signer workflow | `evidence.signer_workflow`: the central test workflow whose artifact attestation the gate requires on evidence. |
| Skill | A folder in the Agent Skills format (a `SKILL.md` and its references) that an agent loads by name. The `aidd` skill (`.agents/skills/aidd/`) tells any coding agent how to work in the loop; the delivery team adds domain packs and practice skills. |
| Small goal | An Epic: a piece of a big goal, two weeks or less. It lists its planned Specs (`specs`) and says how it reaches users (`reaches`). |
| Spec | `specs/<ID>.md`: what, why, scope, acceptance, tests, rollback. |
| Spec approval | A human's approval of what will be built: the Spec with its frozen test and design files, as they read at the commit the person approved. It is posted as `/aidd approve-spec <ID> <commit>`; under `spec_approval_proof: require` (audited) that commit must hold only the Spec and its frozen files. Rule `spec_approval`. *Avoid:* "sign-off", "design approval", or "the design gate". The design files are approved only as part of Spec approval, and a person approves; the gate only checks that it happened. |
| Spec hash | A 32-hex (128-bit) SHA-256 prefix over one canonical JSON document. The document holds the Spec's stable fields, its body, and the blobs of its test and design files. The gate computes it at the approved commit and at head: an approval counts while the two are the same. Nobody types or reads it. *Avoid:* "approval hash": an approval names a commit, never a hash. |
| Spec lane | The lane of normal and major changes: Specify, Spec approval, Implement ⟲ Verify, Review, Merge approval, Publish, Roll out. The Spec and its tests come first, and Spec approval freezes them. |
| Spec phase | The stretch of a spec-lane change before any Task changes anything, while every changed path is the Spec, a file it freezes, or its backfill. Its new tests are expected to fail, so `aidd test` exits 0 and the gate's `tests` rule is pending (`tests.spec_phase`), not failed. |
| Specialist Approver | A person in a pool in `owners.specialists` (security, privacy, data, or a domain expert's pool), whose approval a major change needs from the team profile up. Rule `specialist_approval`. *Avoid:* "specialist reviewer" or "specialist review": they approve. And do not confuse them with the reviewer role, an agent that writes findings and never approves. |
| Specify | The loop step that writes the Spec and its tests before any code exists. It ends at Spec approval. |
| Stack | A set of opinionated standards that go together, plus entries for `project.stack`, such as `python-cli`. It holds no rule text, and it extends at most one other stack. `aidd stack add` adopts one. |
| Standard | A rule that agents read before a step: an industry standard in the standards registry, or an opinionated standard in a `standards` entry of the config. A copy of a library standard records its id, aidd's version, and its hash. *Avoid:* confusing it with a standard change, which is a change class. |
| Standard change | A pre-approved change class (such as a bot patch bump) that merges on green tests with no human approval. |
| Skipped step | A step of the loop the person said to skip for one change ("skip the Spec"). The agent records it in its commit (`Aidd-Skipped: <step>: <their words>`), and the gate reports it without deciding on it ([METHOD.md](METHOD.md#skipped-step)). *Avoid:* turning the loop off to save a step. |
| Standing approval | A person's `approve all`: the agent records each Spec approval and Merge approval for them, citing it, until they type `stop approving`. `approve all but major` keeps major changes for the person. Only a person starts one ([METHOD.md §8](METHOD.md#standing-approval)). On GitHub, each Merge approval it gives turns on the pull request's auto-merge, and `stop approving` turns that off. *Avoid:* confusing it with a standard change, which needs no approval at all. |
| Standards registry | Every standard a role, a domain pack, or a practice skill applies, in `schemas/industry-standards.json`. Each records its source and a quoted sentence where one is published, its edition where it has one, and a `checked` or `reviewed` date. `aidd eval standards` fails on a stale date and on unconfirmed or unsourced entries ([the six checks](TEAM.md#domain-packs)). |
| Status group | One of five groups that every status falls into: backlog, unstarted, started, completed, cancelled. They are the same for Specs, Epics, Initiatives, and proposals, so a board or a tracker mirrors any object by its group ([METHOD.md §5.1](METHOD.md#51-status)). |
| Support period | `project.compliance.support_period`: the last month (`ends`, `YYYY-MM`) in which the product gets security updates. The `cra` target needs it: at least five years, unless people use the product for less time (CRA Art. 13(8)). `aidd validate` fails a `cra` config without one. |
| Support SLA | The contract's Support and service levels schedule. It sets the support tiers, channels and hours, and response and resolution targets by severity (S1 to S4). It also sets escalation, maintenance windows, exclusions, and reporting. Humans agree its targets; the delivery manager reports against them. *Avoid:* confusing it with an SLO, the system's reliability target. |
| Task | A slice of a Spec with its own `scope`. |
| Tenant | `tenant` in the config: the company, or an agency's client, that a repository belongs to. An org preset sets it and may lock it. It is stamped on every gate record, event, and change record. An approval by another tenant's identity (`<tenant>:<login>`) never counts ([Enterprise readiness §13](ENTERPRISE.md#13-multi-tenancy)). |
| Test mode | `tests.mode` in a Spec. `first` (the default): the tests are written before the code and frozen by Spec approval. `with_code`: new code with nothing to break writes its tests with the code, and Merge approval reviews them. |
| Test runner | The `aidd-tests` job: runs the tests on head (green) and base (red) and uploads the evidence. It runs the change's code, so it has no secrets. |
| Tests | The commands whose exit code proves acceptance (`tests.commands`) and the files they run through (`tests.files`). Written before Implement, frozen by the Spec hash. |
| `trace_id` | An identifier shared by every Spec, PR/MR, and event of one piece of work, across repositories. |
| Three rings | Where work is: the inner loop (this machine, private), the local trunk (this machine, private), and the outer loop (shared). Land and Publish are the two boundaries, and a person holds each ([METHOD.md](METHOD.md#three-rings)). |
| Triage | A person's decision on work that an agent suggested on its own (`suggested_by: agent:<role>`, a role in `agents.proactive_roles`). It is also the decision on an issue that `aidd import issues` brought in the same way. It is accepted, declined (the Spec is cancelled), or snoozed until a date, recorded as `triage` in the Spec. A duplicate is a relation, not a decision. Until then the Spec stays a draft; `aidd validate` fails one past draft without it, or with a triage an agent recorded. |
| Trunk-based flow | The default branch is the one trunk: few branches, each short-lived and merged often (`limits.max_branch_age_days`, `max_open_branches`, `max_goal_age_days`). `aidd list` shows each branch's age and how far it is behind. |
| Type | The kind of change, in Conventional Commits vocabulary: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `deps`, `infra`, `data`, `security`, `compliance`. |
| Unlinked author | A commit author the platform cannot map to an account (`email:`); it might be an Approver, so the gate warns or fails. |
| Usability test | The design spec's `## Usability test`, before launch. It gives goals, participants and recruiting, tasks with success criteria, the script, findings with severity and evidence, and the decisions a person makes. After launch, the feedback log. |
| User flows | The design spec's `## Flows`: the sitemap and each main journey as Mermaid diagrams, with entry, exit, and error paths, naming the screens its Screen inventory lists. Frozen with the Spec. |
| Vendor register | The repository's one `vendors` doc, `docs/vendors.md` (`aidd new vendors`). It gives each third party's service, the data shared, its DPA, its SLA, the renewal date, and the owner. `aidd validate` warns 30 days before a renewal; a processor's Art. 28 terms stay in the data map. |
| Verifier | The `verifier` role of the delivery team, the one QA role. In Specify it writes the Spec's tests, which fail on base before any code exists. In Verify, a fresh session, it runs the Spec's tests on the exact head and exercises the built change, and its report is never evidence. It never writes the code. *Avoid:* "the verifier" for `aidd gate`, the program behind `aidd/gate`, a pure function from context to pass, pending, or fail: call that the gate. |
| Verify | The loop step after Implement, run beside Review on one head: the verifier runs the Spec's tests once on the exact head, and exercises the built change against each Acceptance line. Its report starts with the head SHA it checked; a new push makes it stale, and a failure returns to Implement. |
| Vulnerability policy | The repository's one `vulnerability-policy` doc, `docs/security/vulnerability-policy.md` (`aidd new vulnerability-policy`), which the security engineer keeps. It says how to report a vulnerability (a `security.txt` with `Contact` and `Expires`), the triage, the fix times, the advisories and VEX, the weekly rescan of supported releases, and the CRA Art. 14 reporting clocks. With the `cra` target, `aidd doctor` warns on a missing or expiring `security.txt`. |
| Walking skeleton | The smallest end-to-end slice of a new system, usually the first Spec of a greenfield project: every layer wired, one happy path, a term from Alistair Cockburn. Its Task (`skeleton: true`) builds the structure, the contracts, the test runner, and CI. |
| Wireframe mode | A mode of the prototype, opened with `?mode=wireframe` (or its Fidelity bar), not a file of its own. It shows greyscale boxes with no brand color or font, for the rough design directions. The picked direction is then built at full fidelity in the same file. |
| Work item folder | The folder beside a work item's file, named by its id: `specs/SPEC-12.md` keeps everything about it in `specs/SPEC-12/`. It holds the documents the item links (`tech-spec-<topic>.md`), its design files (`design/`), and its explorations (`explore/<slug>/`). `aidd list --json` lists it, and the aidd-mods pane shows it. `docs/` holds the project's official docs instead: ADRs, the architecture overview, runbooks, the glossary. *Avoid:* a Spec's documents in `docs/`. |
| WIP limit | The cap on open changes waiting on one Approver (`limits.max_open_per_approver`; three is a good default). `limits.max_in_progress_per_owner`, when set, caps the Specs in progress that one owner holds. `aidd list` warns past either; neither is a gate rule. It limits humans, never agents, which run every Task whose scope is disjoint. |
