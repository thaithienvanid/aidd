# k6 runs the load test

It answers the load-test choice of `aidd-team:apis-and-services`. k6 is under AGPL-3.0 from Grafana Labs. `tooling/locust` suits a team that writes Python, and `tooling/gatling` a JVM team.

## What the team does

- Install k6 at `pin` in CI, such as with `grafana/setup-k6-action` pinned by commit, and keep the scripts in `load/`.
- Write each SLO as a threshold in `options.thresholds`, such as `http_req_duration: ['p(95)<200']` and `http_req_failed: ['rate<0.01']`.
- Shape the traffic with a scenario. Use an arrival-rate executor, such as `constant-arrival-rate`, so a slow service cannot lower the load it receives.
- Read the address from `__ENV.BASE_URL`, and run against a test deployment with production-shaped data, never production.
- Turn off the usage report with `--no-usage-report`, which k6 otherwise sends on each run.
- Keep a short smoke scenario for each change, and the full load for the release, each with the same thresholds.

## What the gate runs

One `load` test runs `load/main.js` at `pin`. k6 exits non-zero when any threshold fails, so a missed SLO fails the change.
