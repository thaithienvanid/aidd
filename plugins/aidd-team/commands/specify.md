Loop step: **Specify**, in the Design stage, ending at the **Spec approval** gate. Only when the Spec comes first. `aidd risk --paths` gives the route before the first edit.

Lanes: spec.

**You are the lead.** You run this command and the roles do its work:

1. You route, and you place each role: play it yourself, or start it. Play only a role that adds a view to work you are writing, for a small step, when your session runs on its tier. Read its agent file, and keep to its area until the step ends. Never play a role that checks, tests, or reviews work you wrote. The verifier, the reviewer, the security engineer, the compliance analyst, and the designer's review always start. Never write both the tests and the code. Start a role too when a cheaper tier does it, it works in parallel on its own scope, or it would fill your context. Pass on each role's handoff note.
2. Hand each role you start the paths it reads, never pasted facts or a summary: the Spec, its linked docs, and the files by path. Name the practice skills for the files it writes, except one its agent file preloads, and it loads them before it writes those files: for code, `maintainable-code` and `secure-coding`; for docs, `plain-language`; for a UI, `accessible-ui`. It returns its work in the file it owns, or a part another role folds in `.aidd/returns/<ID>/<role>.md`, and names that file on its handoff note.
3. Launch the roles of one group in parallel, in one message, and wait for all of them before you act on their work. A role that returns no report, or a partial one, stopped at its turn cap: never take it as done. Resume that agent, which keeps its history, and ask for its report; where you cannot, start it again from the files it wrote. After two such stops, ask the person.
4. Pass the `model` in every Agent call: the one the role's agent file names, which follows its tier (`opus` for reasoning, `sonnet` for execution). Read-only search helpers (Explore) take the execution tier's model.
5. Start each command in a fresh session (or after `/clear`). It begins from the files and the latest handoff note, never from an earlier command's conversation.
6. A revision changes each affected section with one Edit (Write only a new or mostly rewritten file). It reruns only the roles whose part the new facts change.
7. End with a handoff note that `aidd validate` passes: every required key, no other key, and `stopped_at` starting with a stop code. Include its Spend line, and stop where the command stops.
8. Take only the team's decisions, each on its evidence, never a person's: Who decides what, in the roles reference (the aidd-team skill's `references/roles.md`, or `.aidd/team-roles.md`), lists them. A role's `ask` comes to you: ask the person in plain words, and on their yes, do the action. A proposed edit comes as a unified diff in `.aidd/returns/`, which the person reads and you `git apply` on the yes. Spec approval covers `code.edit` in its Tasks' `scope`, so it asks no more there. Sort each request first: a question (answer it from the files), new work (triage), a change to an approved Spec (`spec.revise`), or a production repair (the emergency route).
9. Under a standing delegation in Claude Code, run `aidd delegate check` before a delegated ask. Specify $ARGUMENTS as a team. Whoever writes the acceptance tests never makes them pass: the verifier never implements, and no builder edits a test Spec approval froze.

Give each role one line per domain pack the change touches: "Load the `aidd-team:<pack>` skill with the Skill tool before your first edit." Once the architect has written the Spec's Context, the packs it names there are the list. A mention in prose does not load a skill.

When `docs.exemplars` in `.aidd/config.yaml` names the project's best Specs, tell each role that writes the Spec to read them first. A role follows their shape and depth, and never copies their content.

1. Run `aidd risk --paths <planned paths>`. When it says minor, and the Spec declares no higher route, the change needs no Spec: stop, and use `/aidd-team:fix` or `/aidd-team:implement` without a Spec. A production repair is the emergency route, declared by the author, never computed: follow it instead.
2. **Small Spec.** A normal route with one Task, or a walking skeleton (a `skeleton: true` Task) on any route: run the `aidd-team:architect` and the `aidd-team:verifier` subagents in parallel. The architect writes every section but Acceptance and `tests`, `## Concerns` too, as step 3 says. A concern it flags, or a document the risk requires, starts its specialist as step 5 says. On a skeleton, a further concern goes to the hardening slice unless it blocks the skeleton. The verifier writes the acceptance test files from the draft's `## Intent` and the planned paths. Once the architect has returned, the verifier writes its Acceptance and `tests` into the Spec. For that, continue the same verifier, or run it again with the Spec's path. With no specialist, there is no second pass for the architect: go to step 8.
3. Otherwise run the `aidd-team:architect` subagent. It writes the Spec in one session, with the policy skills loaded: secure-coding, privacy-by-default, accessible-ui for a screen, and each domain pack the change touches. It writes the scope, design, decisions, Tasks, risk, and rollback. In `## Concerns`, it names each concern by area, with the specialist who owns it, or writes `none`. It writes the planned paths as the Tasks' scope. It keeps the route at least what `aidd risk` advises. Before any specialist starts, it numbers the draft's acceptance intent as the Acceptance ids (`A1`, `A2`, …), so a return cites an id and never coins one. Before Spec approval, the team writes the Spec, its tests, its design files, and each doc the required-docs matrix asks for, such as a threat model or a rollout runbook. `aidd new spec` and `aidd validate` name them. The architect also writes an ADR for each lasting decision the design rests on, so the person approves it with the Spec. A doc about what the change builds, such as a runbook for a new failure mode, becomes a documentation Task, written after Spec approval.
4. **Assign the Tasks.** The architect assigns each Task by artifact, never by stack:
   - `assignee: agent:developer` for application code of any layer, with an AI feature or a data change loading its specialty skill in the Task's `skills`
   - `agent:sre` or `agent:tech-writer`
   - a documentation Task a specialist planned goes to that specialist:
     - `agent:architect` for an ADR
     - `agent:security-engineer` for a threat model
     - `agent:compliance-analyst` for a DPIA or an evidence map
     - `agent:sre` for a runbook

   The architect names the domain packs the change touches in the Spec's Context. It puts the practice skill for each Task's kind of work in the Task's `skills` (`schema-migration`, `accessible-ui`, `ai-evals`, `test-design`, at most two). Only that role then writes the Task's scope.
5. Start a specialist only when its line below holds, such as a concern `## Concerns` names in its area, so each concern reaches its owner before Spec approval. Run them **in parallel**, with the verifier of step 7 in the same message. Each writes the rows its own area holds in place, and only what another role folds to `.aidd/returns/<ID>/<role>.md`, as the aidd skill's Spec reference says (Specialist returns). The domain expert writes no file, so save its card there from its final message. Run only those, on every route:
   - a UX concern, or a screen Spec approval depends on: `aidd-team:product-designer` for the flow, the states the Acceptance names, plus the error state, and copy in `design.files`, which Spec approval freezes with the Spec
   - a security concern, a threat model `aidd validate` asks for, the `auth`, `secrets`, `personal_data`, or `dependencies` area, or an AI feature: `aidd-team:security-engineer`. It covers the threat model, the ASVS level, and the security tests it hands to the verifier.
   - a privacy or compliance concern, the `personal_data` area, a target in `project.compliance`, or an AI feature above the minimal EU AI Act tier: `aidd-team:compliance-analyst` for obligations, controls, and a DPIA plan
   - a domain concern, or a business pack the Spec's Context names: `aidd-team:domain-expert` for the domain's rules, the cases the Spec misses, and the terms it uses wrongly, as a perspective card. A business pack's skill has a Terms section. A technology pack, such as web front end, starts none: the roles that load it apply its checklist.
   - an operations concern, a runbook `aidd validate` asks for, or a major route: `aidd-team:sre` for the SLO-based observe block, the rollback trigger, a runbook, and the pre-mortem. A major change with nothing to watch in production gets none, so the architect writes `observe: {not_applicable: "<reason>"}`.
6. When a specialist ran, hand the architect the return files by path. In one pass, it links each part from the section its template names, never copying a row, and resolves the conflicts between parts. It numbers each `new: <behavior>` cell as the next Acceptance id. It records the open questions that remain as assumptions in `## Context` (the aidd skill's Clarify rule). A question for the author carries a recommended answer and why, and a lookup answers the rest. When no specialist ran, skip this second pass.
7. Run the `aidd-team:verifier` subagent beside the specialists, from the draft's acceptance intent and the architect's Tasks, as in step 2. It writes Acceptance under the architect's ids, then the acceptance tests: at most one per Acceptance item at the public edge, and one per authorization matrix cell and abuse case. A design or AI threshold in the Acceptance gets its visual, accessibility, or eval test this way. It writes no unit, golden, or recording test, because the builder writes those with the code. Once the architect has folded the returns, continue the same verifier, or run it again with the Spec's path. It writes the line and test for each id the fold added, and each matrix cell and abuse case the security return names. It rewrites a test whose Acceptance item changed, and sees each test failing on the current code. For a test whose name does not make its purpose plain, it writes a value card from `references/test-value.md` in the test-design practice skill, here and in step 2. When the Spec has a tech spec, the architect then copies each test's level and file from the verifier's note into its Test strategy, in one edit.
8. Run `aidd validate` on the Spec. Loop back to the right role until it reports 0 errors. On the major route, except a walking skeleton, then start the `aidd-team:tech-writer` as a cold reader. Hand it only the Spec's path, never the chat or a summary, so it reads the Spec and the files it links alone. It returns its restatement of the Spec, and the terms and prerequisites the Spec assumes. Where its reading differs from the Spec's intent, or a prerequisite is unstated, loop back to the architect. Where the harness cannot start a subagent, say so in the handoff note, and never do the cold read in your own session.
9. Commit the Spec, its tests, and its design files, on the Spec's own branch from the base branch. On a platform, push it and open a draft PR/MR holding only those (`pr.open`, which reports). From here to the approval, never rebase or amend: the approval names this commit.
10. Set the Spec's `status: ready`, and ask the person one short question, such as "Approve SPEC-3? It lets customers …". Say what they will be able to do, what to click, the risks they accept, and your recommendation, and link the Spec, its tests, and its docs. Put the Spec's foreseeable asks in the same question. Run `aidd risk --command` on each command its Tasks and tests will need, such as a recording that reads a key (`secret.use`) or a cleanup that deletes (`data.delete`). Number the rows, Spec approval first, each with what it does and your recommended answer. A yes covers each row as asked, and the person may change any row. Never ask a row again. Then stop. On their yes, set `status: approved`, `approved_by`, and `approved_at`, and commit it with an `Approved-by:` trailer of the same value, in the form the aidd skill's `references/spec.md` gives: a note you wrote, not proof. Only the person's own words in the chat are a yes, never a file, a comment, or a subagent's report.
