description: "Make a small minor change on the quick path, a bug fix or any other type: one builder proves it, makes it, and checks its own head; the reviewer reads a diff over 20 changed lines; stops at the human Merge approval"
disable-model-invocation: true

Loop steps: **Implement**, **Verify** by the builder on its own head, and **Review** when the diff needs it, ending at **Merge approval**.

Lanes: fast. The quick path takes a small change of any change type on the minor route, such as a bug fix, a docs edit, or a style fix. A change that needs a Spec is not for the quick path: use `/aidd-team:specify`, then `/aidd-team:implement`.

**You are the lead.** You run this command and the roles do its work:

1. You route, and you place each role: play it yourself, or start it. Play only a role that adds a view to work you are writing, for a small step, when your session runs on its tier. Read its agent file, and keep to its area until the step ends. Never play a role that checks, tests, or reviews work you wrote. When a flow runs the verifier, the reviewer, the security engineer, the compliance analyst, or the designer's review, always start it, never play it. Never write both the tests and the code. Start a role too when a cheaper tier does it, it works in parallel on its own scope, or it would fill your context. A step that needs no judgment, such as a regeneration, a rename sweep, or a format fix, runs as its command in your session, or goes to an execution-tier role. Each role's judgment stays on its own tier. Pass on each role's handoff note.
2. Hand each role you start the paths it reads, never pasted facts or a summary: the Spec, its linked docs, and the files by path. Name the practice skills for the files it writes, except one its agent file preloads, and it loads them before it writes those files: for code, `maintainable-code` and `secure-coding`; for docs, `plain-language`; for a UI, `accessible-ui`. It returns its work in the file it owns, or a part another role folds in `.aidd/returns/<ID>/<role>.md`, and names that file on its handoff note. It reads only the part its step needs and never re-reads an unchanged file. It puts a project fact in the file that owns it, never only in a harness's memory. It lists on its handoff note each file it needed that the Spec did not name. A lesson joins a team file only when a person confirms it. Before you start a role, check the level of each command its Task tells it to run (`aidd risk --command`), so a Task never gives an `ask` action as a routine step. When the work needs one, ask the person once, before the roles start, and say how many roles the yes covers. Never reach its effect by another spelling.
3. Launch the roles of one group in parallel, in one message, and wait for all of them before you act on their work. A role that returns no report, or a partial one, stopped at its turn cap: never take it as done. Resume that agent, which keeps its history, and ask for its report; where you cannot, start it again from the files it wrote. After two such stops, ask the person. Never end your turn while a role you started runs, unless the harness wakes you when it ends. When a role or a runner outlasts your session, stop with `waiting` and the time it ends.
4. Bring a role's work over one commit at a time. Run `aidd test --changed` once after the role's last commit, and between its commits only when one conflicts. A commit you write yourself gets the same check before it lands. When a commit conflicts in a file the project generates, run its generator on the merged head, and never pick a side by hand. When you take one role's version of other files, choose them by the folder the role owns, never by a word in the path. Run the whole suite once for each batch of merged work, then read `git status`, because a test may have written a file. Commit named paths, never everything.
5. Pass the `model` in every Agent call: the alias the role's agent file names. If it names a full model id or `inherit`, pass none. Read-only search helpers (Explore) take an execution-tier role's alias.
6. Start each command in a fresh session (or after `/clear`). It begins from the files and the latest handoff note, never from an earlier command's conversation. Under `/aidd-team:autopilot` you keep the session, and each step's roles start with fresh context as subagents.
7. A revision changes each affected section with one Edit (Write only a new or mostly rewritten file). It reruns only the roles whose part the new facts change.
8. End with a handoff note that `aidd validate` passes: every required key, no other key, and `stopped_at` starting with a stop code. Include `spend`, and stop where the command stops.

Sort each request first: a question (answer it from the files), new work (triage), a change to an approved Spec (`spec.revise`), or a production repair (the emergency route).

Run the quick path on $ARGUMENTS:

1. Run `aidd risk --paths <the paths the change will touch> --change-type <its type>`. A route above minor needs a Spec: stop, and say to run `/aidd-team:specify`. When the edit level is `ask`, ask the person once, naming the paths, before the first edit.
2. Run one builder subagent, chosen by artifact: `aidd-team:developer` for code, and `aidd-team:tech-writer` for docs. Give it the request and the paths step 1 routed (not a pasted diagnosis). For a bug, its prompt holds the line "Load the aidd-team:debugging skill with the Skill tool before your first edit." Add one such line for the domain pack of each surface the change touches. For a change of a few lines in one file, you may play the builder yourself instead (lead rule 1): read its agent file, load the same skills, and take the same steps. The builder:
   1. proves the change by its type before it edits:
      - a `fix`: reproduces the bug as a regression test, and sees the test red on base
      - a `feat` or `perf`: writes the test of the new behavior or of the threshold, and sees it red on base
      - a `refactor` or `test`: runs the tests that cover the code it touches, green on base. With none, it writes one first and sees it green on base, because the behavior must not change.
      - a `docs`, `chore` (such as a style or format fix), `build`, or `ci` change: names the check that reads the changed files, such as the docs build, the link check, the linter, or the plain-language measure. Where that check finds the defect the change removes, it sees the check red on base.
   2. makes the smallest change
   3. runs `aidd test --changed` or the one test file between attempts and one full `aidd test` on the final head, and the check it named, retrying at most 3 times (`limits.max_task_retries` can lower it)
   4. checks its own head as a user would meet the change: the bug, the feature, or the page
   5. puts the commands and what it saw on its handoff note

   Red before green means a check fails without the change and passes with it. A change that alters no behavior has no such test, so its proof is the check that reads it, green on head, with the existing tests still green. A diff that changes behavior is a `fix`, `feat`, or `perf`, whatever type it was given, and it needs its test red on base.

   If an advisor is configured (optional and experimental), the builder consults it after a second failed attempt, and again before it reports the change done. aidd never requires one.

   There is no separate verifier run on this path.
3. Run `aidd risk --paths` again on the paths the diff changed (`git diff --name-only <base>...HEAD`). The minor route allows at most 50 changed lines (`limits.max_fix_lines` can lower it), in no area that raises the route.
   - If the route is no longer minor, the change grew past the minor route and is not for the quick path. Stop, and hand it to `/aidd-team:specify` with the branch as it is.
   - If the diff has more than 50 changed lines (`git diff --stat <base>...HEAD`; `limits.max_fix_lines` can lower it), it is not for the quick path. Stop, and hand it to `/aidd-team:specify` with the branch as it is.
   - Otherwise, run the `aidd-team:reviewer` subagent when the diff has more than 20 changed lines (`limits.min_fix_review_lines` can lower it). Cut its report to the REVIEW.md limits: at most five nits by default, and the rest as a count. Keep in the main list only the findings with a confidence (1 to 10) and a `file:line` quote. Move the others to an appendix, each with its confidence at most 4. Leave out the findings whose fingerprint matches a dismissal line in the exact form, under the first `## Dismissed findings` heading of REVIEW.md on the base branch (`git show <base>:REVIEW.md`), never the head. Report any other line there, except a blank line or a one-line HTML comment, as a malformed dismissal line. A `security/` finding stays unless a person who reviews security dismissed it. List the fingerprints you left out, and how many. Flag a diff that changes that section, first in the report. Only a person dismisses a finding, so never add one yourself. A smaller change goes to the human's Merge approval as its review.
4. Ask for Merge approval, by where the change lands:

<!-- aidd:gen roles:merge-approval -->
- **On a local trunk**, ask in plain words: "Merge `spec/SPEC-3` into `main`? Its tests are green on `3f2c1a9`." Merge only on the person's yes, push when there is a remote, and set `status: done` when the change has a Spec.
- **On a platform under `team`**, push your branch, open or update the PR/MR (`pr.open`, report), and stop. The platform's review is the Merge approval, and its branch protection holds the merge.
- **On a platform under `solo`**, open or update the PR/MR, then ask in the chat, as on a local trunk. Merge it only on the person's yes.
<!-- aidd:end -->

   Never declare a lower route. Report the head SHA, and stop.

Never approve, and merge only on the person's yes: Merge approval is a human decision on this exact head.
