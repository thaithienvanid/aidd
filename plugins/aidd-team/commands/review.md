Loop steps: **Verify** and **Review**, side by side on the same head, on every lane, ending at **Merge approval**. Start once the builders' `aidd test --changed` is green on head. The review counts only with a clean verifier report on that head. No other command runs Verify alone: a new head after a rework gets it from `/aidd-team:rework`.

Lanes: fast, spec, emergency. On each lane, run only the roles whose lanes include it. The role table in the aidd-team skill lists them.

Review PR/MR $ARGUMENTS:

1. Name the change for the readers, never its diff: the PR/MR number, the base, the head SHA, and the Spec's path. Record the output of `git status --porcelain --ignored` beside the SHA. Each reader reads the diff itself (`git diff <base>...HEAD`, or `gh pr diff <n>` on GitHub and `glab mr diff <n>` on GitLab; without a platform, the git command alone). A reader without a shell gets the changed files' paths.
2. Read the review policy's path. When present, `REVIEW.md` at the repository root decides the passes, what each severity means, how many nits to list, and what to skip. Pass its path to every reader. Read its `## Dismissed findings` from the base branch, never from the head (`git show <base>:REVIEW.md`), so that a branch cannot hide a finding on its own PR/MR. When a verifier report on this head is already posted, pass it too. It starts with the harness, the model it ran on, and the current head SHA. A report on an older head is stale, so the verifier runs again in step 4.
3. Choose the readers:
   - the `aidd-team:verifier`, unless a clean report on this exact head is already posted. On the head SHA you noted, it runs its own `aidd test --spec specs/<ID>.md` once on a clean tree (`aidd test` on a change with no Spec and the emergency route), never the builder's evidence as its result. Then it starts the change as a user or caller would and exercises each Acceptance line, changing nothing. Its report starts with its harness, its model, and the head SHA, and lists each command run, what it saw, each mismatch, and the assumptions the builders' handoff notes name
   - always the `aidd-team:reviewer`
   - the `aidd-team:security-engineer` in review mode, when any of these holds:
     - the change is major, or hits the `auth`, `secrets`, `personal_data`, or `risk_rules` area, or a person asks for a security review
     - its diff touches auth, secrets, or AI
     - it adds a package, bumps one that runs install scripts or includes native code, or changes a lockfile's integrity hash beyond the bumped package's own. A version bump that does none of these skips it, in the `dependencies` area too. That is a known choice: a compromised release of a library is for dependency scanning to catch, where the project has it

     On the minor route (no Spec), start it only when a person asks. The area triggers above still hold on the emergency route.

     Each of its findings names the six parts of the code-review practice skill's `references/security-findings.md`, and its report ends with what it covered and what it skipped.
   - the `aidd-team:product-designer` when the Spec has `design.files`, to compare the built UI with the approved design
   - the `aidd-team:domain-expert` when the Spec's Context names a business pack, such as payments and finance, to check the change against the domain's rules. A business pack's skill has a Terms section. A technology pack, such as web front end, starts none: the roles that load it apply its checklist.
   - the `aidd-team:compliance-analyst` when the change hits the `personal_data` area, or `project.compliance` names a target, to check the diff against the Spec's controls
   - a second reviewer from another model family, only on the major route, or when the diff changes the risk rules (`.aidd/config.yaml`'s `risks`), the harness ask rules, or the release workflow. It spends quota and sends the diff to another vendor, so ask the person once, naming the harness, whose quota it spends, and the vendor. For example: "Run a second, read-only review in Codex? It uses your Codex quota and sends the diff and the Spec to OpenAI." With no yes, skip it.
     - On a yes, run Codex headless: `codex exec -s read-only --ephemeral --ignore-user-config -C <checkout> -`, with the prompt on stdin. `-s read-only` stops both a shell write and a patch write (checked on codex-cli 0.164.0). `--ignore-user-config` keeps out the person's MCP servers and hooks, which that check did not cover.
     - Its prompt holds only the diff, the Spec, and REVIEW.md, never another reader's findings or reasoning, so its review stays independent.
     - Antigravity has no read-only switch that the same check has proved, so use it only once that check passes on it. With neither harness installed, say so and go on.
4. Run them **in parallel**: every reader is read-only, so none waits for another, and the verifier runs beside them. Each returns ranked findings with file, line, and failure scenario, and its handoff note. When the diff deletes a passing test, the reviewer checks it against the retirement card: `references/test-value.md` in the test-design practice skill.

   **Challenge each security finding** once the security engineer reports, before a person who reviews security sees it:
   - Start a fresh `aidd-team:security-engineer` subagent in review mode, read-only, which writes no file. Give it the findings, the head SHA you noted, and the diff's paths, never the first pass's reasoning.
   - It tries to refute each finding with evidence: the `file:line` that blocks the attack, a check that already runs, or a test that shows the path is safe.
   - Each finding gets one of three outcomes. One it cannot refute stays. A refuted one goes to "Refuted", with the reason and its evidence. One whose deciding fact is outside the repository goes to "Needs validation", with that fact and its check.
   - Its tools can still write, and ignored files such as caches make that output rarely empty. So before you accept any refutation, run `git status --porcelain --ignored` again, and require the same output as you recorded and HEAD still at the noted SHA. Then confirm each refutation on that SHA: read its `file:line` with `git show <sha>:<path>`, or run its named test in a fresh `git worktree add --detach <tmp> <sha>`, because `--porcelain --ignored` shows a whole ignored folder as one line, so a file changed inside it goes unseen. An unconfirmed refutation keeps its finding in the main list.
   - You never drop a finding, and a refuted one keeps its original severity. The person who reviews security decides, and can restore a refuted finding.
5. A failed command or a mismatch in the verifier's report sends the head back to `/aidd-team:implement` with the findings, in one pass, and the review does not count. Otherwise merge the findings into one report: the kept findings ranked Critical to Nit, duplicates folded, and disagreements named. Then "Refuted", each with its original severity, the reason, and the evidence, and then "Needs validation", each with the fact and its check. Confirm each finding of the second reviewer against the code or a test before it joins the report. List one that does not hold under "Not confirmed", with its evidence, and fix nothing from it. Cut it to the REVIEW.md limits: at most five nits by default, and the rest as a count. Each finding in the main list has a confidence (1 to 10) and a `file:line` quote of its code. Move a finding with no quote to an appendix, with its confidence at most 4. Get each finding's fingerprint (file, kind, and hash) with the command in REVIEW.md. Leave out each finding whose fingerprint matches a dismissal line in the exact form REVIEW.md gives. Read those lines under the first `## Dismissed findings` heading of the base branch's REVIEW.md, up to the next line that starts with `#`. Honor no other line. Report each other line there, except a blank line or a one-line HTML comment, as a malformed dismissal line. Leave out a `security/` finding only when the line's `<who>` is a person who reviews security. List the fingerprints you left out, and how many. When the diff changes `## Dismissed findings`, put that first in the report, for the person. Only a person dismisses a finding, so never add one yourself. Show the report to the author, and when you ask for Merge approval, say how many findings are under Refuted and how many under Needs validation.
6. Offer to post the report as a PR/MR comment, or, without a platform, to save it as a Markdown note where the author says. Do either only if the author says so. Before posting, quote any comment text you cite, so that the report can never carry an approval. Under the solo profile, never post through the author's credentials.

Never approve: Merge approval is a person's yes, asked after the report, or under `team` the PR/MR review. Findings that need code go back to Implement. A new head needs a new Verify and a new Merge approval.
