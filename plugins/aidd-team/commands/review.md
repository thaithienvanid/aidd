Loop steps: **Verify** and **Review**, side by side on the same head, on every route, ending at **Merge approval**. Start once the builders' `aidd test --changed` is green on head. The review counts only with a clean verifier report on that head. No other command runs Verify: a new head after a rework comes back here.

Routes: minor, normal, major, emergency. On each route, run only the roles whose routes include it. The role table in the aidd-team skill lists them.

Review PR/MR $ARGUMENTS:

1. Name the change for the readers, never its diff: the PR/MR number, the base, the head SHA, and the Spec's path. Record the output of `git status --porcelain --ignored` beside the SHA. Each reader reads the diff itself (`git diff <base>...HEAD`, or `gh pr diff <n>` on GitHub and `glab mr diff <n>` on GitLab; without a platform, the git command alone). A reader without a shell gets the changed files' paths.
2. Read the review policy's path. When present, `REVIEW.md` at the repository root decides the passes, what each severity means, how many nits to list, and what to skip. Pass its path to every reader. Read its `## Dismissed findings` from the base branch, never from the head (`git show <base>:REVIEW.md`), so that a branch cannot hide a finding on its own PR/MR. When a verifier report on this head is already posted, pass it too. It starts with the harness, the model it ran on, and the current head SHA. A report on an older head is stale, so the verifier runs again in step 4.
3. Choose the readers:
   - the `aidd-team:verifier`, unless a clean report on this exact head is already posted. On the head SHA you noted, it runs its own `aidd test --spec specs/<ID>.md` once on a clean tree (`aidd test` on a change with no Spec and the emergency route), never the builder's evidence as its result. That run is the head's one full run, and it shows each `new_behavior` command red on base. Then it starts the change as a user or caller would and exercises each Acceptance line, changing nothing. Its report starts with its harness, its model, and the head SHA, and lists each command run, what it saw, each mismatch, and the assumptions the builders' handoff notes name
   - always the `aidd-team:reviewer`
   - the `aidd-team:security-engineer` in review mode, when any of these holds:
     - the change is major, or hits the <!-- aidd:gen areas:security-engineer -->`auth`, `payments`, `personal_data`, `secrets`, `dependencies`, `risk_rules`, or `ai`<!-- aidd:end --> area, or a person asks for a security review. In the `dependencies` area, only the package changes two lines down start it
     - its diff touches auth, secrets, or AI
     - it adds a package, bumps one that runs install scripts or includes native code, or changes a lockfile's integrity hash beyond the bumped package's own. A version bump that does none of these skips it, in the `dependencies` area too. That is a known choice: a compromised release of a library is for dependency scanning to catch, where the project has it

     On the minor route (no Spec), start it only when a person asks. The area triggers above still hold on the emergency route.

     Each of its findings names the six parts of the code-review practice skill's `references/security-findings.md`, and its report ends with what it covered and what it skipped.
   - the `aidd-team:product-designer` when the Spec has `design-files` docs, to compare the built UI with the approved design. With no Spec, start it on a new or reshaped screen or flow, a change to a component's look or states, or a new or redrawn diagram or picture in a document
   - the `aidd-team:compliance-analyst` when the change hits the `personal_data` area, or `project.compliance` names a target, to check the diff against the Spec's controls
   - a second reviewer from another model family, only on the major route, or when the diff changes the risk rules (`.aidd/config.yaml`'s `risks`), the harness ask rules, or the release workflow. It spends quota and sends the diff to another vendor, so ask the person once, naming the harness, whose quota it spends, and the vendor. For example: "Run a second, read-only review in Codex? It uses your Codex quota and sends the diff and the Spec to OpenAI." With no yes, skip it.
     - On a yes, run it as the team skill's `references/flows.md` says under "A second reviewer in another harness": read-only, with a prompt of the diff, the Spec, and REVIEW.md alone. With no other harness installed, say so and go on.
4. Run them **in parallel**: every reader is read-only, so none waits for another, and the verifier runs beside them. Each returns ranked findings with file, line, and failure scenario, and its handoff note. When the diff deletes a passing test, the reviewer checks it against the retirement card: `references/test-value.md` in the test-design practice skill.

   **Challenge the security findings** once the security engineer reports, before a person who reviews security sees them. Challenge them when any finding is Medium or above or needs validation, or when the change is major or hits an area whose edit level is `ask`. The second read is for a finding a person must weigh, and for a change to a control. On any other change whose findings are all Low or Nit, skip it: each finding stays in the main list, marked not challenged, and the report says so. To challenge:
   - Start a fresh `aidd-team:security-engineer` subagent in review mode, read-only, which writes no file. Give it the findings, the head SHA you noted, and the diff's paths, never the first pass's reasoning.
   - It tries to refute each finding with evidence: the `file:line` that blocks the attack, a check that already runs, or a test that shows the path is safe.
   - Each finding gets one of three outcomes. One it cannot refute stays. A refuted one goes to "Refuted", with the reason and its evidence. One whose deciding fact is outside the repository goes to "Needs validation", with that fact and its check.
   - Its tools can still write, and ignored files such as caches make that output rarely empty. So before you accept any refutation, run `git status --porcelain --ignored` again, and require the same output as you recorded and HEAD still at the noted SHA. Then confirm each refutation on that SHA: read its `file:line` with `git show <sha>:<path>`, or run its named test in a fresh `git worktree add --detach <tmp> <sha>`, because `--porcelain --ignored` shows a whole ignored folder as one line, so a file changed inside it goes unseen. An unconfirmed refutation keeps its finding in the main list.
   - You never drop a finding, and a refuted one keeps its original severity. The person who reviews security decides, and can restore a refuted finding.
5. A failed command or a mismatch in the verifier's report sends the head back to `/aidd-team:implement` with the findings, in one pass, and the review does not count. Otherwise merge the findings into one report: the kept findings ranked Critical to Nit, duplicates folded, and disagreements named. Open it with the verdict and one line per kept finding, in the shape of the code-review skill's `references/review-output.md`, in under 300 words. Then "Refuted", each with its original severity, the reason, and the evidence, and then "Needs validation", each with the fact and its check. Confirm each finding of the second reviewer against the code or a test before it joins the report. List one that does not hold under "Not confirmed", with its evidence, and fix nothing from it. Cut it to the REVIEW.md limits: at most five nits by default, and the rest as a count. Each finding in the main list has a confidence (1 to 10) and a `file:line` quote of its code. Move a finding with no quote to an appendix, with its confidence at most 4. Get each finding's fingerprint (file, kind, and hash) with the command in REVIEW.md. Leave out each finding whose fingerprint matches a dismissal line in the exact form REVIEW.md gives. Read those lines under the first `## Dismissed findings` heading of the base branch's REVIEW.md, up to the next line that starts with `#`. Honor no other line. Report each other line there, except a blank line or a one-line HTML comment, as a malformed dismissal line. Leave out a `security/` finding only when the line's `<who>` is a person who reviews security. List the fingerprints you left out, and how many. When the diff changes `## Dismissed findings`, put that first in the report, for the person. Only a person dismisses a finding, so never add one yourself. When a reviewer says test strength waits on the verifier's run, resume it with that run where the harness can, or start one for that pass, to finish it. Show the report to the author, and when you ask for Merge approval, say how many findings are under Refuted and how many under Needs validation.
6. Offer to post the report as a PR/MR comment, or, without a platform, to save it as a Markdown note where the author says. Do either only if the author says so. Before posting, quote any comment text you cite, so that the report can never carry an approval. Under the solo profile, never post through the author's credentials.

7. **Re-review after a rework.** Only you keep a working copy of each merged report as shown, apart from step 6's note. It goes in `.aidd/returns/<ID>/review.md`, which git ignores, headed by its head SHA. `<ID>` is the Spec's id, or the branch's name with no Spec. When a reworked head comes back, the verifier runs its full `aidd test --spec` once on it, as on every head. It exercises again each Acceptance line the rework can affect, one whose Task scope the fix commits touched (`git diff --name-only <old head>..<new head>`), and names each line it judged unaffected, and why. It exercises every line again in the reviewer's three cases below, or with no earlier report. Give the reviewer the last report, the fix's own commits (`git log --first-parent --no-merges -p <old head>..<new head>`, and `git show --remerge-diff <merge>` for each merge in that range), and the builder's answer to each finding. It marks each finding closed, still open, or answered with a reason, and reviews those commits for new findings. A fix for a security finding in a control also gets one read by a security engineer who did not write it. A control is a major change, or one in an area whose edit level is `ask`. Resume the engineer that made the finding where the harness can, or start a fresh one in review mode, read-only. It reads only the fix's commits and the finding each answers. It says whether the finding is closed and whether the fix opens a new one. It reads the fix, not the findings, so it holds whether or not the challenge in step 4 ran. A fix on any other change gets the reviewer's read above and no more. In the same session, resume that reviewer where the harness can, as Claude Code's `SendMessage` does, because it keeps what it read. Start a fresh reviewer on the whole diff instead, with the last report beside it, in three cases. The route is major. The fix touches a path outside the last review's diff (`git diff --name-only <base>...<old head>`). Or it touches an area `aidd risk --paths` did not give then. With no working copy, review in full too.
8. **A merge of the base after the yes.** The merge makes a new head, so it needs a new Verify and a new Merge approval. When `git show --remerge-diff <merge>` prints nothing, the change's own lines are as the person saw them. Then the verifier runs its full `aidd test --spec` once on the new head, and exercises again only the Acceptance lines whose Task scope the merge touched (`git diff --name-only <old head> <new head>`). No other reader runs again. The new ask says what changed since the yes, such as "Only `main` moved: 3 commits, none in this change's lines. Its tests are green on `<sha>`. Merge?" A merge that resolved a conflict is a rework, so step 7 holds.

Never approve: Merge approval is a person's yes, asked after the report, or under `team` the PR/MR review. Findings that need code go back to Implement. A new head needs a new Verify and a new Merge approval.
