# aidd-team

An optional Claude Code plugin that runs the [aidd](https://github.com/thaithienvanid/aidd#readme) loop as a development team. <!-- aidd:gen count:roles -->12<!-- aidd:end --> agent roles, each with a standard industry name, apply their discipline's standards and write only their own files. It needs the core `aidd` plugin (the skill and the MCP server).

```text
/plugin marketplace add thaithienvanid/aidd
/plugin install aidd@aidd
/plugin install aidd-team@aidd
/plugin install aidd-packs@aidd   # the domain packs, in a project that calls for one (optional)
```

Humans keep every decision: who approves a Spec and a change, who reviews high-risk work, who runs an incident, and who directs the team.

<!-- aidd:gen roles:commands -->
- **Commands:** `/aidd-team:plan`, `/aidd-team:mvp`, `/aidd-team:propose`, `/aidd-team:onboard`, `/aidd-team:specify`, `/aidd-team:implement`, `/aidd-team:review`, `/aidd-team:fix`, `/aidd-team:rollout`, `/aidd-team:handover`, `/aidd-team:postmortem`, `/aidd-team:retro`; one per flow in the registry, each running its roles in order and stopping where a person decides. `/aidd-team:autopilot` runs those flows one after another, picking each step from `aidd status`, and stops at each ask.
<!-- aidd:end -->
- **Risk rules, not a control:** before an action, each role checks its risk rule (`aidd risk`, or the MCP `risk` tool). On `ask`, it stops, and the lead asks the person and acts on their yes. No role approves or merges. The roles follow their instructions, and no hook checks their writes. The hard stops come from the harness's own ask rules, which `aidd init` writes, and from the platform's branch protection.
- **Know-how:** each role carries its discipline's standards. It loads a pack for every domain the change touches, by the name that `aidd risk --paths`, the config, or the lead gives. The packs are the optional `aidd-packs` plugin, because no setting keeps a skill both loadable by a model and out of Claude Code's skill listing. It also loads a playbook for the kind of work in a Task (up to two, named in its `skills`). Everything carries a checked date. `aidd eval standards` fails on a standard nobody re-checked within its review cadence: 90 days for an emerging one, a year otherwise ([docs/TEAM.md](https://github.com/thaithienvanid/aidd/blob/main/docs/TEAM.md)).
- **Extensions:** each role names the skills, plugins, and MCP servers that extend it. Any other one is added the same way, verified and pinned, through a change.
- **Without the plugin:** `aidd init --aidd-team` installs the roles, practice skills, and commands as Claude Code project files, with the domain packs the repository calls for (`agents.domain_packs` adds another). Each file is named `aidd-<name>` (`.claude/agents/aidd-developer.md`, `/aidd-implement`), so none collides with a built-in agent or your own. `aidd init --aidd-team` also installs the roles reference that each role file points to for its standards (`.aidd/team-roles.md`). For Codex, GitHub Copilot, Google Antigravity, Grok Build, OpenCode, and Kiro, it also writes each role as that agent's own agent file. `AGENTS.md` gets a short section that points at those files.
- **Model tiers:** each role carries a harness-neutral `tier` that follows the cost of its mistakes. Its agent file gives the reason.
  - `execution` is the default, on a mid-size model, because the tests, the review, or a human catch the role's mistakes. The verifier is in it too.
  - `reasoning`, the strongest model, is only for the roles whose judgment no test checks, such as the architect and the reviewer.

  There are no other tiers. A role moves between tiers only on eval evidence. The Claude Code plugin derives `model:` from the tier (`team_registry.tier_model`, a model alias). For a copied team, `agents.models` can set `inherit` (the session's model) or any model by name, per tier or per role. On any other harness, read the tier and pick your own model.

Roles are defined once, in `schemas/roles.json`; the tables here and each agent's role block are generated from it.
