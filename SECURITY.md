# Security policy

## Report a vulnerability

Use GitHub's private vulnerability reporting on this repository. Open "Security" → "Report a vulnerability", or go straight to <https://github.com/thaithienvanid/aidd/security/advisories/new>. Do not open a public issue. Expect an acknowledgement within 3 business days, and a fix or mitigation plan within 30 days.

If that form is not open to you, contact the maintainer through a contact option on their GitHub profile, <https://github.com/thaithienvanid>, and ask only for a private channel. Share the details once you have one. The same times apply from that first contact.

## In scope

- Any way for a change to reach a protected branch while `aidd/gate` should have failed or stayed pending. That includes forged evidence, approval replay, separation-of-duties bypass, protected-path evasion, config tampering, and trusting PR-controlled code in the gate job.
- Glob, schema, or YAML parsing bugs that change a decision.
- Leaks of tokens or secrets through gate output, events, or artifacts.
- Template workflows that grant more permissions than their job needs.

## Trust model

[METHOD.md §14](docs/METHOD.md#14-platform-bindings-and-trust) owns the full model; this is a summary. Known limits are in [RATIONALE.md](docs/RATIONALE.md#known-limits-in-100).

- **The gate job is trusted.** It runs from the default branch and reads the PR/MR head as git objects only. It runs Policy from the base branch without tokens, and never executes the change's code.
- **The status source must be pinned** to a dedicated GitHub App. Without it, anyone with write access can post `aidd/gate`, and the gate is advisory. It is also advisory without `mode: enforce` or a rule that requires the check, which a private repository on GitHub Free cannot have. [What holds without them](docs/PLATFORMS.md#what-holds-without-the-full-setup) lists the rest.
- **The gate runs aidd from the reusable workflow's own commit**, with no package build, and keeps the App key only in the `aidd-gate` environment.
- **The test job is untrusted.** The platform token is present in the job and stripped from every test command. aidd rejects stale, missing, substituted, self-reported, and cross-PR evidence. But it can't make hostile test code honest, because a malicious change to tests, build scripts, or dependencies can make its own tests lie. The Spec approval and Merge approval human reviews are the control for that.
- **The config is read from the base branch**, and changing it is a protected, major change.
- **The guard trusts the repository's Claude Code settings.** A repository's committed Claude Code settings can set environment variables and add their own hooks. So they can weaken the guard. The guard runs git from a fixed system path and passes it only a short list of variables, such as `HOME` and `LANG`. So a `PATH`, `GIT_*`, or `LD_PRELOAD` setting does not reach that git. It also turns off `core.fsmonitor`, git hooks, and the filter, diff, and merge driver programs in the repository's own git config. Your global and system git config still apply. The plugin's launchers do not use `[`, which an exported function can replace. These defend against what reaches the session through the repository's committed content and the ordinary commands an agent runs. They do not defend against a local writer that changes `.git/config`, `HOME`, or the git programs. They also do not defend against code that an agent runs through the shell, which it can already do. For both, `aidd/gate` in CI, on a clean checkout, is the control. Trust those settings as you trust the repository's code, since `aidd/gate` still decides on the diff.
- **Advisory mode keeps the always-on rules.** In the solo and team profiles the guard advises by default. So an edit outside the Spec's scope, on a protected path, or with no Spec goes through with a note. In every mode it still denies an agent's approval, land, merge, or publish for a person, and a change to their decision records. It also denies a looser config, a looser `agents.delegate`, a change to the guard's own wiring, and a rewrite of the default branch. The gate's report on the real diff, and the review, are the control for the rest. `mode: enforce` blocks it all.
- **A guard that cannot run fails one way in every agent.** When aidd itself cannot start, or fails inside a check, the guard blocks under the `audited` profile, `mode: enforce`, or an organization's `AIDD_HOOK_FAIL_CLOSED=1`. Otherwise it says why on stderr and gives no opinion, so the agent's own settings decide, and Antigravity asks you. The gate still decides what merges. Claude Code, Codex, Grok Build, Google Antigravity, and OpenCode read this one rule from the config's own `profile` and `mode` lines, so a config aidd cannot load still decides it. The org profile enforces by default, but a guard that cannot run blocks there only with `mode: enforce` written in the config.
- **Typed decisions trust the prompt.** aidd's prompt hook records `approve SPEC-1`, `land it`, `publish`, or `approve all` from the prompt, in every harness aidd wires. It cannot tell the person's keyboard from a message another session sends to this one. So the guard denies each way it can read, which covers another agent started with a decision as its prompt, keystrokes into a terminal, and an orchestrator's message. A script that starts an agent, or a call to a local agent server whose URL or body the command doesn't show, is out of its reach. On your own machine, aidd records your decisions; it does not prove them against an agent set on forging one. For proof, use a person's review on the platform, or signed approvals with `gates.local_approvals: signed` and a key that asks for your touch.
- **A browser is outside the guard.** Browser automation, such as Orca's browser commands, can act on a platform's own web page, where only signed approvals, branch protection, and the gate hold.
- **The guard reads only the writes it knows.** A harness tool it does not know, such as Grok's image generator or OpenCode's Code Mode, is denied in a repository that uses aidd, and wherever it names a path inside one. It judges each write in the repository that holds the target, whatever the session's folder. It reads a path as the kernel does, following each symbolic link before the `..` after it. It puts a path into its case on disk, and treats a hard link's source as written. It follows a symbolic link into the git directory, also one the same line makes with `ln -s` or `cp -s`. It denies a write to a file with more than one hard link wherever it holds the writer. A test runs each case under real bash and checks that the guard denies exactly the writes bash makes. For a writer it holds, such as a role, a helper, or the lead under `delegate`, it denies a command that runs code it cannot read:
  - a command substitution or backticks where a command starts;
  - a shell fed by stdin, such as a here-string, a here-document, an input file, or a pipe like `... | bash`;
  - code bash runs later or from elsewhere, such as `trap` with a command, and `source` or `.` of a file;
  - a program that runs commands, such as `xargs`, `parallel`, `find -exec`, `-execdir`, `-ok`, or `-okdir`, `fd -x` or `-X`, and their kin, such as `gxargs`, `sem`, `rush`, `xe`, `gfind`, and `bfs`. The exception is `xargs` or `find -exec|-execdir` that runs only a reader named plainly with plain words: `wc`, `grep`, `head`, `tail`, `cat`, `basename`, `dirname`, `ls`, or `stat`. It may also be `sort` or `file` after a `--` that keeps the input's words from being options. An unquoted glob in a find pattern, such as `-name *`, voids the exception, because the shell may expand it into an action, such as a file named `-delete`. A quoted pattern, such as `-name '*.py'`, is find's own, so it keeps the exception.

  It also denies a write target with a brace expansion, such as `src/{a,b}.py`. It reads the decision records' ref, `refs/aidd/decisions`, as bash passes it to git, quoting joined and slashes run together, in any case. It denies a command that writes any other ref under `refs/aidd/` by name, too, because only aidd writes there. It denies a git command that writes a ref only the shell names, such as `$R` or a brace. It denies a git command that feeds refs on stdin with `--stdin` or `fast-import`, or rewrites every ref. It also denies one whose refspec writes under `refs/aidd/`, or a wildcard outside `refs/heads/`, `refs/remotes/`, and `refs/tags/`. That refspec may be on the command line, or set for the run with `-c`, `--config-env`, or `GIT_CONFIG_*`. It may also be stored in a remote's config, a mirror remote among them, which the guard reads before each fetch, pull, or push.

  The guard reads a shell's reserved words, such as `if`, `then`, `do`, `{`, `!`, and `coproc`, the way it reads a wrapper. A program that only the shell or the input of `xargs` or `find` names is denied for every session. That covers `$X`, `$(...)`, a glob, or `xargs -I C C`, even when the line sets the variable, as in `X=gh; $X pr merge`. So is `xargs` that hands its input to `env`, `nice`, `sudo`, `xargs`, or a shell. It reads what each program that runs commands runs as the agent's own, with each word it fills in as one only the shell names. That includes `busybox` and `toybox` applets, `script -c`, `watch`, and `flock`. In any other command, except a search or an `echo`, a word that names `git`, `gh`, `glab`, `aidd`, `tmux`, or `orca` starts a command it reads too, as in `ssh host gh pr merge`. A word only the shell or the input fills in counts as any option, and may split into an option and a name. So it may be `--approve` for `gh pr review`, `--confirmed` for `aidd`, or `-f main` for `git branch`. The guard keeps each word's quoting from the line's own text, never from a here-document, a substitution, or a child shell. So a quoted word is one word: a quoted text, such as `-b 'why?'`, or a quoted expansion right after an option that takes it, such as `--body "$MSG"`, is that option's value. A quoted expansion anywhere else may still start with `-`, so it counts as any option. A `for` loop over at most 16 literal words runs as its body once for each word, with the word in place of each quoted `"$f"`. That holds only when nothing on the line can change the loop's variable: no assignment to it, no `read`, `declare`, `printf -v`, `eval`, `trap`, function, group, or other loop, and no expansion but the loop's own. Any other loop's variable stays a word only the shell fills in. A line that runs `gh` or `glab` sets no variable and binds none in a loop, except `GH_PAGER=cat`, `PAGER=cat`, `GLAB_PAGER=cat`, `NO_COLOR=1`, `GH_PROMPT_DISABLED=1`, and a plain `GH_REPO` or `GH_HOST`, since gh and the git it runs read programs from many variables. A `gh` or `glab` verb under `alias`, `extension`, or `config` passes only when it reads, such as `list` or `get`.

  For every session, it reads a line as bash joins it. A backslash before a newline joins two lines, and a `#` starts a comment only where it starts a word. It reads the command in each substitution, in backticks anywhere or in `$(...)` inside double quotes, as one run in a folder it does not know. It reads what a shell with no script runs from a here-string or from the text `echo` or `printf` pipes into it, what `trap` runs later, and the words `env -S` splits. It denies `source` or `.` of a process substitution or of stdin, as in `. <(...)`. Text `echo` pipes with any backslash in it is text it cannot follow, since bash's `echo` keeps the backslash for the shell to read. A `-a` in a `gh pr review` cluster, such as `-ab LGTM`, counts as `--approve`, and so does an option after a `--` that `-b` takes as its value. A line's text that names an approval, such as the approval command or the decision records' ref, is denied unless it only describes or documents. Text lands as a document when `echo`, `printf`, `cat`, or `tee` puts it into a plain path inside the repository and outside its git directory, as the Write tool would. Text that a pipe, a terminal, an interpreter, or a program that posts or records could reach still counts.

  It reads a branch name in any case, since a case-insensitive disk finds `MAIN` as `main`. A branch name with a glob or a brace counts as any branch, and so does a `git branch` word a glob starts, unless the command lists. On the base branch it denies each git command that moves it, a `filter-branch` or `filter-repo` that rewrites it among them. It denies `git replace` and any write under `refs/replace/`. aidd reads every git object with replace refs off, so no replace ref stands in for an approval. It denies a git config key that names a program git runs, also when a person runs git. That covers hooks, the file monitor, the pager and editors, ssh, credential helpers, diff and merge drivers, filters, aliases, and the transports and URL rewrites a remote may use. It reads `git config`, `cp`, and `env` options by any prefix their programs take.

  For every session, it reads find's own writes, which are `-delete`, `-fprint`, `-fprintf`, and `-fls`, and what `xargs`, `find`, or their kin have a writer write. A file that only their input names may be any file, so it may be the config. The exception is find with one `-name` test of a plain name before its action, which bounds what it finds. That name must be no protected file and no name in the git directory. So `find . -name cache.db -delete` runs in the main session, and `git ls-files | xargs sed -i ...` is denied, so name the files instead. A shell write into the git directory, such as `.git/refs/...`, `.git/HEAD`, a hook, or the config, is denied for every writer in a repository that adopted aidd. The guard reads its target after the line's own plain assignments, like `D=.git/refs`, and each `cd`, and as written, since `read` or `printf -v` may change a value. After a `cd` to a folder only the shell names, it reads a write as one under any folder, so `config.yaml` there may be the config. A `<>` redirect writes too. A target the shell builds counts as the git directory's when its plain parts may name one, as `"$(...)/HEAD"` or `$D/refs/...` do. `tests/test_guard_ref_oracle.py` runs such commands with real git and fails on any that moves a ref the guard allowed. These are its known limits, and `aidd/gate` in CI decides on the diff:
  - a program that writes by itself, such as a Python script, an interpreter run as `python -c`, a build tool, or a package manager. That includes a program the agent wrote and runs under git's or gh's name, through `PATH`, `hash -p`, or an `export` that a persistent shell keeps. A program the agent runs can still change the always-on rules' files and refs on this machine. aidd shows each change with the person's next decision, and never blocks it: the decision takes it in, and lists it with how to put it back. A looser config, a rewritten history of the decision records, or a signed record aidd can't verify waits for a dialog bound to exactly what it showed, or the person's own terminal. Until then the guard keeps the stricter rules. aidd verifies a record against the signers the last decision kept, never the live ones. An unsigned local approval is no proof against a local writer, so a record added without signing counts as ordinary, and signed approvals are the control. A change that could stop the guard itself waits for aidd's own MCP dialog or the person's terminal. Such a change is a git hook, a git config key that names a program, the guard's wiring, or the launcher. A dialog in aidd-mods or OpenCode counts only because the guard denies an agent's `--confirmed`, so it never takes such a change in. The decision's words that aidd keeps are read back only as words it parses as a decision. An agent's `aidd land`, `aidd approve`, or `aidd publish` after a change stops until the person says their words again. The gate in CI, on a clean checkout, and signed approvals are the controls;
  - for the main session, a script a shell runs from a file or a download, as in `bash x.sh` or `curl ... | sh`;
  - a command another machine or program runs from one quoted word, such as `ssh host 'gh pr merge 3'`;
  - a writer outside the documented list, such as `rsync` or `curl -o`;
  - a command that the guard's parser reads differently from bash;
  - an alias the shell expands, such as one a script defines after `shopt -s expand_aliases`, or a `gh` alias set outside the line;
  - a write to git's global config file, such as `~/.gitconfig`, which may set a program git runs for every repository;
  - `git -c core.hooksPath=...` or another program key for one run, which runs that program only as the agent itself;
  - an MCP server whose tools the hook matcher never sends, or whose tools name a path under a key the guard does not read;
  - a hard link to a repository file, written from a session whose folder is outside every repository;
  - a local writer of `.git/`, such as one that moves the autopilot lease away or edits the files next to it;
  - a shell write whose target the shell builds from pieces the line does not set plainly;
  - a request to a local agent server whose URL or body the command doesn't show, because shell variables, a config file the client reads by itself, or the environment builds it;
  - on Google Antigravity, a typed decision is read from the conversation's transcript, since its hook event carries no prompt. The guard denies an agent's writes there, but a program the agent starts could still write it;
  - on Codex and Antigravity, a role's write area, because their tool events name no subagent, so the guard judges a role's writes as the session's.

  The guard fails closed where its reader cannot be exact, so it also denies some commands that write nothing protected. Each has a plain form the guard reads:
  - a loop the guard does not write out, such as one whose variable is unquoted or set again, or one in a group, is denied when its body writes through the variable. Quote the variable, as in `for f in a b; do git checkout --ours -- "$f"; done`, or run the commands one by one;
  - a program a variable names is denied, even `G=git; $G status`, because several checks read the program each in their own way, so none resolves it. Name the program;
  - for a role, `find -delete` with a quoted glob is denied, because which files it removes, only the disk says. Name the files;
  - a word `git restore --staged` takes before `--` with a quoted expansion, as in `git restore --staged "$f"`, may still be `--worktree`, since its value may start with `-`. Write `git restore --staged -- "$f"`;
  - a variable set on a line that runs `gh` or `glab`, such as `GH_EDITOR=vim`. Set it in a separate command, or use gh's own flags, such as `--repo` and `--hostname`;
  - a write to a variable the line set, as in `T=$(mktemp); echo x > "$T"`, may name the config, since the value may change before the write. Write to a literal path;
  - an `echo` with a backslash, or a redirect, piped into a shell, as in `echo ls 2>/dev/null | bash`. Use `printf`, or `bash -c`;
  - text that names an approval, edited with `sed -i` or a script in an interpreter's here-document. Use the Edit tool.
- **GitLab** is only as trustworthy as the pipeline execution policy that injects the gate. Fork MR pipelines fail closed. A merge train car passes only when its commit's tree is the approved head merged onto the car ahead or the target.
- **An approval line an App posts for a person never counts**, since whoever holds the App's user token, an agent included, could have posted it.

## Data handling

The gate reads the change through the platform's API and writes a status, a record, and an event, and it carries no telemetry. At run time the gate reaches the platform's API and the artifact storage that API redirects evidence downloads to. It fetches the change's commits from the platform's git server. Beyond those, it reaches only what you configure, which is an `extends` parent or org preset fetched by URL, and the attestation endpoints when `evidence.signer_workflow` is set. [The full egress list](docs/PLATFORMS.md#github-enterprise-server-and-restricted-actions) names every host. What it reads, writes, and keeps, and for how long, is listed in [docs/ENTERPRISE.md](docs/ENTERPRISE.md#7-data-handling-and-privacy).

Outside the gate, these commands reach the network, and only when you run them:

- Any command that loads a config whose `extends` names a URL fetches that URL, `aidd validate` among them. The guard hook and the session hooks never do.
- `aidd init` and `aidd upgrade` can ask github.com for the commit of the aidd release tag with `git ls-remote`. They wait 5 seconds at most and work without an answer.
- `aidd doctor` asks github.com with `git ls-remote` whether the aidd commit that the CI files pin exists. With a GitHub token from `GH_TOKEN`, `GITHUB_TOKEN`, or `gh auth token`, it also reads the repository and its branch rules from the GitHub API. `aidd gate --paths`, the MCP `gate` tool with `paths`, `aidd list`, `aidd goal list`, `aidd autopilot next`, and `aidd digest` run the same checks.
- `aidd autopilot next` may read the approval lines and reviews of the branch's open pull request from the platform's API, as the gate does. It needs a GitHub token for that. It also fetches the pull request's head and base from the platform's git server into `refs/aidd/*` in your local repository. It trusts only the repository that `project.repo` pins on the base branch, because `origin` is local git config that an agent can change. It counts an approval only for the local head and the local Spec hash. Offline under `AIDD_OFFLINE=1`, without a token, or without a pinned repository, it asks a person instead.
- `aidd integrate` and `aidd sync` fetch a goal branch's upstream from the platform's git server first, when it has one, and `aidd integrate` pushes the goal branch it moved there. `aidd goal open` pushes a new goal branch to `origin`, when there is one. Each uses your own git credentials and sends nothing else.
- `aidd import issues --github` reads the open issues of the repository you name from the GitHub API.
- `aidd eval standards --online` fetches the evidence URL of each entry in the standards registry. It also asks for the newest release of each library standard's tool, from the release feed of PyPI, npm, crates.io, Maven Central, NuGet, the Go module proxy, or GitHub releases. For a language version, it asks the official toolchain feed, which is go.dev, nodejs.org, the .NET release index at builds.dotnet.microsoft.com, Adoptium at api.adoptium.net, or python.org at www.python.org. The default check is offline.
- `aidd record verify --online` and `aidd record verify --bundle` run `gh attestation verify`, which reaches the attestation endpoints.
- In a repository whose gate runs on GitHub, `aidd approve spec` and `aidd approve merge` read who your token signs in as, and the branch's open pull request, from the GitHub API. Then they post your approval there as you, either as the approval line in a comment or as an approving review of the head. They use your own token from `GH_TOKEN`, `GITHUB_TOKEN`, or `gh auth token`, and post only after your yes. Your `merge it`, or your standing approval, also turns on the pull request's auto-merge, only where the base branch requires `aidd/gate`. `aidd approve stop`, which your typed `stop approving` runs, asks GitHub for the open pull requests whose auto-merge your standing approval turned on, and turns it off.
- `aidd publish`, which a person runs or asks for by typing `publish`, pushes the branch to the remote with your own git credentials. It pushes your decision records in `refs/aidd/decisions` too, which hold your email and login, unless `--no-records` keeps them here. On GitHub, it then opens the branch's pull request and posts your recorded Spec approvals there as you, with your token. On GitLab, it does the same on the merge request, with `GITLAB_TOKEN` only for the host `GITLAB_HOST` names (gitlab.com by default), or else the token `glab` stored for the project's host and port. aidd asks `glab` with its token and host variables removed. It posts nothing with a bot's token, and only on the project's own merge request at the head it just pushed, never a fork's.
- `aidd self-update`, and once a day the command a person runs at a terminal, ask github.com with `git ls-remote` for the latest aidd release. The daily check only says when one is out. `aidd self-update`, or the daily check under `AIDD_AUTO_UPDATE=1`, downloads that release's wheel and `SHA256SUMS` from its GitHub Release. It refuses a wheel whose sha256 does not match, and, with `gh` on PATH, runs `gh attestation verify` on it. uv, pipx, or pip then install that file, with its dependencies, of which it has none. `aidd self-update --main` instead fetches the tip of main from github.com, unverified. All of it runs in aidd's own cache folder, so the current repository's git config or `uv.toml` cannot steer it. The daily check never runs in CI, in a shell an agent started, or in a hook. `AIDD_NO_UPDATE_CHECK=1` turns it off.

The CI templates and the Claude Code mod connect too. The secret scan workflow that `aidd init` writes downloads gitleaks from its GitHub release and checks its SHA-256. The optional `aidd-diagnose.yml` fetches Claude Code from the npm registry, and sends a failed test log to the Anthropic API with your `ANTHROPIC_API_KEY`. The optional `aidd-notify.yml` posts to the Slack or Teams webhooks you set. In the aidd-mods plugin, `/aidd update` runs `claude plugin update` for each aidd plugin after one dialog. PLATFORMS.md covers [the diagnose workflow](docs/PLATFORMS.md#vendor-services-that-plug-into-the-loop) and [the webhooks](docs/PLATFORMS.md#notifications), and INSTALL.md covers [the plugin updates](docs/INSTALL.md#claude-code).

`AIDD_OFFLINE=1` turns off the `git ls-remote` lookup of `aidd init` and `aidd upgrade`, the daily update check, and the network checks of `aidd doctor` and of the commands that run them. The session hooks turn off the same checks for themselves. `AIDD_OFFLINE=1` does not stop an `extends` fetch, or a command whose flag asks for the network, such as `--online` or `--github`.

Autopilot writes outside the working tree, in the git directory at `$(git rev-parse --git-common-dir)/aidd/`. `aidd autopilot` writes `lease.json`, `journal.jsonl`, and the run events in `events.jsonl`. These files hold session ids, scopes, your git email, times, step codes and results, the heads they ran on, and the token counts, costs, and words a note records. Nothing sends them anywhere, and git never commits them. aidd commands write them, refuse a symbolic link in their place, and keep only the last lines of each journal file. But an agent with a shell can edit them. So the autopilot limits, the timebox and the token and cost caps, guide a cooperating autopilot. In Claude Code, the token cap counts what the session's own transcripts show; in another harness, the spend is self-reported. The person and the gate stay the controls, so a journal line never counts as an approval, and a person's outcome never comes from it. A person can remove the folder at any time; the next run starts without a lease or a journal. Autopilot's checks resist edits to the working tree and to the branch's content. They do not resist a local writer that rewrites git refs or `.git/config`, such as one that moves the local base branch; the gate in CI, on a clean checkout, stays the control for merges.

The commands that a project configures, such as its `tests` commands, `uv run`, or `npx`, belong to the project. They can fetch packages, and aidd does not control them.

## Supported versions

| Version | Supported | Security fixes |
| --- | --- | --- |
| 1.x, latest minor | yes | yes |
| 1.x, older minors | no | no; upgrade to the latest minor |

Nothing is released yet, and 1.0.0 will be the first version. There is no fixed release cadence, so "supported" means the latest minor of the latest major. An older minor keeps working — the gate is versioned through `aidd_version` — but it receives no fixes. Supported Pythons are 3.11 through 3.15, the versions in the classifiers of `pyproject.toml`. CI tests each on Linux, and on macOS and Windows in the manual run each release requires. A Python that leaves the CI matrix leaves support here too.
