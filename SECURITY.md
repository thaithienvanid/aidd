# Security policy

## Report a vulnerability

Use GitHub's private vulnerability reporting on this repository. Open "Security" → "Report a vulnerability", or go straight to <https://github.com/thaithienvanid/aidd/security/advisories/new>. Do not open a public issue. Expect an acknowledgement within 3 business days, and a fix or mitigation plan within 30 days.

If that form is not open to you, contact the maintainer through a contact option on their GitHub profile, <https://github.com/thaithienvanid>, and ask only for a private channel. Share the details once you have one. The same times apply from that first contact.

## What aidd does not do

aidd enforces nothing. It computes advice: the route of a change, and the level of each action (`allow`, `report`, or `ask`). The agent reads that advice through the skill and acts on it. A model can still ignore the skill, so never treat aidd's advice as a control.

The hard stops come from tools that already enforce:

- **The harness's own ask rules.** `aidd init` and `aidd upgrade` write each `ask` rule's command patterns into the harness's own settings. They do it for every harness with a documented, committed permission prompt: Claude Code, OpenCode v2 and later, Codex, Grok Build, Qwen Code, and VS Code's agent. [GUIDE.md](docs/GUIDE.md#every-coding-agent) lists each file. The harness then asks the person before a matched command runs. Codex and Grok Build read the rules only once the person trusts the folder. No prompt holds `intent.agree` for sure. Codex and Qwen Code match leading words only, and the trailer's value varies. Claude Code's pattern misses a commit message written as a heredoc, its own form (checked live on 2026-11-08). A message read from `-F <file>` or written as `-m "$MSG"` hides the trailer from the pattern too. So the skill asks, and `aidd status` and `aidd validate` count an agreement only when its commit carries the person's `Agreed-by` trailer. `aidd agree <ID>...` is the person's own way to make that commit, in their terminal, with their git identity. aidd itself sets the two fields on the named Intents that wait for agreement, refuses a file with an edit no commit holds, and commits those files alone. It applies nothing a run saved. It is `intent.agree` too, so every harness with ask rules asks before it runs. A harness that matches anywhere in a line asks at any spelling, and Codex and Qwen Code ask at its plain and launcher forms. It also runs only when its input and output are a terminal. That check is a net like the patterns: it stops an agent's plain shell call, but not one that makes a pseudo-terminal, such as with `pty.spawn` or `script`. What holds is the platform's branch protection and your own review of the commit. A harness without ask rules gets the skill alone, and `aidd doctor` says so. `aidd init` also lets aidd's own five MCP tools run with no prompt in Codex and Claude Code, by name and for aidd's server only. `risk`, `status`, `validate`, and `recall` only read. Like the CLI, they fetch a parent config that the repository's `extends` names by URL, which `AIDD_OFFLINE=1` stops. `record` writes only `.git/aidd/records/` and refuses a secret's shape. No record leaves the machine, since `aidd records push` is a command of its own, an `ask`. `aidd uninstall` takes the approvals out. With `mcp: {allow_own_tools: false}` in the config, the tools keep asking: `aidd init` and `aidd upgrade` write no approval, and take out the ones aidd wrote. A config that does not load adds no approval. Claude Code reads a project's `permissions.allow` only once the person trusts the folder, as Codex reads its rules.
- **The platform's branch protection.** It is the one control that holds whatever the agent runs. Protect the default branch: require a pull request and the test check, and block force pushes and deletion. Under `team`, also require a person's approving review. Under `solo`, nothing on the platform holds a merge for a second person. aidd never sets it for you, so set it yourself on GitHub or GitLab.

A command pattern is a net, not a control. It matches the command text the harness sees. An agent can reach the same effect through a script, an alias, a variable, another program, or an API call that no pattern matches. So the ask rules catch the common case, and branch protection stays the control.

`aidd risk --command` reads a command more closely than a pattern does. It looks inside the wrappers an agent uses by habit or by accident, such as `sudo`, `env`, `timeout`, `bash -c`, and `$(...)`, and it reads `gh api` flags in any order. That is advice for a cooperative agent, and no guard against one that hides a command on purpose. The harness's ask rules and branch protection are the hard stops.

## What stays unsafe

aidd's threat model is a cooperative agent that may forget a rule, never one that works around it. `.git/` is the person's own. So the nets below are cheap, and each breaks no normal setup. These are their limits:

- **Reading a secret file.** `secret.use` asks when a common reader, such as `cat`, `grep`, `source`, or `cp`, names a file that holds secrets, from its own list in `schemas/risks.json`. Claude Code, Grok Build, and Qwen Code also ask before their own file-read tool reads one. OpenCode's own defaults ask before it reads a `.env` file, and aidd adds no read rule there. Codex and VS Code's agent document no rule for a file read, so there the skill and `aidd risk` carry the ask. The harness rules hold the read tool only, never a shell reader, because a pattern for each reader and each path would nearly double the rules' size. A secret still leaks through any other program, a script, or a shell glob such as `cat .env*`. `env` and `printenv` stay allowed, because the agent runs them at every debugging step, so a secret in the environment prints with no ask. In Claude Code, aidd's rules carve the `.env` templates back out, such as `Read(!**/.env.example)`. They come after aidd's own read rules and before a person's, so a carve-out never lifts a rule of theirs. A person's own entry stays after aidd's carve-outs, even a copy of one of aidd's rules, so no carve-out lifts it. A file named `secrets.<ext>` asks whatever its extension, such as `settings/secrets.py`, because `file_reads.include` wins over the code excludes. Claude Code's rules write `Read(**/secrets.*)` again after the carve-outs, so the later rule takes it back in. That order, and a carve-out reaching only rules from the same file, are as Claude Code's docs say, unvalidated against a live Claude Code. A secret written into an ordinary code or settings file, such as `local_settings.py`, reads as code, with no ask. aidd's Claude Code rules also carve out source code, such as `**/*.py`, which the broad `credentials.*`, `secrets.*`, and `secrets/**` would match. Claude Code may still ask for code inside a `secrets/` folder. Its docs say a carve-out cannot reopen a file in a folder that a rule blocks whole. Grok Build and Qwen Code document no carve-out, so they ask for an example file and for code such as `credentials.py`. Claude Code asks for another file that `aidd risk` allows, such as `id_rsa.pub`.
- **Editing a frozen test.** After Spec approval, a Spec's tests (its `tests.files`) change only by `spec.revise`. `aidd init` and `aidd upgrade` write an `Edit` ask rule for each test file of every Spec that is approved, in progress, or in review. Claude Code, Grok Build, and OpenCode v2 have a file-edit rule, so each asks before its own edit tool changes one of those files. The rules come from the Spec files in the working copy, so they are as current as the last `aidd upgrade --yes`. A Spec approved after it has no rule until the next run, and `aidd doctor` says so. An agent can change a Spec's status and so drop the ask, with no ask of its own. That is the same gap as `sed -i`: then only a person's review of the pull request, a platform rule such as CODEOWNERS, and a delegated merge's check hold the tests. While a Spec file does not parse, an upgrade keeps the edit asks it wrote and names the file, and `aidd doctor` names it too. Together the approved Specs may list at most 500 test files and globs. Past that, an upgrade keeps the asks it wrote, as for a Spec that does not parse. `aidd upgrade` and `aidd doctor` name the Spec that lists the most, so one Spec's junk paths cannot push another's asks out. A copy of one of these rules that you wrote yourself stays when aidd drops its own, in Claude Code, where aidd's record keeps a count for each copy. The rule leaves, also at the next upgrade, once the Spec is done, rolled back, cancelled, or revised to a draft. Codex, Qwen Code, and VS Code's agent document no file-edit rule, so there the skill holds the tests. It also holds them in OpenCode when you have an edit rule of your own. A delegated merge's check compares them in every harness. A shell write, such as `sed -i`, a redirect, or a script, is no edit tool, so the rule may miss it. Claude Code's docs say its `Edit` rules also reach the file commands it recognizes in Bash, which aidd has not checked for an ask rule. `aidd validate` does not compare a test file with its approved form, so the control is a person's review of the pull request. Under a delegation, `aidd delegate check` for a merge defers when a file the change's own Spec froze differs from the commit its approval covers. It also defers when a file that a Spec froze differs from the fork point, unless the change records a revision of that Spec. `aidd test --require-green` stops there too. Holding the Spec is no revision: a branch named `spec/<ID>` or a prose edit changes nothing its approval froze. A revision is a new `revisions` entry, and the run says so in a note. A Spec freezes its `tests.files`, design files, frozen docs, and the files its test commands name, from approval until it is done, rolled back, or cancelled. A helper that a test only imports or reads is not frozen, so no check compares it. A test section of a manifest, such as `pyproject.toml#tool.pytest`, gets no rule, because a rule on the manifest would ask at every dependency bump. The checks compare that section's value, so a dependency bump beside it passes. A manifest that is gone or does not parse counts as changed. A path with a space, a bracket, a brace, a parenthesis, a backslash, or a character outside printable ASCII gets none either. Claude Code anchors its path at the project root. Grok Build's docs say nothing of the anchor, so aidd writes `**/` before the path, and Grok Build may also ask for a same-named file deeper in the tree, unvalidated against a live Grok Build. OpenCode's docs say nothing of it either, so aidd writes a leading `*`, which also matches an absolute path. OpenCode applies the last rule that matches, so an ask among your own edit rules raises ordering cases: a deny it would turn into an ask, an allow it would not outrank. So aidd writes OpenCode's edit asks only when `opencode.json` holds no edit rule of yours, and appends them to the `permissions` list. An edit rule is any `permission.edit`, `write`, `patch`, or `apply_patch` entry, in any form, a `permission` string, a `tools` switch for one of them, an agent's rule for one, or a `permissions` entry for one of those actions or for every action. With one of yours, aidd writes no ask, and takes out the ones it wrote earlier. `aidd doctor` names your rule and says no ask rule guards those tests. `aidd doctor` reads only `opencode.json`. OpenCode loads lower-priority config first and global rules after, so an edit rule in another file can come later and win. A deny of yours in another file can also sit before aidd's appended asks, which then outrank it. aidd's shell asks share this residual risk. An edit ask that you add yourself, identical to one aidd wrote, is taken for aidd's after the write, and aidd takes it out with its own. Anyone who can write the Spec files can add a path to `tests.files`, which adds an ask, never removes one. A pull request that lists a broad glob makes the harness ask more, which a person's review sees.
- **A local merge into the default branch.** `git.merge` asks before a `git merge` or a `git pull` while the default branch is checked out, and `aidd risk` reads that branch from git. A `git pull` asks there when any of its words is no option, whatever that word names. One with only options pulls the branch's own upstream, so it never asks there, when that upstream is the same-named branch on a configured remote. Any other upstream asks on the default branch: a local branch set with `git branch --set-upstream-to=feat main` (itself allowed), or a remote's copy of another branch. aidd also resolves each branch a merge names the way git does, so a tag named `main` is never the branch. It reads names as the repository is before the line runs. So a command earlier on the line that can create or move a ref, or change an upstream, makes the names unknown, and the merge asks. It fails closed: every command counts, except a short list of reads and of writes that move only the branch checked out. A `-c` on the merge itself counts too, and so does a command inside `bash -c`. So does a `git fetch` or `git pull`, because git follows the tags of what it brings, so `origin/main` can name a tag that the line made. Only `--no-tags` leaves it out. No harness documents a rule that reads the branch, and a `git merge` rule everywhere would ask at every merge of main into a feature branch. So the harness rules hold no `git merge` or `git pull`, and the skill and `aidd risk` carry this ask. aidd reads the branch in the folder the command runs in, after any `cd` or `pushd` earlier on the line. A `git checkout` or `git switch` earlier on the line adds the branch it names to read, and the stricter of that branch and the session's wins, because a checkout can fail or run unwaited. A branch the line creates is your own, another branch that exists is shared, and a name aidd cannot read, such as `-`, a tag, a commit, or a variable, counts as the default branch. So `git checkout -b feat && git merge x` still asks on the default branch, and a push that names its branch keeps its own reading. A merge or a push that names another repository (`git -C`, `--git-dir`, `--work-tree`, or `GIT_DIR`), or follows a `cd` aidd cannot model, asks on any branch. That is a target it cannot resolve: a variable, `-`, `~`, a missing folder, or a relative one while `CDPATH` is set. It is also a `cd` inside a command another runs, such as `bash -c` or `eval`, and the end of a subshell. So does a merge where git cannot tell the default branch. The MCP `risk` tool runs in the session's folder. Without its `folder` input, or `--folder` on the CLI, it reads that folder's branch, not the one where the command runs. A `folder` that is no git checkout asks. A cherry-pick or a rebase can also land another branch's work there. So can any command that moves the default branch's ref, such as `git fetch . a:main`, `git branch -f`, `git update-ref`, `git checkout -B`, or `git reset` to another branch. Those are left to the agent's judgment and the skill. Branch protection holds the remote's default branch.
- **A command that runs inside a program aidd does not read.** `aidd risk` reads a program by its file name, so `/usr/bin/git push` reads as `git push`, and it reads inside `env`, `sh -c`, and `bash -c`. It does not read the command string of another shell: `cmd /c git.exe push origin main`, `cmd.exe /c gh pr merge 5`, and `powershell -c git push origin main` all read as `allow`, with a note that no action matches. A program by any other name is not read either, even when it runs `git push` inside: a wrapper such as `my-git-wrapper`, or a script such as `/opt/tools/release.sh`. Any program whose file is named `git` reads as git, wherever its file sits. The harnesses' ask rules match the text of a command, never what it runs. The default branch's protection on the platform is what holds a push made this way.
- **A branch deletion through a push, in Claude Code.** Claude Code reads a trailing `:*` as its prefix form, so it and Grok Build hold no rule for `git push <remote> :<ref>`. There the skill and `aidd risk` carry that ask.
- **A program by its Windows name.** `aidd risk --command` reads a command as a POSIX shell does. So `git.exe`, `C:\Git\bin\git.exe`, and `bash.exe -c '...'` are programs it does not know. The answer is `allow`, with a note that no action's pattern matches and no rule gave it. On Windows, the harness's own ask rules are the stop.
- **A redirection written before the command.** `aidd risk` reads `cat .env` and `cat <.env` as using a secret file, so they ask. It does not read `< .env cat`, where the redirection comes first, so that line reads `allow`.
- **A write aidd does not read as an edit.** `aidd risk --command` reads a write to a file as an edit of it. It gives the level `aidd risk --paths` gives the file, and the answer names the file. It reads the target of a redirection (`>`, `>>`, `>|`, `<>`, `&>`, `2>`) and the file a writer names. The writers are `tee`, `cp`, `mv`, `install`, `ln`, `sed -i`, `perl -i`, `dd of=`, `truncate`, `rm`, and `unlink`, from `code.edit`'s `file_writes` in `schemas/risks.json`. These are its limits:
  - A program not on that list reads as before. So `curl -o .claude/settings.json`, `rsync`, `touch`, `patch`, `find -exec`, `find -delete`, `git rm`, or a script that opens the file writes with no ask. `touch` is off the list because it writes no content.
  - A path aidd cannot read is left unchecked. The answer stays as it was, with a note that names the path and says why. A word the shell expands is one case: a variable, a substitution, a glob, or a brace, such as `> "$LOG"`, `tee $(mktemp)`, `settings.{json,bak}`, or `rm .claude/*.json`. A redirect to a variable is everyday shell, so asking for each would slow honest work.
  - A relative path is read from the folder the command was typed in, and aidd follows no `cd`. From a word that may change the folder to the end of the line, the folder is unknown. Those words are `cd`, `chdir`, `pushd`, `popd`, and a command word the shell expands or that names a folder, but not `[` or `[[`, which test. They also include `CDPATH`, `auto_cd`, `cdable_vars`, and `env -C` or `sudo -D` in any spelling, also inside a subshell, a pipeline, or a `bash -c`. A shell function that changes the folder, such as a jump tool, cannot be known.
  - Where the folder is unknown, aidd reads a relative path by its name alone, and raises only for what an area guards by name. That is a tracked file that ends with the name where an area's glob names a file or a kind of file, such as `.aidd/config.yaml` or `**/*.pem`. It also covers a place such a glob could put the name, and a path of an area that the name ends with. So `config.yaml` could be `.aidd/config.yaml`, and `x/config.yaml` could not.
  - A bare name that only a folder-wide area guards, such as `index.ts` under `src/users/`, raises nothing. The command keeps its own level, and the note names the file for `aidd risk --paths`. The one cost is that an honest `> config.yaml` or `> settings.json` after such a word asks. A new file under a folder-wide area, and a script that changes the folder, such as `source env.sh` or `. ./env.sh`, are not seen. The `.` and `source` words are not folder changes, because aidd does not read the script they run.
  - A copy or a move of a folder writes files whose names the command does not give. That covers `cp -r`, `-R`, `-a`, a source that is a folder or that the shell expands, and `mv dir x`. The folder it lands in reads as `aidd risk --paths` reads that folder: every tracked file under it, and a file that could land there. So it never reads lower than `--paths` for that folder. It can read higher than the files copied, such as `cp -r template/ .` in a repository that tracks a config. With `-r`, `-R`, or `--recursive`, `rm` reads each operand as a folder too, so `rm -r .claude` reads as every tracked file under `.claude`. `rm -rf` also keeps the level of `data.delete`.
  - A folder that an earlier command on the same line makes is not known yet. So `mkdir d && mv d x` reads `x` as a file.
  - A writer's long option is read as the current GNU `sed`, `cp`, `mv`, `install`, and `ln` take it: in full, or as a prefix that only one of their long options starts, such as `--in-pl` for `--in-place`. A version with other long options can take a prefix that aidd reads as ambiguous, and aidd then reads no option. A `-t` is read as the GNU programs read it, alone (`cp -t DIR`) or in a run of short flags (`cp -rt DIR`). One that follows another letter, as in `cp -rt DIR`, may be part of a value, as in the BSD `install -B.dist`, so it is read both ways: the folder and the last word are destinations. The other short options are read as before, and the macOS `sed -I`, which edits in place, is not read.
  - A device, a file under the system's temporary folder, and a file or a whole folder in one of aidd's own output folders (`.aidd/*/`) that git ignores are no edit. So `.aidd/tmp/roles/<role>.log` stays `allow`, and so does removing `.aidd/tmp/roles`. Any other file git ignores keeps the level its area gives, so `.env`, `.claude/settings.local.json`, and `.mcp.json` still ask or report.
  - A path outside the repository counts only when an area names it with a glob that starts with `/`. So a write to another checkout of this repository, to your home folder, or after a `cd` into another repository reads `allow`. A `cd` out and back in reads as the file in this repository.
  - aidd reads the file system when it answers. A link, or a folder that a later command on the line makes or replaces, can differ when the command runs.
  - No harness's ask rule holds the files of the `risk_rules` area. The harnesses ask before the edit of a frozen test only, and only through their edit tool. So a shell write to a frozen test reads as its command does.
- **The emergency route in CI.** A Spec on the emergency route cuts the run to the test commands the base marks `smoke`, by design, so a production repair is not held up. The CI check is then green on those commands alone. The emergency review that follows is the control, and a delegated merge defers on this route. The backfill is overdue from the day after `emergency.backfill_due`, by the local date, until `outcome.learn_ref` records the review. A `backfill_due` more than 30 days ahead warns, as a far `review_due` does, and blocks nothing.
- **Where a push goes.** `aidd risk` reads a `git push` from its words: the remote, the refspecs, the options, and the branch checked out. A `*` in a refspec reads as every branch, the default one too. One more check can only raise the level. If `remote.<name>.push` is set or `remote.<name>.mirror` is true for the remote the push goes to, or `push.default` is `upstream`, `tracking`, or `matching`, the push reads as one that may reach the default branch, with a note. A push that names a `<src>:<dst>` for every refspec is not raised by `remote.<name>.push`. A `-c` or `--config-env` on the same git command whose key starts with `remote.`, `push.`, `branch.`, `include.`, or `includeIf.` also raises it, with a note that names the key. aidd reads no value there, so it asks for a harmless key too, such as `-c push.followTags=true`. It asks git for `mirror` as a boolean, as git reads it. It reads no other setting, no included config file, and no environment variable except `GIT_DIR` and `GIT_WORK_TREE`, which name another repository. It does not read an abbreviated option name, a push option that acts on the server such as GitLab's merge request options, a git alias, or a hook. A config changed between the check and the push also goes unread.
- **What CI keeps from a test run.** aidd's GitHub action and its GitLab job upload `evidence.json` and each test command's full output as an artifact, and keep it for 90 days. A test that prints a secret puts it there, for everyone who can read the repository's artifacts. Set the action's `upload-logs` input, or the GitLab job's `AIDD_UPLOAD_LOGS` variable, to `false` to keep `evidence.json` only.
- **An OpenCode allow in a config aidd does not read.** OpenCode applies the last rule that matches, and it reads more than `opencode.json`: the system and global config, `.opencode/`, which outranks the root files, managed preferences, agent files, and a session's rules. An allow there can come after aidd's asks and win. `aidd doctor` reads `opencode.json` and `opencode.jsonc`, their agents included, and names each allow there that outranks an ask. Elsewhere, the skill and `aidd risk` carry the ask.
- **A standing delegation.** A delegate is an agent on the same machine as the agents it checks, so aidd cannot authenticate it. Any session under that OS user can write a record, a report, or an evidence file in its name, or delete a defer record or the stop file. The check runs again in full at the hook and at the answer tool, so a forged record skips only the delegate's judgment. The check cannot see a test that passes without checking the Acceptance, or a deploy set up on a host's website.
- **The delegation's hook.** It only answers a prompt the ask rules raise, so when it fails or never loads (`--bare`, `disableAllHooks`), the prompt stays. A Claude Code mod that approves the call, a merge through another MCP server's tool, or an action no ask rule names passes it by. Auto mode is a second net, and its docs say it does not guarantee safety. Before you delegate a merge, protect the default branch: require the `tests` check, block force pushes and deletion, and make a person production's required reviewer. The digest works only when you read it.
- **A delegated local merge, with no remote,** rests on the repository's own suite, which the check runs again on the exact head. A weak or empty suite passes, and no platform holds the default branch. The delegate's read of the diff can only defer, never prove the change right.
- **A standing delegation with no remote.** Its trust anchor is files on your machine, the default branch and the records, which an agent with shell access can write. So the delegate check stops honest mistakes and confused agents, not a local agent set on forging them.
- **The strong path for a delegation is a remote.** On GitHub, the check reads the platform's own branch rules, and this pull request's latest `tests` check run on the head. It has two limits. The rules hold only for a token they bind, so the check defers when the session's token can bypass them, as an admin with `enforce_admins` off or a ruleset's bypass can. And a check run proves only that the tests ran green, never that they check the Acceptance.
- **What the deploy readers cannot see.** The delegate check, `aidd doctor`, and `aidd init` read the repository's GitHub workflow files and its `.gitlab-ci.yml` as text. The check also reads the names of the tracked files a host deploys from, such as `vercel.json`, and the Pages source on GitHub. They cannot see the files of any other CI system, project or group CI variables, a host's own Git integration, the targets of a GitLab `include:`, or branch-protection settings. Branch protection and a required reviewer on production hold those gaps. That is why `environments` is the person's own statement, and the fill-in `aidd init` writes is a proposal.
- **A shape the readers cannot read counts as deploying.** A file can show that something deploys. It can never show that nothing does. A GitHub workflow with a deploy step whose `on:` they cannot read counts as running on every branch and tag. Such an `on:` holds a YAML alias, a YAML tag such as `!!seq`, a block scalar, or a duplicate key. A workflow file that is a link or unreadable counts as one that may deploy, and so does one over 1 MiB in `aidd doctor` and `aidd init`. A GitLab file with an `include:`, a `workflow:`, an anchor, an alias, or a tag is read for no job. It counts as deploying when any line names a deploy or an environment. So does a GitLab job that deploys and whose `rules:`, `only:`, or `except:` lines fall outside the grammar the reader knows. A delegated merge then defers.
- **Local forgery past the line above.** An agent with a shell can still reach a delegated action around the hook. It can pipe a `delegate_answer` call into `aidd mcp`, or put its own `gh` or `git` first on the PATH the check inherits. aidd counts none of these as a control.
- **What the delegate reads.** The delegate is a model, and the agent that asks writes much of what it reads. The check holds that text to rules that can only defer. Every part of the Spec an accept covers reaches the delegate whole: the Request, Acceptance, Design, Concerns, Rollback, Tasks with their scopes, and `risk`. A part past its cap defers and is named (`text_too_long`), and so does a diffstat of more than 300 files. A text with a character a reader cannot see defers (`text_hides_characters`), except a joiner between two letters outside ASCII. Each part is read as the packet carries it, besides the raw file, so an escape in a quoted YAML value is read too. The approval-phrase list is matched against the text as written and as the secret scan folds it, so a fullwidth or zero-width spelling is found. A look-alike letter from another script, such as a Cyrillic `а`, is not folded, so the list is a tripwire and not a control.
- **The Spec's own Request is the asker's text.** The agent that asks writes it on its own branch, so the packet labels it so. It also carries the saved request that the Spec's parent Intent names, read from the default branch's tip. The packet calls it the person's only when the Spec as the tip holds names the parent, or the Intent on the tip lists the Spec as a slice. A `parent` that only the change's head holds reaches the delegate as `claimed_request`, the change's own claim, so a change cannot borrow another Intent's request. With no saved request, the delegate defers on drift it cannot tie to the Acceptance. A person who can change the default branch can still change the saved request.
- **No record is a person's yes.** A delegated merge counts only the delegate's own accept of the Spec's approval, and only while `spec.approve` is delegated. A `decision` record is history, because any session can write one in a person's name. With `spec.approve` reserved, the person merges. A file in `.git/aidd/records/` that does not read as a record defers every delegated check until it is repaired or moved.
- **An open decision holds a delegated approval or merge.** A role's `open_decisions` entry has an `id` and its choices. It stands until a later handoff note's `answered` holds that `id` and one of those choices, written exactly. Until then, a delegated Spec approval or merge defers. Text on `decided` answers nothing, because a match of prose is no fact. A note is an agent's text, so it only narrows: an entry with no `id`, or one that does not read, stays open, and a note without the field asks nothing. What stays true: agents write both notes, so the check proves that one of the offered choices was recorded, never that it was a good one. A person's review of the change judges the choice. A delegate could read the notes too, but the packet does not carry them yet. A push of the change's own branch reads no note, because it lands nothing on the default branch.
- **The base decides what a Spec is.** The merge check reads a Spec's status, route, Task scope, tests, and frozen files as `aidd test` does, from the base where the base holds the Spec. A status or route the head lowers or claims defers anyway, so the head only makes the check stricter. A base config that does not load stops `aidd test --require-green`, so no value of the head's decides in its place. So a person merges the change that repairs that config, past the required check. The delegate's check stops on the same file, because the delegation lives in it, and no head vouches for its own config. A change that touches an open Spec's scope without holding it is a note, and its own paths decide whether it may merge with no Spec. A file that Spec froze is not a note: it must stay as the fork point holds it.
- **A commit the head does not control reads in today's shape.** The base, the default branch's tip, and the commit an approval covers read by the retired-names table of the aidd that runs, so `aidd upgrade` changes no answer. The head must already be in today's shape, so a head that still holds a retired name fails with the step. In aidd's own repository run from source, the head ships that table, as it ships `risks.json`. A name the upgrade leaves for a person is refused in the same way, so a check treats it as unreadable. A Spec says `risk.irreversible`. An old `risk.reversible` fails `aidd validate` on the head. A commit before the upgrade reads with the opposite value, never with its own value under the new name.
- **A limit can only make aidd stricter.** A project's `limits` lower what guards a control, such as the retries a Task gets, and no check that decides reads them from the head.
- **The delegate's model is the harness's choice.** aidd cannot see which model a harness runs. It warns only when `agents.models` names the delegate's model and a commit's `Assisted-by` names the same one. A `review_due` more than 180 days ahead also warns, and defers nothing.
- **A race on the folders.** aidd checks for a link before it writes, and opens the file itself without following one. A process of yours that swaps a folder on its path for a link between the check and the write can still redirect the write. A process that runs as you can write those files anyway, so this is out of scope.
- **The agent-identity check is a tripwire, not a control.** `aidd validate`, the waivers, `--approvers`, and Intent agreement refuse a value that names an agent or a bot, or hides one behind a lookalike letter, an `agent:` prefix, or an agent's address. That catches honest mistakes and plain agent names. Who is a person and who is an agent has one grammar, `$defs/identity` in `schemas/common.schema.json`. `agent:` and `role:` name agents, and a type's name is never a tenant's. A test holds that no identity that read as an agent reads as a person. A name wholly in another script that only looks like an agent's, such as `соԁех`, reads as a person. An agent that disguises itself could as well write a real person's name, so the controls are the harness's ask rules, the platform's branch protection, and the person's own words in the chat.
- **OpenCode v1.** aidd writes OpenCode's ask rules in v2's `permissions` list, which OpenCode v1 refuses, so aidd supports OpenCode v2 and later. `aidd doctor` names an installed v1, and installing v2 is the next step, as [GUIDE.md](docs/GUIDE.md#every-coding-agent) says. It runs only an `opencode` from outside the repository.
- **A harness's ask rules hold only in the mode its documentation names.** Each harness shows its prompt in a default permission mode, and some modes skip it. VS Code's agent skips aidd's rules under the Allow all level, Autopilot, and `chat.tools.global.autoApprove`, for read-only or sandboxed commands in Copilot sessions, and in worktree sessions. Grok Build skips them under always-approve. In OpenCode an agent's own allow, or a config in `.opencode/`, wins. Codex's `exec --ignore-rules` skips them. Claude Code asks in every permission mode. Whether Codex's bypass flag and Qwen Code's YOLO mode skip them is unconfirmed. [GUIDE.md](docs/GUIDE.md#every-coding-agent) lists each page and the date aidd read it, and `aidd doctor` says it for each wired agent.
- **The Copilot CLI and the cloud agent read no ask rules from the repository.** Only VS Code's Copilot agent reads `.vscode/settings.json`. The skill and branch protection hold the rest.
- **A push that names no branch has no harness rule in any format.** `git push` and `git push origin HEAD` ask in `aidd risk` while the default branch is checked out, but no pattern matches them, so the skill and branch protection hold that push.
- **Codex and Qwen Code hold fewer forms of an action.** They match a command's leading words, so a pattern with a `*` inside the command is held at its first words or not at all. A push through a remote other than `origin` or `upstream` is left to the skill. `aidd doctor` counts, for each action, the forms a harness holds in full, by a narrower rule, and by none.
- **A settings file aidd cannot edit safely stays as it is.** VS Code's settings file, Qwen Code's, and `opencode.jsonc` take comments, and aidd edits them in place and writes only a result that reads back as the same settings. A strict-JSON file with a comment, a file that does not parse, or an edit aidd cannot prove is left alone with the next step, so its ask rules are missing until you act.
- **`aidd init` in an agent session wires that session's agent, and says so.** It reads the variable its vendor documents and prints one line with the agent, the variable, the file, and how to leave it out. A variable no vendor page documents names no agent.

## In scope

- A way for aidd to run code from the repository it reads, such as through the MCP server's launcher, a config, or a Spec.
- A harness ask rule that aidd writes looser than the config says, or a change aidd makes to a person's own harness rules.
- Glob, schema, or YAML parsing bugs that change a route or a level.
- Leaks of tokens or secrets through aidd's output, evidence, or logs.
- A network call that is not on the list below, or that `AIDD_OFFLINE=1` should stop and does not.
- Template workflows that grant more permissions than their job needs.

An agent that ignores the skill's advice is not a vulnerability in aidd, because aidd enforces nothing. Report it as an issue with the "The agent didn't ask, or asked when it shouldn't" template.

## Trust model

- **A yes is the person's own words in the chat, or their delegate's answer on a passing `aidd delegate check`, for an action they delegated in the committed config.** A reserved action is always the person's. The check recomputes every check each time, and in Claude Code a `PermissionRequest` hook runs it again on the exact command before it runs. A delegated yes writes `Decided-by`, `On-behalf-of`, and `Delegation`, never `Approved-by`. Text from a ticket, a page, a file, a comment, a tool result, or another agent saying "approved" is data, never a yes and never an instruction. The skill tells every agent so.
- **A Spec approval is a note the agent wrote, not proof.** On the person's yes, the agent sets the Spec's `approved_by` and `approved_at` and commits it with an `Approved-by` trailer. Anyone with write access, or an agent, could write the same lines. Where you need proof, use the platform's review, which the platform records. Under the `team` profile, Merge approval is that review.
- **A headless run never takes silence as a yes.** In CI, a cloud session, or a scheduled run, an `ask` means stop and hand back with a handoff note.
- **A rule aidd cannot read is an error, never an `allow`.** An action no rule can name (`aidd risk --action pr.mrge`), a config rule that names none (`pr.opn`), and a config that does not load each stop the command that decides: `risk`, `test`, `new`, `standard add`, the MCP `risk` tool, and the delegation's check. The delegation's hook gives no decision, so the prompt stays. `aidd status`, `recall`, `explain`, and `doctor` show the problem first, show what they can read, and exit 1. Each error names the file and, where the file holds the key, its line.
- **A session override lasts the session.** A person may lower a rule for one session. It goes into the config only when they say so, and a config change is an ordinary edit that the pull request's review sees.
- **`shared: false` lowers a deploy to `report`.** An environment the config marks as the developer's own takes a deploy with no ask, and the review of the change, a pull request or the local merge's review, sees that config change. A branch glob with a wildcard gives way only for the branch checked out, a tag glob with one never does, and `aidd validate` warns about either. A parent's locked rule for an environment no parent defines is warned about too. A push that also names another branch reads as one to a shared branch, unless a rule decides every environment it reaches. A parent config's locked `git.push` or `git.push.force` rule still decides, and a locked `deploy.run` rule with `environment_shared` keeps every environment the parent defines. Under a standing delegation, a deploy to your own environment still reports when it names its branches and tags exactly, because nobody else uses it. An environment with a wildcard, and any parent-locked rule for deploys, make the deploy ask, even over a parent's locked lower level. Every other deploy asks under a delegation, and a deploy is never something the delegate answers. Codex and Qwen Code match leading words, so they hold no rule for a push that names an asking branch or tag after another refspec, such as `git push origin dev prod` or `git push origin feat prod`. The skill asks there.
- **aidd owns only the harness rules it wrote.** `.aidd/harness-rules.json` lists them, so `aidd upgrade` and `aidd uninstall` change only those entries, never a person's own. It also lists the one other setting aidd writes there, Claude Code's `worktree.baseRef: head` where the team's roles run. That setting grants no permission and changes no ask rule, and `aidd uninstall` takes it out only while it holds `head`.
- **aidd writes a repository's file only as a regular file inside it.** A cloned repository, a teammate's branch, or an agent can commit a link that points a write elsewhere, such as `.claude/settings.json -> ~/.ssh/authorized_keys`. So every command refuses a link at a file it writes or on the way to it. It also refuses a hard link, and a pipe or a device there. The command names what it refuses, skips that file, and goes on with the others. `aidd test` instead runs nothing when a file it checks for a change is refused. The same holds in the git folder, for the records, the list of pulled records, the index, and the delegation's stop file. In your home folder, aidd follows no link out of the folder it owns, such as `~/.aidd`. Your own settings there, such as `~/.claude/settings.json`, are yours, so aidd reads them through a link of yours, as a dotfiles setup makes. A file aidd creates in a repository is never more open than its folder: others may read it only when they may read the folder, and nobody but you ever writes it. The files aidd keeps for itself, such as evidence and records, are yours alone.
- **`aidd upgrade` prints each value it removes, scrubbed.** It shows the key and the value so a person can find them in git, with each credential hidden by the same patterns the records' secret check uses. A line that hid one says the file's own history holds the full value.
- **aidd removes only the team files it wrote.** `.aidd/team-files.json` lists each by its SHA-256, so `aidd upgrade` removes a file it no longer writes only while it holds what aidd wrote, and keeps a changed one with a note.
- **The test job is untrusted.** `aidd test` binds each exit code to the head commit, and the evidence names the commit it ran on. But it runs the head's own test code. An author who rewrites a test to pass, or changes a build script or a dependency to make one lie, is outside what the runner can see. The controls for that are the frozen-test edit rule, the delegate's frozen check, and a person's review of the diff. The runner does guard what aidd decides. The base commit decides what must run and what is excused, so a head cannot drop a test, lower a Spec, or move a folder to skip one. That holds for the commit the branch forked from, and the author chooses the fork point. A branch is not held to a test the default branch added after the fork, because that test may need code the branch lacks. When the default branch changed what decides since the fork, the run says so with a note and a `target_moved` field in the evidence. The note gives the next step: update the branch, then run again. A delegated merge defers on a head that does not hold the default branch's tip. The ruleset aidd writes turns on GitHub's "Require branches to be up to date before merging", which holds a change to the default branch's newest tests; a merge queue does the same ([page](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), read 2026-11-11). On GitLab, use the fast-forward merge method ([page](https://docs.gitlab.com/ee/user/project/merge_requests/methods/), read 2026-11-11). A run that gates a merge (`aidd test --require-green`, used by the CI templates and the delegate's own run) excuses no failing test. aidd cannot tell a test file from code, and a new Spec that freezes a wide glob would excuse a broken suite. A person's local run still excuses a Spec's own test before Implement, to say the new tests fail as expected.
- **Removing a test takes two changes, and both show it.** `aidd test` runs the base's copy of a test command that the head changes or removes. So one change cannot remove an approved test and break what it checked. Two changes in a row can: the first removes the command while it still passes, and the second breaks the behaviour. Each one prints a note that it changes an approved Spec, and a delegated merge defers on it. A person's review of that note is the control.
- **A worktree's test summary can be forged by whoever writes to it.** `aidd status` shows the last `aidd test` run from the untracked `.aidd/evidence/evidence.json`, for a person to read. It shows none when git tracks any file in that folder, in any case of its letters. It shows none when a link or a file stands for the folder or a parent of it, or when a link lies anywhere on the way. `aidd test` refuses a link at the evidence folder, its `evidence.json`, and its `logs` folder before it runs, and opens each evidence file and log it writes without following a link. Someone who can write to the worktree can still forge the untracked file, so the summary is never evidence.
- **aidd signs and verifies nothing.** It runs neither `ssh-keygen` nor `gpg`. Where you need signed history, use git's own commit signing and the platform's rule that requires it.
- **The MCP server's launcher trusts nothing in the project.** The aidd plugin starts `aidd mcp` with a `/bin/sh` line in `.claude-plugin/plugin.json`. That line:
  - unsets `CDPATH` and any shell function named `test`, `cd`, `pwd`, or `command`, so the person's shell setup cannot change what it runs;
  - serves the folder in `CLAUDE_PROJECT_DIR`, or the current folder with a warning, and refuses a value that is not a folder;
  - refuses to start when the plugin's source lies inside the project, so a repository cannot ship its own aidd;
  - takes `python3` or `uv` only from outside the project, and drops every `PATH` entry inside it before it asks uv for a Python;
  - runs Python with `-I -S`, so no `PYTHON*` variable, no site folder, and no module in the project folder load;
  - asks uv with `--offline --no-project --no-config --no-python-downloads`, with `VIRTUAL_ENV` and `CONDA_PREFIX` unset, so a project's uv settings or virtual environment cannot steer it.
- **A pushed record is permanent.** A record keeps the question, the person's git name, and their exact words, in `.git/aidd/records/`. `aidd records push` sends them to the remote's `refs/aidd/records`, where everyone who can read the repository reads them, and union merge never removes one. So `records.push` is `ask`, and the push first checks every file it would send: a link, a file that is no record, or a value that looks like a secret stops it. Its commit carries only the remote's record files and those records, never other history. A push never rewrites a record the remote holds: a local edit of one refuses the push. Records are not signed, and anyone who can push `refs/aidd/records` can write it with plain git. So these checks stop an accidental rewrite, not a forgery by someone with push rights.
- **A pulled record is another's text.** `aidd records pull` adds only records that pass the checks for size, for secrets, and for the fields this aidd knows. A record with a type or a field this aidd does not know, as a newer aidd writes, is kept as it is, and `aidd records` marks it `read in part`. The pull notes each record as pulled, and `aidd records` says so. `aidd risk --suggest` never counts a pulled record, a record read in part, or a decision the MCP tool wrote without `answer.by`. A delegated merge counts a pulled `delegate_answer` for nothing but a defer.
- **The MCP tools write only records and a cache.** `risk`, `status`, and `validate` answer from the repository's files and git, and write nothing. `recall` also refreshes its cache, `.git/aidd/index.sqlite`, which aidd builds again from the files. `record` writes one new file in `.git/aidd/records/`, never over another, after it checks the record's shape. It refuses a value that looks like a known key or token, a password in a URL, or a credential assignment. Those patterns catch a slip, not every secret, so a record never holds one on purpose, and `aidd records push` asks first. Each record says what wrote it, `written_with: cli` or `mcp`. Since the tool runs with no prompt, it never fills a decision's `answer.by` from the git name, so a record there never reads as the person's own.
- **A config preset fetched by URL is checked.** An `extends` URL must use https, resolve only to public addresses, and match its `sha256` pin. aidd follows no redirect. Behind a proxy (`HTTPS_PROXY`), the proxy resolves the host, so aidd cannot pin the server's address. The `sha256` pin still refuses wrong content.
- **A lock is a floor, never a trump.** A rule an organization's preset marks `locked: true` sets the lowest level of what it covers. It lowers nothing. The level is the higher of the lock's and the one the most specific rule that is not locked gives, built-in rules included. So a preset that locks `code.edit: report` still leaves the built-in `ask` for edits in `auth` and `payments`, and a locked `allow` changes no level. A lock can only raise. A repository's own rule can still lower a built-in level where no lock covers it.
- **A read form reads `allow` only when it provably writes nothing.** `aidd risk --command` reads a tag listing, `kubectl apply` or `kubectl delete` with `--dry-run=client`, `aws s3 rm` with `--dryrun`, and a few documented help flags as `allow`. Each form's own documentation says it writes nothing. A command reads as one only when it is that program by its bare name, typed as it runs and not inside a wrapper. It has no setting, redirection, or expansion, and only words the form lists. So `xargs`, `sudo`, `sh -c`, `$(...)`, a second command, and any unlisted word keep the action. A preview that still runs the project's code is not a form. `git push --dry-run` runs the pre-push hook (checked on git 2.55). `npm publish --dry-run`, `cargo publish --dry-run`, and `wrangler deploy --dry-run` run scripts or a build. A harness's ask rule matches leading words, so it can still ask for a form that `aidd risk` reads as `allow`. A config cannot add a form.
- **Auth and infrastructure paths hold in every language, by stem, never by a word inside another.** The built-in `auth` area now reaches a middleware, a `.guard` file, `permissions`, `rbac`, `acl`, and `auth` joined to middleware, guard, filter, or interceptor, in any language, and `infra` reaches each tool's own file names and a top-level `infra`, `infrastructure`, or `iac` folder. A pattern is added and none is removed from the rules' effect, so no route or edit level falls. The areas' excludes did not change, because an exclude would lower files the old lists reached. So a test fixture or example file that holds a new stem routes like any other.
- **The plugins' channel is git at `stable`, and the stable ruleset restricts who moves it.** A plugin update reaches an adopter, and runs as the MCP server and the CLI, from the commit `stable` points at. The ruleset blocks deletion and force-push and restricts updates, so only an actor on its bypass list can move the branch, and only forward. A fast-forward needs only a commit that descends from the tip, so the bypass list is the control: keep it to the maintainers who release. No checksum or attestation covers this channel.

## Data handling

aidd carries no telemetry. These commands reach the network, and only when you run them:

- `aidd self-update`, and once a day the command a person runs at a terminal, ask github.com with `git ls-remote` for the latest aidd release. The daily check only says when one is out. `aidd self-update`, or the daily check under `AIDD_UPDATE=install`, downloads that release's wheel and `SHA256SUMS` from its GitHub Release. It refuses a wheel whose sha256 does not match, and, with `gh` on PATH, runs `gh attestation verify` on it. uv, pipx, or pip then install that file, which has no dependencies. With no release yet, `aidd self-update` falls back to the tip of main, unverified, and says so. It reads the commit from the same `git ls-remote https://github.com/thaithienvanid/aidd`, and uv, pipx, or pip then fetch `git+https://github.com/thaithienvanid/aidd@<commit>` from github.com; `aidd self-update --main` asks for it even when a release exists. All of it runs in aidd's own cache folder, so the current repository's git config or `uv.toml` cannot steer it. The daily check never runs in CI or in a shell an agent started. `AIDD_UPDATE=off` turns it off.
- `aidd init` and `aidd upgrade` can ask github.com for the commit of the aidd release tag with `git ls-remote`, so the CI files pin a commit. When they add the Claude Code plugins' marketplace, or find the one `aidd init` wrote with no branch, they also ask whether the `stable` branch exists, so the marketplace follows releases once there is one. They wait 5 seconds at most and work without an answer: the marketplace then follows `main`.
- `aidd init --claude-plugins` runs `claude plugin marketplace add thaithienvanid/aidd`, or `thaithienvanid/aidd#stable` once a release exists, and `claude plugin install`, and Claude Code fetches the plugins from github.com. Without the install, init wires the repository files instead.
- `aidd doctor` asks github.com with `git ls-remote` whether the aidd commit that the CI files pin exists, and, when a Claude Code settings file adds aidd's marketplace with no branch, whether the `stable` branch exists.
- Any command that loads a config whose `extends` names a URL fetches that URL, `aidd validate` among them.
- `aidd delegate check`, under a standing delegation in a repository whose remote is on GitHub, reads github.com with `gh api` and the session's own `gh` sign-in. Each read is a GET, about seven a check. It reads the default branch and its tip, the branch rules, and the pull request. It also reads the `tests` check run and its workflow run on the head, and the Pages source. It sends nothing and writes nothing there. `AIDD_OFFLINE=1` stops them, and the check then defers, because it never falls back to local evidence. With no remote, the check reads only this clone.
- `aidd records pull` and `aidd records push` fetch and push the ref `refs/aidd/records` through git, with a remote the clone already names, never a URL, and the push first prints where git sends it. The built-in rules ask before `records.push` however aidd is started, and before a `git push` of the ref. Like every pattern, that is a net, not a control.
- `aidd eval standards --online` fetches the citation URL of each entry in the standards registry. It also asks for the newest release of each library standard's tool, and of each tool a pack or practice skill pins in a command. It reads the release feed of PyPI, npm, crates.io, Maven Central, NuGet, the Go module proxy, or GitHub releases. For a language version, it asks the official toolchain feed, which is go.dev, nodejs.org, the .NET release index at builds.dotnet.microsoft.com, Adoptium at api.adoptium.net, or python.org at www.python.org. The default check is offline. It fetches https URLs only, and refuses a redirect to any other scheme.
- `aidd eval routing`, `aidd eval roles`, and `aidd eval tasks` start the agent CLI that `--agent-command` names, and that agent calls its own model provider. A maintainer runs them by hand, at a terminal or as the manual `evals` workflow.
- `aidd prototype --serve` listens for the design's page until Ctrl-C, on 127.0.0.1 only, or on the local network with `--lan`. It answers GET with the page and the files of the design's folder, never a path out of it or a dot-file, and lists no folder. It refuses a design at the repository's top, whose folder is the whole repository. It answers only a request addressed to its own address, so a page that rebinds a domain to 127.0.0.1 reads nothing. Under `--lan`, every path starts with a random token that only the printed address carries, and `network.listen` is a `report` action, so an agent that follows the skill says it started the listener. `--lan` serves plain HTTP. The Host check and the random token stop a guess, but not someone who sniffs the network, so on a network you don't trust, use a tunnel or keep to 127.0.0.1. Like every pattern, that is a net, not a control. It makes no outbound call.

The installer and the CI templates connect too. `install.sh` downloads a release's wheel and `SHA256SUMS` from its GitHub Release, or from the mirror `AIDD_RELEASE_URL` names. With no `AIDD_REF` and no release yet, it asks github.com for the commit `main` points to, with `git ls-remote https://github.com/thaithienvanid/aidd refs/heads/main`, else `https://api.github.com/repos/thaithienvanid/aidd/commits/main`, and builds from source at that commit, unverified, and says so. With `gh` on PATH, it runs `gh attestation verify` on the wheel before it installs anything, and accepts only the release workflow's attestation for that tag, so a dry run's attestation of `main` never passes. A mirror needs `AIDD_SHA256` or `gh`, because its `SHA256SUMS` proves nothing alone. The optional security workflow, `templates/github/aidd-security.yml`, runs four jobs. OSV-Scanner builds from the Go module proxy and asks the OSV database about each lockfile. Semgrep installs from PyPI and fetches the Semgrep Registry's free rules, with its metrics off. Syft writes an SBOM. gitleaks downloads from its GitHub release and checks its SHA-256. The GitLab template, `templates/gitlab/aidd-security.gitlab-ci.yml`, runs gitleaks the same way. The scanners' own sources are not under aidd's control. Without `gh`, the installer and `aidd self-update` still check the wheel against `SHA256SUMS`, and say plainly that its build provenance went unchecked.

aidd writes these files outside the repository, and nothing else outside it:

- `~/.aidd/bin/aidd`, the launcher of aidd's MCP server. `aidd init` writes it when it wires the server, and every repository's `.mcp.json` that names it starts it, so `aidd init` in any repository rewrites it for all of them. Only an installed aidd writes it: uv, pipx, the one-line installer, `pip install` (also `--user`), the zipapp, or a Claude Code plugin's copy. An editable install counts as a source checkout. An aidd that runs from a source checkout leaves it as it is and prints a `kept` line. So a branch's unfinished code never becomes the aidd of every repository here. `aidd doctor` warns when the launcher starts a source checkout or a path that is gone. `aidd uninstall` keeps it and says why.
- aidd's cache folder, `$XDG_CACHE_HOME/aidd`, else `~/.cache/aidd`. It holds `self-update-checked`, the day of the last daily check, and `self-update/`, where `git ls-remote` and a reinstall run. Each release wheel `aidd self-update` downloads and verifies stays there, under `self-update/<tag>/`. It also holds `pyz-<hash>/`, named by the first 24 hex characters of a zipapp's sha256: the data that zipapp extracts on its first run, about 6 MB. A folder no zipapp has used for two weeks is removed when another zipapp extracts its own.
- Folders in the system's temporary folder, each removed when its command ends. `aidd test` checks a red test in an `aidd-red-*` worktree, and `aidd eval tasks` runs each case in an `aidd-eval-*` folder. `aidd delegate check` runs `aidd test` on the head in an `aidd-delegate-*` worktree, for a Spec approval and for a local merge. `aidd records push` and `python -m aidd.pyz` each build in another. `install.sh` downloads the release wheel into one, and removes it when the script exits.
- With neither uv nor pipx, `install.sh` installs into a venv of its own at `$XDG_DATA_HOME/aidd/venv`, else `~/.local/share/aidd/venv`, and links `~/.local/bin/aidd` to it. `aidd self-update` reinstalls there.

Other tools write their own folders when aidd runs them. uv, pipx, and pip keep the installed aidd where each keeps its tools. `aidd init --claude-plugins` runs `claude plugin`, which writes Claude Code's user settings and its plugin cache.

The git folder is yours. `git clone` never copies a repository's config, hooks, or `info/` folder, so what a clone holds there, you wrote. A repository you received with its `.git` folder, in an archive or from a shared drive, is untrusted to git itself, to your editor, and to your agent. aidd cannot make that safe, so clone it again.

Under that model, aidd adds a net under its own reads, for what a tree can carry without `.git/`: its `.gitattributes`, `.gitmodules`, and files. Git runs with the handler variables dropped. It runs no hook file, fsmonitor, pager, external diff, or textconv, and it does not enter a submodule's work tree. Git 2.54 and later also run a hook that config names (`hook.<name>.command`), which `core.hooksPath` does not stop, and a tracked file can bring one in through `include.path`. Git has no switch for all of them, so a call that can start a hook turns off each hook name the repository's config lists with `hook.<name>.enabled=false`, and a `status` writes no index. A `diff` is such a call too, because it refreshes the index when a file's stat changed and its content did not, which starts `post-index-change`. An earlier git ignores those keys. A read that can run a filter (status, diff, cat-file) blanks every filter that the repository's own config names. A read of refs, commits, or trees (rev-parse, ls-tree) runs no filter, so it skips that step. A signature field such as `%G?` is refused, because git would run the repository's `gpg.program`. Filters and hooks in your global or system git config, such as git-lfs, still run. `aidd doctor` starts the MCP server only when `.mcp.json` holds the entry `aidd init` writes, and says it did not start any other. A fetch or push through aidd enters no submodule, and a fetch runs no alternate-refs command.

Two parts of the net need a recent git. A read ignores the tree's attributes only with git 2.40 or newer, and the git of older Xcode Command Line Tools is 2.39. A read fetches no missing object only with a git that has the May 2024 fix for CVE-2024-32465. The installer runs its `git ls-remote` calls from its own folder, with none of your git config, over https alone.

What aidd does not cover: a call to a remote keeps your `GIT_SSH_COMMAND`, `GIT_ASKPASS`, and `GIT_PROXY_COMMAND`, by design. It also runs the repository's own ssh command, credential helper, askpass program, proxy, upload-pack and receive-pack, and `remote.<name>.vcs`, and it honors `http.sslVerify`. A push to a remote on a local path runs that remote's own hooks and config, such as `pre-receive` and `core.alternateRefsCommand`. The commands that write a clone, such as `checkout` or `worktree add`, run its filters. `src/aidd/kernel/git.py` names each.

`AIDD_OFFLINE=1` stops every optional call: the `git ls-remote` lookups of `aidd init`, `aidd upgrade`, and `aidd doctor`, the daily update check, the prototype server, and an `extends` fetch, so a config whose parent is a URL then fails to load with that reason. It also stops the plugin install of `aidd init --claude-plugins`, which wires the repository files instead. `aidd self-update` then says it is offline and installs nothing. `AIDD_OFFLINE=1` does not stop a command whose flag asks for the network, such as `--online`.

The commands that a project configures, such as its `tests` commands, `uv run`, or `npx`, belong to the project. They can fetch packages, and aidd does not control them.

## Supported versions

| Version | Supported | Security fixes |
| --- | --- | --- |
| 1.x, latest minor | yes | yes |
| 1.x, older minors | no | no; upgrade to the latest minor |

Nothing is released yet, and 1.0.0 will be the first version. There is no fixed release cadence, so "supported" means the latest minor of the latest major. An older minor keeps working, but it receives no fixes. Supported Pythons are 3.11 through 3.15, the versions in the classifiers of `pyproject.toml`. CI tests each on Linux, and on macOS and Windows in the manual run each release requires. A Python that leaves the CI matrix leaves support here too.
