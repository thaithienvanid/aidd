# Changelog

This file lists every notable change to aidd.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The method, the schemas, the gate, the CI templates, the skill, and the team plugin share one version. Every record carries `aidd_version`. [CONTRIBUTING.md](CONTRIBUTING.md#versioning) says what counts as a patch, a minor, or a major change.

## [1.0.0] - Unreleased

AIDD, short for AI-Driven Development, is a method for delivering software with AI agents. Agents do the work, and humans decide what to build, what lands, and what leaves their machine. aidd is the open-source toolkit that runs it. It's a command-line tool with no runtime dependencies, a CI check named `aidd/gate`, a skill that coding agents read, and an optional delivery team of agent roles. This is the first release, so everything below is new.

### Added

#### The method and the loop

- **[One loop](docs/METHOD.md) for every change.** It runs Plan, Specify, Spec approval, Implement and Verify until green, Review, Merge approval, Publish, Roll out, and Learn. The person runs the outer loop, and the team runs the inner one. The loop is always on.
- **Four decisions stay a person's.** They're D1 the plan, D2 Spec approval, D3 the release, and D4 the launch. Spec approval binds the Spec, its tests, and its design as they read at the commit the person approved. Merge approval binds the head commit. The team decides the rest on evidence, and METHOD §5.2 names who takes each decision.
- **Routes and profiles.** aidd sizes each change by what it touches, as `standard`, `minor`, `normal`, `major`, or `emergency`. The author may ask for more control, never less, and the gate computes the route again from the real diff. The profiles `solo`, `team`, `org`, and `audited` set how strict the gate is.
- **The Spec** is the work item and the contract. It holds the intent, the Acceptance, the scope, the tests, the risk, the rollback, an observe window, and a cost estimate that `aidd validate` checks against the project's budget. `aidd revise <ID> "<why>"` reopens an approved Spec as a change order, also one that left the branch, which it restores to record why and then removes again. The Merge approval then names each file that Spec froze and that changed since its approval. A Task's scope names a module, and `aidd new spec --paths` and `aidd import` keep a protected or risky file exact.
- **Requirements a machine can check.** A business rule with three or more conditions becomes a decision table, with one Acceptance id per row. `aidd validate` warns about a word the glossary says to avoid.
- **Runbook readiness.** `aidd validate` warns about a linked runbook's unchecked launch-readiness boxes while its Spec is in review.
- **Maintain and deprecations.** `aidd list --upkeep` lists the upkeep that is due, and each item a person picks becomes its own change. A Spec's `deprecations` names what it deprecates and its sunset, and a passed sunset warns until a Spec that removes it lands.
- **The loop fits the work to its reason.** A major change gets a tech spec and a runbook only for a reason beyond a protected path. The verifier's run on a clean tree is the one full agent run per head, and Review runs Verify beside its readers on that head.

#### Decide once, in your own words

- **Three rings.** Work moves through the inner loop and the local trunk on your machine, then the shared outer loop, as [METHOD.md](docs/METHOD.md#three-rings) explains. `land it`, or `aidd land`, lands a change on the local trunk. `publish`, or `aidd publish`, takes it off your machine, and `merge it` merges its pull request.
- **Who publishes.** The config's `publish` says either `person`, the default, or `agents`. Under `person`, the guard holds an agent's push and pull request until you type `publish`, even through a git alias or a platform API call. `aidd publish` carries your recorded Spec approvals to the pull request on GitHub.
- **Typed words are the decision, in every agent.** `approve SPEC-1`, `approve merge`, `land it`, `publish`, `merge it`, `approve all`, and a proposal's `decide PROP-1 go` and `sign off PROP-1` record exactly what you named, before the model reads the prompt. aidd's own prompt hook does it in Claude Code, Codex, OpenCode, Grok Build, and Google Antigravity, with no plugin and no terminal. In Claude Code, the MCP tools `approve_spec`, `approve_merge`, `land`, and `publish` can also open a dialog. The prompt hook and the aidd-mods pane read a prompt the same way: Unicode NFKC, with no zero-width or other format characters, and every space as a plain space. A prompt with a direction control, or a digit that folding makes from any shape but a fullwidth digit, decides nothing.
- **No question twice.** A note says whether aidd recorded your words, and why not, with the fix. A Spec that isn't ready isn't offered to you. A typed `land it` or `merge it` holds for the fix the gate or the reviewer asks for, while the Spec stays as approved.
- **Never blocked by a failing gate.** Your Merge approval is recorded whatever else fails, and the gate holds the merge until the team fixes it. On GitHub, `merge it` posts your approving review, and `aidd approve merge --auto-merge` turns on the pull request's auto-merge where the base branch requires `aidd/gate`.
- **Standing approval.** `approve all` lets the agent record each Spec approval and Merge approval for you, and land the work, until you type `stop approving`. `approve all and publish` also publishes, and `approve all but major` keeps major changes for you. The plan and every launch stay yours.
- **Local-first.** aidd needs only git. Your typed words, or `aidd approve spec`, `aidd approve merge`, and `aidd land` at your own terminal, record each decision, and `aidd land` lands exactly the tree it tested. It builds that commit without a checkout and moves the base branch where it is checked out, so `land it` works from a linked worktree, and a refusal moves nothing. It runs your `commit-msg` hook on the landed message, as `main` holds it and without credentials, and no other hook. It signs when `commit.gpgsign` is set. Where a platform's gate decides, aidd posts your approval on the pull request instead.
- **Your account, found for you.** Where the Approvers are GitHub logins, aidd uses the signed-in `gh` account that is an Approver and names it. With a wrong git email, the refusal gives the one-line fix.

#### The gate and the guard

- **The gate** checks each change before it merges. `aidd gate` decides pass, pending, or fail from facts. New behavior fails on the base commit and passes on the head, the change stays in its approved scope, and the right humans approved it. Its rules answer five questions, generated from the rulebook.
- **The guard** checks each step an agent takes. It denies an edit outside the active Spec's scope, an edit of a frozen test, and an agent's command that approves, lands, merges, or publishes. It holds deploy commands until a person allows them.
- **Advisory by default, with always-on rules.** In the solo and team profiles the guard and the gate advise, and an edit outside the rules goes through with a note once a session for each kind. The org and audited profiles enforce, and `mode` sets either. In every mode [the always-on rules](docs/METHOD.md#always-on-rules) hold, so no agent approves, lands, merges, or publishes for a person, changes their decision records, or loosens the config and the guard's wiring.
- **Checks follow the branch.** The default branch gets the full gate, a goal branch moves only through `aidd integrate` and `aidd sync`, and a Spec or Task branch keeps each edit in scope, as [METHOD §10.4](docs/METHOD.md#checks-by-branch) says. On `explore/<topic>` the guard allows every edit that the person's own typed `explore branch <topic>` freed, and the gate's rule `explore` fails the branch with `explore.branch`, so nothing merges from it. `/aidd-team:explore` builds a direction that needs real code there.
- **No Change Request block by default.** The gate derives a change's declaration from facts it checks: the one Spec the diff carries, or else the route the diff computes, the riskiest type the commit subjects name, and `assisted_by` from the trailers. A change never routes below its diff, and the head the tests ran on is the head that lands. A block stays for an emergency, a standard change, several Specs, or a route or risk the paths don't show.
- **A preference edit isn't major.** A change that edits only `mission`, `goal`, or `locale` in `.aidd/config.yaml` no longer takes the major route from the file. The gate reads base and head with the strict reader, and any other key, or a config it can't read, keeps the file protected.
- **Specialists by content.** A risk rule's `content` patterns match the lines a diff adds, such as raw SQL or a model API call, and ask that specialist pool on any route.
- **Codes you can look up.** The gate shows each finding by its code, such as `scope.outside`, and `aidd gate --explain <code>` gives its meaning and fix. Each finding's fix starts with its code's own next step, then adds the head, the pool, or the path. [ERRORS.md](docs/ERRORS.md) lists every finding, step, guard, and exit code at a stable anchor, and the run summary on GitHub links to it. A crash says it's a bug in aidd, and `AIDD_DEBUG=1` prints the traceback to attach.
- **A helper only reads, in the shell too.** A subagent that isn't an aidd-team role may only read. So the guard lets it run only a short list of read programs, such as `grep`, `rg`, `cat`, `find`, `sed -n`, and git's reads, and denies the rest, PowerShell among them. It also denies their options that write a file or start a program the command names, a program named by its path, and a line that sets a variable. The denial lists the reads, and says to hand a test run or a script to a role or the main session.
- **The guard, swept against real git.** A property-based sweep dresses ref-moving git commands in every shell form, then real bash and git judge each one, so a command the guard allowed that moved a protected ref fails the test. A small fixed-seed sample runs on every change, and a weekly job sweeps a larger sample seeded by the ISO week.
- **Changes made outside the agent's session, part of your next decision.** A program the agent runs, such as a Python script or a package manager, could change what the always-on rules stand on. At each decision, aidd keeps the watched state: the config's control keys, the guard's wiring, HEAD's branch, the decision records, the base branch, the git hooks, and your aidd launcher. Your next decision takes in what changed since, and it's never asked about on its own. A dialog lists each change before you answer, and aidd's note after a typed decision lists it, with how to put each back. Claude Code shows you that list directly. A looser config, a rewritten history of decision records, or a signed record aidd can't verify waits for a dialog that shows it, and until then the guard keeps the stricter rules. A change that could stop the guard itself, such as a git hook or a git config key that names a program, waits for aidd's own MCP dialog or your own terminal. When something changes after you decide, the agent's `aidd land`, `aidd approve`, or `aidd publish` stops and names your words to say again. Ordinary work is never paused, and a `mission` edit is no change.
- **Every stop says what to do next.** Each denial, finding, and error gives a step that works where the person is. A test fails on a message with no step, or one that names a command or flag that doesn't exist.
- **Evidence from a clean tree.** `aidd test` records when it ran in a tree with changes the repository's `.gitignore` files don't ignore, so one clone's `.git/info/exclude` or your global excludes never hide a file CI would see. The gate holds that evidence with `tests.dirty_tree`. `aidd init` and `aidd upgrade` add what each stack's tests and builds leave to `.gitignore`, and the files macOS and Windows leave, such as `.DS_Store`, in marked blocks that `aidd uninstall` takes back.
- **Always on, never in the way.** When you say to skip a step for a change, the agent records your words in its commit as `Aidd-Skipped`, and the gate reports the skip without failing it. `hooks.level: "off"` turns off the session hooks, and `components` the loop or autopilot, one at a time, and the [How-to](docs/HOW-TO.md#use-only-the-parts-you-want) shows how.
- **See what you can set.** `aidd config` lists the settings your config sets, with each value and where it comes from, then the few you may want to set. `aidd config --all` lists every setting and what it does. The config `aidd init` writes names its schema on its first line, so an editor completes each key.
- **Short help first.** `aidd --help` lists only the everyday commands you type, each a row of the README's everyday table. `aidd help --all` lists every command by group, and `aidd help <command>` shows one in full. Every command works as before.

#### Every coding agent

- **Any coding agent.** The `aidd` skill is a self-contained Agent Skills folder. aidd supports <!-- aidd:gen count:harnesses -->26<!-- aidd:end --> coding agents, such as Claude Code, Codex, Cursor, and Copilot, and `aidd init` wires the ones it finds. The guard runs in <!-- aidd:gen list:guard-harnesses -->Claude Code, Codex, Google Antigravity, Grok Build, and OpenCode V2<!-- aidd:end -->, and each was checked against a live run of that harness. In Google Antigravity, `aidd init` also wires aidd's MCP server as a workspace plugin in `.agents/plugins/aidd/`, and the guard reads the `agy` CLI's file tools and holds a subagent to its role. `aidd upgrade` keeps aidd's own entries in their files current, and leaves a hook command you changed as you wrote it, with a note.
- **The `/aidd` verbs.** Claude Code's `aidd-mods` plugin and OpenCode's `.opencode/plugins/aidd-tui/` add `/aidd status`, `/aidd approve`, `/aidd stop`, `/aidd land`, `/aidd merge`, `/aidd publish`, `/aidd decide`, `/aidd sign-off`, `/aidd explore`, `/aidd update`, and `/aidd init`. `/aidd` alone lists every decision that's yours, one line each, with the words that make it. So you never need to know the words in advance. In OpenCode, each answer is recorded from the terminal's own dialog as `--decided-via opencode`, which the guard denies to an agent's shell.
- **OpenCode V2.** The guard plugin `.opencode/plugins/aidd.js` asks aidd before every tool call, every shell, and every prompt, and it runs the session-start and pre-compact hooks. When a turn ends, it runs the stop hook, as Claude Code's `Stop` does, and after a compaction the session-start note reads the saved state back. It denies Code Mode's code-running tool, and a shell call whose command it can't read, since the guard can't check either.
- **Codex.** `aidd init` wires the guard and the session hooks in `.codex/hooks.json`, and the `aidd` MCP server in `.codex/config.toml`, which Codex reads in a trusted project. `--team` writes the team commands as skills in `.agents/skills/`, which you run as `$aidd-<flow>` and Codex never starts on its own.
- **Grok Build.** The guard reads Grok's tools on both of its routes, `StrReplace`, `Write`, `EditNotebook`, `Delete`, and `apply_patch` among them, and denies a tool it does not know in a repository that uses aidd.
- **Orca.** Inside [Orca](docs/ORCA.md), the session hooks put the next step and the work's state on the worktree's card, move the worktree to its board column, and mark it unread while a person decides. `aidd publish` links the pull or merge request there. It's display only, never evidence, and `hooks.orca_status: false` turns it off. `aidd init --orca` writes the documented `orca.yaml` and never replaces one.
- **MCP.** `aidd mcp` serves the checks and the decision dialogs as MCP tools. It speaks MCP 2026-07-28, and still answers a client that opens with `initialize` at 2025-11-25 or 2025-06-18.
- **Platforms.** On GitHub, aidd brings a reusable gate workflow, a composite test action, a GitHub App as the status source, and merge-queue support. GitLab support is experimental, and covers merge trains and `aidd publish`, which opens the merge request and carries your Spec approvals there; it's not yet run against a production instance. Any other CI builds a context file and runs `aidd gate --context`. [PLATFORMS.md](docs/PLATFORMS.md#leave-a-ci-provider-or-a-git-platform) says how to leave a provider and keep aidd's records.
- **Setup.** `aidd init --dry-run` reads the repository first, and `aidd init` writes the config, the skill, and the CI files with the gate in the profile's mode. At your own terminal it asks for the profile and the approver, then offers the Day-0 commit. Run again, it adds only what's new, such as another agent with `--harness`. It refuses a `--test` command that starts with `NAME=value`, and names the `env` form that runs. `aidd doctor` checks the wiring, `aidd upgrade` keeps the files current, and `aidd uninstall` reverses them. An upgrade refuses when the config names a newer aidd, or a version it can't read, and in aidd's own source it runs only from that checkout. `/aidd update` upgrades the files only on a CLI the check called the latest, or one it just updated. [Install](docs/INSTALL.md#updates) explains the rest.
- **From GitHub only.** aidd is not on PyPI, so a package named `aidd` there is not this one. `install.sh` installs a release's wheel from its GitHub Release. It installs once the wheel matches the release's `SHA256SUMS` and, with `gh` on PATH, once its build provenance verifies. `AIDD_RELEASE_URL` points it at a mirror of the releases, which also needs `AIDD_SHA256` or `gh`, because a mirror's `SHA256SUMS` proves nothing alone.

#### Plans, goals, and the flow

- **Big goals and small goals.** A big goal is an Initiative of small goals, Epics of two weeks or less. Each Epic says how it reaches users. `incremental`, the default, lands each Spec by itself, `flagged` keeps it behind a flag until its `launch` Spec, and `batched` uses a goal branch.
- **Goal branches.** `aidd goal open` cuts `goal/<EPIC>`, `aidd integrate` lands each verified Spec in it with no person asked, and `aidd sync` merges newer work in, never rebasing. `--undo` takes a Spec out, and the release to `main` is [one decision](docs/METHOD.md#103-goals-big-small-and-how-each-reaches-users).
- **Trunk-based flow.** `aidd list`, `aidd goal list`, and `aidd doctor` show each open branch with its age. They warn past `limits.max_open_branches`, `limits.max_branch_age_days`, and `limits.max_goal_age_days`, and when the local trunk goes unpublished too long. `aidd doctor` also notes a linked worktree that holds the default branch, with the commands that move it back. [METHOD §10.4](docs/METHOD.md#104-trunk-based-flow) has the limits.
- **Worktrees.** `aidd worktrees` shows what each worktree holds and whether it merged, and `aidd worktrees clean` removes the merged ones after a person's yes. One dev stack serves them all, through `project.dev_services` and `AIDD_WORKTREE`.

#### The delivery team

- **Agent roles led by humans.** The optional `aidd-team` plugin adds <!-- aidd:gen count:roles -->13<!-- aidd:end --> roles, from product manager to SRE, and <!-- aidd:gen count:commands -->19<!-- aidd:end --> commands, from `/aidd-team:plan` to `/aidd-team:maintain`. Each role writes only its own files and hands off through a file and a short note. The verifier writes the tests and runs the built change, and never writes the code. The reviewer stays the separate check of the code.
- **One developer for every code Task.** The developer builds AI features and data work too, and the Task's `skills` load the specialty: `ai-evals`, `ai-features`, `schema-migration`, or a data pack. Only the SRE stays apart, because CI and infrastructure are protected paths. The SRE also builds the pipelines and the infrastructure it runs, and the platform engineer role is gone.
- **The team as your software company.** The team lists each decision that a standard, the project's rules, or aidd's default settled. You read them on the Merge approval page, and under "Decisions the team made" in `aidd digest`, which `--client` calls "What we decided for you". A request that changes what you agreed becomes a change order, as [ADOPTION.md](docs/ADOPTION.md#the-team-as-your-software-company) explains.
- **Client work.** The `delivery-manager` role qualifies client work, keeps the RAID log, and writes the contract with `aidd new contract`. Where it isn't installed, the product manager does its work as the `fallback`. `/aidd-team:handover` hands a delivered system over for sign-off.
- **Perspectives before a plan.** A consult round asks the architect, the designer, the security engineer, and the `domain-expert` for a card each. The domain expert speaks for its domain pack and edits no file.
- **Each role's record.** `aidd metrics --roles` prints one row per role, from the gate events, the Specs' Tasks, the guard's log, and the reverts, with the role's latest eval result. Under 10 changes a row is too few to judge.
- **Role placement.** The lead of each team command places each role. It plays a role that adds a view to its own work, with the pack from `aidd context <ID> --role <role> --play --session <id>`. The guard then holds the session to that role's files too, so playing a role only ever narrows what it may write. The session ends it with `--stop-playing`, or it lapses after 12 hours. Since the session sets and ends it itself, it keeps an agent on track and is no control. So the lead starts every role that checks, tests, or reviews, and every role under autopilot, and the guard holds a started role by itself. Each role it starts gets its context pack, never pasted facts.
- **Every hand-off has an owner.** Each role writes only what its area holds, so the design system's text and a suggested Spec reach the role that writes them. The compliance analyst reads the diff at Review. The table of who decides what ships with the team, and Codex runs each command as `$aidd-<flow>`.
- **Several teams and the ecosystem.** [ADOPTION.md](docs/ADOPTION.md#several-teams) maps Team Topologies onto the config, so growth adds Approvers, owners, and presets, never a second loop. `aidd extensions suggest` names the plugins that fit each role, and aidd installs none.

#### Autopilot

- **The engine decides.** `aidd autopilot next` computes the one next action from git, which is to run a team command, ask a person, or stop. `/aidd-team:autopilot` runs those actions between your decisions, and its stop message names each decision that waits and the command that goes on.
- **Each role keeps its product-level work.** The team registry says which of a change's documents feeds which product-level work. When a change feeds one and leaves it as it was, `aidd validate` warns, so the same change brings it in line. `aidd context` hands that work to its owner and to the roles that build or check against it.
- **The whole product, clickable.** `aidd new product-prototype` starts the designer's living prototype in `docs/design/app/`. `sitemap.json` defines the navigation once, so every screen shows the same items in the same order. `flows/` holds one file per flow. `aidd prototype` assembles it into one page in `.aidd/views/`, and checks that every link opens a screen, every screen has a state, and every flow is reachable. It exits 1 on a problem, and writes no page it cannot build.
- **One prototype viewer, like a design tool.** A Spec's prototype and the whole product open in the same workspace. It has device frames for the web, iOS, and Android, and a review column that says how many states you have seen and opens the next one (N). The Board shows every screen in every state, System the tokens and components, and Build details each screen. Each screen renders in its own frame, so the product's styles, breakpoints, and dark mode work as they will in the built UI. Full screen (F) shows the screen alone and still clickable. There is no wireframe mode: a rough direction is an exploration's sketch. `aidd prototype <file>` opens a Spec's frozen prototype in the current viewer, and never changes the file.
- **The prototype tool, aidd-team's own.** The viewer, the checks, and the component contract live in `plugins/aidd-team/tools/prototype/`, one standard-library file that runs without aidd. `aidd prototype` runs it. A Spec's prototype file holds the design only, so the viewer is never copied into a project, and every design gets every fix to it. A design names its format, so a newer tool reads an older design.
- **The viewer, complete for review.** The side panels hide with `[` and `]`, and a frame too wide for them closes them. A web page or a desktop window fits by its width, beside two desktop frames and a full-width web frame. The Board can draw an arrow for each link between screens. A feedback note has a kind (change, remove, add, question), and the Notes tab shows the earlier rounds, each item done or open. When a design names its Spec, the notes end with the words to type, such as `approve SPEC-24`, because the page records no decision. Compare shows the built UI's screenshot of each view beside the design, read from local files only.
- **`aidd context` gives each step what it reads.** A loop step's reads are data, `loop.step_reads` in the team registry. Implement reads its tests. Verify reads the Acceptance, the tests, the evidence, and the `aidd test` command. Review reads the diff's stat, the Acceptance, the `aidd gate` command, and the linked threat models. A pack carries its head commit and the Spec hash, so a stale one shows.
- **Review results that hold.** `aidd prototype --check <file>` runs every rule on a Spec's design file: links, states, test ids, names, and the lint. It names each problem with its line, and holds a design to the rules of the format it names, so an upgrade never fails an approved design. `--screens` lists the screens and their states as JSON, so a test parses no HTML, and `--open` opens the written page in your browser. The feedback and round-changes files have schemas, and `aidd validate` warns on one they reject. `aidd extensions suggest --json` has its own schema too. In the viewer, a note pins to the exact element with a number, stays in the browser per design and round, and downloads as the round's file. Deep links also open the Board, System, safe areas, and feedback mode.
- **The product designer checks the finish.** Before a round and before done, its fidelity pass reads a screenshot of every state at three widths, in both themes, at 200% text and right to left. Done means no Fix point is open. The pass is sized to the change. A small UI fix gets a quick pass from its author. A new or reshaped screen, flow, or component gets the designer's full pass, a team's own tools included.
- **The designer knows where each item goes.** The prototyping skill's design review gains a "Where it goes" table, one rule a row with its standard. It covers width classes, the platform's home for navigation, phone reach, grouping, order, sticky bars, overlays, and target size. The screenshot loop checks placement beside axe, so text under a fixed or sticky box, a toolbar that wraps, or a next step off screen fails, with what to do.
- **The designer names things once.** The product designer now loads `naming`, whose design names keep a component's name from design to code. They name a token by its role, a screen by the person's task, and a test id in kebab-case that survives a redesign, and give each thing one UI label on every screen.
- **A browser for the designer and the verifier.** The optional `browser-review` toolset lets them use Playwright MCP wherever it is installed. The guard holds a role's browser to local pages and the hosts a project lists in `agents.browser_hosts`, and denies `browser_run_code_unsafe`. It notes instead of denying in advisory mode, and for the person's own session except under the audited profile or an autopilot lease. The toolset's install line starts the server with `--allowed-origins`, which narrows the requests the browser makes, and the designer serves the prototype on localhost. A shell check runs before the post-tool hook, so a call that is not a role's costs about 5 ms. Without it, the skill names the shell route: headless Chrome, and Playwright in a scratch folder.
- **Room to finish.** Every role's turn cap is at least 100, and 150 for the developer, architect, security engineer, reviewer, verifier, and product designer. In Claude Code, a new hook, `aidd hook post-tool`, counts each role's tool calls and tells it at 80% and 95% of its cap to wrap up. aidd also holds a role's stop once while its handoff note is missing. `AIDD_HOOK_TURN_CAP` lowers the cap for a test run, and `aidd eval hooks` now checks the count and the browser rule live. A role that still stops at its cap comes back partial, and the lead resumes it to finish its report.
- **A `context` practice skill.** Every role starts a step from its pack, reads by path, never re-reads what it has, and ends with the handoff note.
- **Two depth references.** `plain-language` gains UX copy state by state (empty, no results, loading, error, offline, permission denied, success, validation), with the voice taken from the design system and a weak-versus-strong example; the product designer now loads it. `maintainable-code` gains search before you write: where to look for an existing helper, what makes it reusable, and when to extend it instead.
- **Toolsets, picked by enabling.** A role's registry entry may name toolsets, each a bundle of its extensions. The product designer's `ai-design` is Open Design, or Claude Design, a hosted, paid service a person agrees to, with Impeccable, whose detector is a Spec test command. `aidd extensions suggest` lists them, each part with its pin and what it can touch. The designer uses what the project enabled, and with none, the prototype tool. Enabled, a new glossary term, means the repository's own committed settings turn a tool on: a machine-wide install never chooses a project's tools. No config key picks a role's tools.
- **The product designer sizes the work to the ask.** One screen or flow may be one prototype file and done. Directions come first only when the approach is open, and the product prototype is updated only where the project keeps one.
- **The design system, the designer's, changed in a Task.** `loop.documents` has a `design-system` row: the product designer owns `DESIGN.md` and `design/tokens.json`, and `aidd context` hands the developer, the verifier, and the reviewer `DESIGN.md` to build against; `aidd list --json` names it under `living`. Its new `changed_only_in_a_task` keeps the tokens the product ships out of the designer's living area, so only an approved Task's scope opens them. A person may assign that Task to the designer by name (`agent:product-designer`), which opens its scope to the designer alone, through the new `{scope:assigned}` write area. It reads the Tasks from the approved text and opens only on an approval recorded on this machine, so a Task the designer writes for itself, or a stored status, opens nothing. The denial names the step that does. A key starting with `_` in a Spec is the guard's own marker and is dropped.
- **A Spec that does not parse fails closed.** The guard read a branch Spec it could not parse as no Spec at all, so a malformed header lifted every Spec rule. Now it denies every write but that Spec, names the parse error and the line, and lets the lead or a role that writes Specs fix it. A plain page in the specs folder, such as a README or a Spec's notes, is no work item and blocks nothing. An edit that would break a Spec's header or change its `kind` is denied before it lands, and each denial says to ask the person when a value is ambiguous, never guess. The gate does the same: a work item in the diff that does not parse fails `spec.unparsable`, where it used to read the change as having no Spec and route it by its paths.
- **Design states and data.** The design spec writes an error state for each problem type the API returns (RFC 9457) and lists edge-case example data. The screenshot loop fails on sideways scroll, and the web pack prefers `transform` and `opacity` for motion.
- **A neutral start, a separate showcase.** A new design starts from a skeleton: one screen, plain chrome, and the project's own tokens when it keeps a design system, so no example biases it. The complete example is a showcase, `aidd prototype --example`, shown and never copied.
- **Stories checked against the design.** `aidd prototype --components` prints the component contract: each component, its variants, its screens, and its test ids. `aidd prototype --stories storybook-static/index.json` fails when a variant has no story under its name.
- **Components named once, built once.** The designer names each reusable part with `data-component` and `data-variant`. The System view shows each one with its variants and the screens that use it. The developer builds one component per name, with a Storybook story per variant and state. Storybook is the web pack's default `component-catalog`. Its MCP server (emerging) lets an agent read the components and run their tests.
- **Worked examples for judgment.** The reviewer's code-review skill and the security engineer's threat-model skill each carry contrast pairs: a weak finding or threat entry, a strong one, and the line between them. They use placeholders, never a domain, and load only when needed.
- **Security findings with a shape.** A security finding names who attacks, the input they control, the control it gets past, the boundary, the impact, and the proof, or it's a hardening note with no severity. Severity follows the impact shown. A finding that depends on a fact outside the repository is marked "needs validation", with its check. The security review searches sibling paths after a serious finding, and says what it covered. `REVIEW.md` says the same for every reviewer.
- **Verify and Review side by side.** Once a head is green, one step asks for both on that head and names them in `codes`. The run goes on when both are clean there. A failure in either returns to Implement once, and a new head needs both again.
- **Bounded.** A run holds a lease on its work, with a timebox, token and cost caps, a circuit breaker per step, and a stall breaker across the run. A Spec goes back to Implement or Specify at most three times in one run. A stop that sets work aside says what broke and where to read why, and a note's own words never reach that message.
- **For runs nobody watches.** `autopilot.notify` runs a command once each time a run stops for you. A crashed session's lease is taken over after 20 quiet minutes, and `claude -p` runs it headless. With `autopilot.parallel`, independent Specs run in parallel worktrees. [Autopilot](docs/AUTOPILOT.md#runs-nobody-watches) has the details.
- **In each agent's own words.** The flow tells `aidd autopilot next` which agent runs it, so each command comes as that agent runs it, such as `$aidd-implement` in Codex, with the file that holds it. You decide once: type the decision, and the run goes on once aidd records it.
- **A harness you can check.** `aidd doctor --autopilot` finds the guard in every agent aidd wired, checks Claude Code's sandbox, and prints every `permissions.allow` rule a run needs. In Codex, it names the `--add-dir` that lets the run write its lease in `.git`. It warns when a run would hold untrusted input, credentials, and open egress at once, the Rule of Two, or a long-lived GitHub token.
- **Tried for real.** Runs with real models in Claude Code, Codex, and OpenCode, from a one-line fix to a new goal, each stopped at a person's decision or at a problem it reported. [Real runs](docs/AUTOPILOT.md#real-runs) lists the problems they found, and each fix has a test.

### Security

- **No abbreviated options.** argparse read an abbreviated long option as the full one, so `aidd land --confirm HEAD` claimed a dialog answer the guard denies as `--confirmed`. No aidd command takes an abbreviated long option now, and the guard reads every prefix of `--confirmed` from `--co` on as the option itself.
- **Every ref under `refs/aidd/` is aidd's.** The guard denied a refspec into `refs/aidd/`, but `git update-ref` or `git symbolic-ref` could name one there plainly, such as the merge queue's ref. It denies that too now.
- **Updates you can trust.** `aidd self-update` installs only a release, never the tip of main unless you pass `--main`, and only once the wheel matches the release's SHA256SUMS and, with `gh` on PATH, its build provenance. The daily check says a release is out, and it installs by itself only with `AIDD_AUTO_UPDATE=1`.
- **The trust model.** The gate job runs from the default branch, reads the change as git objects only, and never runs its code. The test job is untrusted, so the platform token is stripped from its commands, and the evidence binds to the commit. [SECURITY.md](SECURITY.md) has the full model.
- **Pinned CI and provenance.** Every workflow pins each third-party action by commit SHA, and CodeQL, zizmor, actionlint, and OpenSSF Scorecard check the repository. The release workflow verifies the tag signature, CI, and `aidd/gate` before it builds, attests build provenance and a CycloneDX SBOM, and publishes the GitHub Release. That's where aidd comes from, because aidd is not on PyPI.
- **Releases you can rebuild.** The release builds every artifact again on a fresh runner, and stops unless each matches `SHA256SUMS`.
- **Agent risks mapped.** CONTROLS.md maps aidd to the OWASP Top 10 for Agentic Applications, CRA Annex I, NIS2, DORA (EU) 2022/2554, and the OSPS Baseline, and names what stays yours.
- **Scanning for adopters.** `aidd init --security-ci` adds OSV-Scanner, Semgrep Community Edition, gitleaks, and an SBOM, each on a read-only token.
- **No telemetry.** SECURITY.md lists every place aidd connects, and a test fails on a network module missing from that list. `AIDD_OFFLINE=1` stops the network checks.
- **The guard fails closed where it must.** It denies a command it can't read for a writer it holds. It blocks when it can't run only where the project asks, through the `audited` profile, `mode: enforce`, or an organization's `AIDD_HOOK_FAIL_CLOSED=1`, the same rule in every agent's hook. It never writes to the user's settings.
- **The decision records stay a person's.** The guard denies every way it knows that an agent's command could write `refs/aidd/decisions` or move the base branch under a name it can't read. They include a name the shell builds, a wildcard or brace refspec, refs fed on stdin, a refspec set through git config, a mirror remote, and a shell write into the git directory. A test runs each form in a real shell against a real repository.
- **Shell forms are read, never trusted.** The guard reads what `xargs`, `parallel`, `find`, `fd -x`, `busybox`, `script -c`, `watch`, and `flock` run, and the commands behind `if`, `{`, `!`, and loops. It denies, for every session, a program only the shell or a runner's input names, and fails closed where it can't read a word exactly. It reads a line as bash does: a line continuation, a comment, a substitution in backticks or double quotes, a here-string, `trap`, and `env -S`. It keeps each word's quoting, so a quoted find pattern, a quoted `gh pr review` text, and a loop over literal words read exactly, and text that only lands in the repository's files may name an approval. A line that runs `gh` or `glab` sets no variable, and changes no alias, extension, or config. [SECURITY.md](SECURITY.md#trust-model) lists what that denies, and the plain form that works.
- **Branches, refs, and git's own programs stay a person's.** The guard counts a branch name in another case, or one a glob or a brace spells, as the branch it may be. It denies `git replace`, `filter-branch` or `filter-repo` on a protected branch, and a git config key that names a program git runs, such as `core.hooksPath` or an alias. aidd reads every git object with replace refs off. Only git and aidd commands write in the git directory, wherever git keeps it, also outside the work tree, as `git init --separate-git-dir` and a bare repository's worktrees do.
- **Agents never pass for humans.** One rule decides whether an identity is an agent, and a lookalike name counts as one. The guard denies an agent's attempt to type a decision into another terminal, or to start another agent with one as its prompt, through `claude -p`, `npx`, `orca agent launch --prompt`, an Orca Task's `--spec`, `orca claude-teams`, `orca emulator exec`, `arch`, or a local agent server.
- **Every script a test command runs is frozen.** The Spec hash now covers a script at the top with a script's extension (`bash test.sh`), the program as a relative path (`scripts/run-tests`), and a pytest node id's file. A Spec whose commands name one hashes anew, so an approval recorded before needs a new one.
- **A recorded Spec approval binds only a known Spec commit.** An approval of the base commit warns with `spec_approval.names_base`, and one of a commit the repository doesn't have fails `spec_approval.voided` with that reason.
- **Each role held to its area in Antigravity too.** An Antigravity subagent's events name no parent, so the guard reads its role from the parent's message Antigravity writes into the subagent's conversation folder. In enforce mode, a subagent of another type is a helper and only reads, as in Claude Code.
- **Only the lead starts another role.** In enforce mode, in Claude Code, OpenCode, and Antigravity, a role starts its own type or a helper, and the guard denies the rest. So a verifier never starts a developer to fix the code it checks. Claude Code ignores a subagent's own `Agent(...)` type list, so the guard holds this line. A Claude Code main session started with `--agent` is the lead, as a live run showed.
- **Quoted words to an agent program are text.** The guard no longer denies `claude -p "..." --allowedTools "Bash(git status*)"`: a quoted glob passes to the agent as written. Text typed into a terminal keeps the strict check, since the shell there expands it. Starting Claude Code with `--settings`, `--setting-sources`, or `--bare`, or after the line moves its config folder (`CLAUDE_CONFIG_DIR`, `HOME`), is denied, however it is launched, since each may drop aidd's hooks.
- **A dropped config setting is a loosening.** Removing `mode`, `agents.helpers`, `agents.delegate`, or `hooks.level` from the config hands it to a parent or the profile, which may be looser, so a person decides it. So does a repair of a config aidd could not read that sets anything looser than its profile.
- **Approved test settings stay frozen in `pyproject.toml` and `package.json`.** A Spec freezes a manifest's test section by itself, such as `pyproject.toml#tool.pytest`, and `aidd new spec` adds the ones the top-level manifests hold. For `scripts.test`, that is pretest, test, and posttest when each runs one known test runner, or else every script. An edit of a frozen section after Spec approval voids it, and the guard denies one it can read; a dependency bump never does. A rebase, a squash, an amend, or a branch rename keeps a stale approval's freeze, because git's reflog of the branch still holds the approved commit. On a Spec's change, the gate warns when a test section changes that no Spec freezes. A runner config read before a manifest, such as `pytest.toml` or `.coveragerc`, counts as the test setup too. `aidd list` says which files changed since a Spec's last approval. When you approve a Spec again, every approval dialog and the terminal first name each test change since its last approval: the Spec's tests block, a frozen test file, or a frozen section. The diff covers the manifests too, and each dialog shows every warning, as the merge and land dialogs now do too. A change that voids a local approval opens no test: the frozen files stay frozen, as approved, until `aidd revise` records why. `aidd test` writes no evidence when the run changed the Spec, a frozen file, or the config.
- **Each role starts with its step's context.** In Claude Code, a role's subagent starts with its context pack: what `aidd context <ID> --role <role>` lists for the Spec its branch works on. Elsewhere a role runs that command itself. A Claude Code session is titled by its branch's Spec, such as "SPEC-12 · Hold large refunds", unless the person named it.
- **Each role thinks as hard as its tier asks.** In Claude Code, a reasoning role runs at `xhigh` effort and an execution role at `high`. `agents.effort` sets any level per tier or role.
- **The architect designs from measured goals.** The `aidd-team:system-design` practice skill takes a Design from quality scenarios with a measure, through a rough sizing and two or three options, one of which adds less that is new. It weighs the options in one trade-off table, then decides in an ADR, with a check for each boundary.
- **A data stack, and models you serve yourself.** The data pack gains three choices, each with a default: transformation (dbt Core, with SQLFluff), orchestrator (Apache Airflow, or Dagster), and ingestion (dlt, or Airbyte, whose platform is source-available). The AI pack gains model serving: a hosted provider by default, vLLM on your own GPUs behind the gateway, and Ollama on a developer's machine. Each model is pinned by revision, and its evals run again on any change. A `python-data` stack starts a data project with them.
- **Helpers, by one name and one setting.** A helper is a subagent that is not an aidd-team role. In enforce mode it only reads, unless the config says `agents.helpers: write`, which a child config cannot loosen. In advisory mode, the solo and team default, every subagent writes and runs what the main session may, so nobody sets anything.
- **An approver list that can never approve is named at init.** With no platform, a local approval counts as your git email, so `aidd init` and `aidd doctor` name a list of `@logins` alone, with the command that fixes it.
- **What agents keep getting denied here.** At session start, the note names the guard's most repeated denials in this repository over the last week, each with the step that works instead.
- **Live hook checks.** `aidd eval hooks --harness <name> --agent-command "<cmd>"` runs one real session of a harness in a scratch repository, judges what aidd's dialect reads from each hook event, and pins the masked events in a test. For Antigravity, it pins each conversation's messages too, since the guard reads a subagent's role from them. `AIDD_HOOK_CAPTURE=<file>` copies each raw event a hook gets.
- **The always-on rules hold when the config breaks.** A config an agent made invalid counts as a loosening, and one a person broke never switches them off. A folder, a glob, or a pathspec that holds the config or the guard's wiring is held as the file is, as with `rm -r .aidd`.

### Known limits

[RATIONALE.md](docs/RATIONALE.md#known-limits-in-100) lists every limit. These matter most in 1.0.0:

- An install from before 1.0.0 starts fresh. Delete any `aidd hook pre-edit` entry from your agent's settings, then run `aidd init`. Your next decision records a new watched state.
- Autopilot's real runs were in Claude Code, Codex, OpenCode, and Antigravity, each on one small repository. In OpenCode, a headless `opencode run` doesn't load the command, so attach it with `-f`. In Antigravity, the guard read each role of the run from the parent's message. Grok Build runs it as `/aidd-autopilot`, not yet tried with real models. Another agent runs its steps by hand with `aidd autopilot next`.
- Autopilot trusts the local machine. A local writer of git refs or `.git/config` is out of its scope, and the gate in CI is the control.
- A typed decision trusts the prompt, since a program that starts an agent by itself could type one. The platform review, or signed approvals, is the proof.
- The guard reaches only the writes it can read. For a role or the main session, a program that writes by itself is out of its reach, such as an interpreter or a build tool. The gate on the real diff is the control.
- The role evals weren't run again with real models after the agent files changed, and aidd publishes no eval baselines.
- The gate hasn't yet judged a live pull request on GitHub or GitLab.
- Signing and publishing wait for a public repository.
