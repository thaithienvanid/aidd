# Changelog

This file lists every notable change to aidd.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The method, the schemas, the gate, the CI templates, the skill, and the team plugin share one version. Every record carries `aidd_version`. [CONTRIBUTING.md](CONTRIBUTING.md#versioning) says what counts as a patch, a minor, or a major change.

## [1.0.0] - Unreleased

AIDD (AI-Driven Development) is a method for delivering software with AI agents: agents do the work, and people decide what to build and what ships. aidd is the open-source toolkit that runs it: a command-line tool with no runtime dependencies, a CI check named `aidd/gate`, and a skill that coding agents read. This is the first release, so everything below is new.

### Added

- **The method.** Every change runs one loop: Plan, Specify, Spec approval, Implement and Verify until green, Review, Merge approval, Ship, and Learn ([docs/METHOD.md](docs/METHOD.md)). A person makes two decisions. Spec approval binds a hash of the Spec, its tests, and its design, and Merge approval binds the head commit. aidd sizes each change by what it touches. That size is its route: `standard`, `minor`, `normal`, `major`, or `emergency`. The author can ask for more control, never less, and the gate computes the route again from the real diff. Four profiles, `solo`, `team`, `org`, and `regulated`, set how strict the gate is. The Spec is the work item and the contract: intent, acceptance, scope, tests, risk, rollback, and an observe window. Maintain is the same loop on a rhythm: `aidd list --upkeep` lists the upkeep that is due, and each item a person picks enters the loop as its own change.
- **The gate and red-then-green evidence.** `aidd gate` decides pass, pending, or fail from the facts of a change, and the platform status is `aidd/gate`. New behaviour must fail on the base commit and pass on the head commit, in your own CI. The gate also checks that the change stayed inside the approved scope and that the right people approved it. Separation of duties holds for every author, co-author, and committer, and an agent never approves. The gate reads its config, the Policy, and CODEOWNERS from the base branch, and it fails closed. Each run writes a record, and `aidd record verify` checks the in-toto change record of a decision.
- **Local-first work.** aidd needs only git, so a person can approve and ship on their own machine. `aidd approve spec` and `aidd approve merge` record a listed Approver's decision from their own git identity, after a one-time code. `aidd ship` merges a passing branch and lands exactly the tree it tested. `aidd approve` and `aidd ship` refuse in any shell that an agent started. `aidd init --dry-run` reads the repository first: its stacks, test commands, sensitive areas, owners, and CI. `aidd init` then writes the config, the skill, and the CI files, with the gate in advisory mode. `aidd doctor` checks the wiring, `aidd upgrade` keeps it current, and `aidd uninstall` reverses `aidd init`.
- **Platforms.** On GitHub, aidd ships a reusable gate workflow, a composite test action, and a GitHub App as the status source. The gate judges each merge-queue entry on its merge-group commit. GitLab support is experimental: the gate runs on merged-results pipelines, and merge trains are not supported. Any other CI builds a context file and runs `aidd gate --context`. The gate blocks a merge only in enforce mode, as a check the platform requires.
- **Coding agents.** The `aidd` skill is a self-contained Agent Skills folder that any coding agent can read. aidd supports <!-- aidd:gen count:harnesses -->26<!-- aidd:end --> coding agents, such as Claude Code, Codex, Cursor, and Copilot, and `aidd init` wires the ones it finds. The guard allows or denies, and never prompts. It denies an edit outside the active Spec's scope, an edit to a frozen test, and an agent's command that approves, merges, or ships. It holds deploy commands until a person allows them. The session hooks brief the agent, remind it when code changed without passing evidence, and save the state of the work before a compaction. `aidd mcp` serves the same checks as MCP tools. `[agents] delegate` tells the main session which team role owns a file, and can deny its edit so that the role makes it.
- **The delivery team.** The optional `aidd-team` plugin adds <!-- aidd:gen count:roles -->16<!-- aidd:end --> agent roles that people lead, from product manager to SRE. Each role writes only its own files, hands off through a file and a short note, and never approves or merges. The tester who writes the tests never builds the code, and the verifier wrote neither. The roles that decide, design, or judge run on the `reasoning` tier, and the others on `execution`. The plugin has <!-- aidd:gen count:commands -->19<!-- aidd:end --> commands, from `/aidd-team:plan` to `/aidd-team:maintain`, which routes the upkeep that is due. The `delivery-manager` role qualifies client work, keeps the RAID log, and writes the contract with `aidd new contract`. Where it is not installed, the product manager does its work (`fallback`). `/aidd-team:handover` hands a delivered system over to the client for sign-off.
- **Autopilot and `aidd context` (experimental).** `aidd autopilot next` computes the one next action from git: run a team command, ask a person, or stop. `/aidd-team:autopilot` runs those actions between a person's decisions, and stops whenever a person must decide. A run holds a lease on its work, with a timebox, optional token and cost caps, and a circuit breaker. `aidd context` lists what a step reads, by path, with a token estimate each. Both are experimental, so their names can change in a minor release.
- **Knowledge.** The roles read <!-- aidd:gen count:packs -->19<!-- aidd:end --> domain packs and <!-- aidd:gen count:practices -->29<!-- aidd:end --> practice skills, such as `naming` and `modular-monolith`. Each one cites dated standards, and each standard records its edition, its source, a sentence quoted from that source, and a `checked` date. `aidd eval standards` fails on an entry past its review. The `enterprise-controls` pack holds controls that each name the test or record that proves them, mapped to SOC 2, ISO/IEC 27001:2022, and GDPR. **Product defaults** (`[project.defaults]`) give every product light and dark themes, responsive layouts, security headers, and more. A new project starts as a modular monolith in a monorepo. A person turns a default off only with a reason. The plain-language skill sets the writing level by reader: ste-80 (the ASD-STE100 writing rules) inside the team, plain language (ISO 24495-1) for clients and users. aidd writes its own docs, skills, and messages at ste-80.
- **The standards library and stacks.** A library standard fills one open choice of a pack or a practice skill, such as the linter or the workspace tool. A choice can have several options in one ecosystem, and exactly one of them is aidd's default. A stack is a set of standards that go together. `aidd standard add` and `aidd stack add` copy them into a project, with their tests. Each standard shows its trust tier: checked by an agent, or reviewed by a person.
- **Design and proposals.** `aidd new design-spec <topic> --spec <ID> --prototype` writes a design spec and a one-file HTML prototype of every screen in a flow. `/aidd-team:explore` drafts two or three directions, and `aidd explore` renders one page that compares them, round by round. A person picks the direction. A proposal holds work that someone outside the team must agree to first. Its sign-off binds the exact text by hash, and `aidd proposal convert` turns an accepted proposal into an Initiative and Epics.
- **Spec quality.** `aidd validate` warns when an Acceptance line or a non-functional requirement uses a vague word, such as "fast" or "robust", and states no target. A person can name the project's best Specs as exemplars (`[docs] exemplars`), and whoever writes a Spec reads them first. `aidd validate` also warns when no test command covers an Acceptance item.
- **Proof.** The conformance suite holds <!-- aidd:gen count:examples -->22<!-- aidd:end --> gate examples and <!-- aidd:gen count:mutations -->198<!-- aidd:end --> data mutations, each pinned by a finding code. `aidd eval examples` replays them, so another implementation of the gate can show that it matches. `aidd eval routing` and `aidd eval roles` score an agent on <!-- aidd:gen count:routing-scenarios -->59<!-- aidd:end --> routing scenarios and <!-- aidd:gen count:role-scenarios -->17<!-- aidd:end --> role scenarios. Each eval record names the commit and a hash of the material it measured. The JSON Schemas are the source of truth, and `aidd gen-docs --check` fails when a generated table or count drifts.

### Security

- **The trust model.** The gate job is trusted: it runs from the default branch, reads the change as git objects only, and never runs its code. The test job is untrusted. The platform token is stripped from every test command, and the evidence binds to the commit. [SECURITY.md](SECURITY.md) has the full model and how to report a vulnerability.
- **Pinned CI.** Every workflow and template pins each third-party action by commit SHA. CodeQL, zizmor, actionlint, and OpenSSF Scorecard check the repository.
- **Provenance and SBOM.** The release workflow verifies the tag signature, CI, and `aidd/gate` before it builds. It attests build provenance and a CycloneDX SBOM for the packages and `aidd.pyz`. It publishes to PyPI through trusted publishing.
- **Security scanning for adopters.** `aidd init --security-ci` writes a workflow that runs OSV-Scanner, Semgrep Community Edition, gitleaks, and a CycloneDX SBOM, each on a read-only token. The secret scan reads its config from the base branch, so a pull request cannot turn off its own scan.
- **Network use.** aidd sends no telemetry, and SECURITY.md lists every place it connects. A test fails when a module that uses the network is not on that list. `AIDD_OFFLINE=1` stops the network checks of `aidd init`, `aidd upgrade`, and `aidd doctor`.
- **The guard denies what it cannot read.** For a writer it holds, such as a role or the lead under `delegate`, the guard denies a command that runs code it cannot read. Examples are a command substitution where a command starts, a shell fed by a pipe, and `xargs` or `find -exec`. It follows `sh -c` and `eval`, and it reads each path as the kernel does. Any error while it checks a command denies the command.

### Known limits

[docs/RATIONALE.md](docs/RATIONALE.md#known-limits-in-100) lists every limit. These matter most in 1.0.0:

- Autopilot is experimental, and it has never run with a real model. Its fixture tests use scripted notes in place of agents.
- Autopilot trusts the local machine. A local writer of git refs or `.git/config` is out of its scope, and the gate in CI is the control.
- The guard reaches only the writes it can read. A program that writes by itself, such as an interpreter, a build tool, or a package manager, is out of its reach. So is a command that its parser reads differently from bash. The gate, on the real diff, is the control.
- The role evals were not run again with real models after the agent files changed. aidd publishes no eval baselines, and each eval run needs an API key.
- The gate has not yet judged a live pull request on GitHub or GitLab. This repository starts to use its own gate with that first run. The work in 1.0.0 was made before it, so that work has no Specs.
- Signing and publishing wait for a public repository. Until then, the release workflow signs, attests, and publishes nothing.
