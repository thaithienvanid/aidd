# Changelog

This file lists every notable change to aidd.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The method, the schemas, the risk rules, the CI templates, the skill, and the team plugin share one version. Every config carries `aidd_version`. [CONTRIBUTING.md](CONTRIBUTING.md#versioning) says what counts as a patch, a minor, or a major change. An upgrade within a major version never turns an approved Spec's frozen test red ([the promise](CONTRIBUTING.md#frozen-tests)).

## [1.0.0] - Unreleased

AIDD, short for AI-Driven Development, is a method for delivering software with AI agents. Agents do the work and follow one loop, and you decide the risky steps. aidd is the open-source toolkit that runs it. It's a command-line tool with no runtime dependencies, a skill that coding agents read, an optional delivery team of agent roles, and a standards library. aidd advises and enforces nothing. This is the first release, so everything below is new.

### Added

#### The method and the loop

- **[One loop](docs/METHOD.md) for every change.** It runs Plan, Specify, Spec approval, Implement and Verify until green, Review, Merge approval, Merge, Roll out, and Learn. The team runs the work, and you decide at each ask. Retries are capped at 3 a Task, a flaky test is a finding, and red before green is the practice for new behavior.
- **Routes as advice.** `aidd risk --paths` sizes a change by what it touches, as `minor`, `normal`, `major`, or `emergency`. The route sets the lane: the fast lane with no Spec, the spec lane, or the emergency lane, which repairs production first and writes the Spec after. An area can raise the route, so an edit in `payments` makes the change major. The author may declare higher.
- **Profiles.** `solo` asks for Spec approval on major changes, and asks before anything reaches the default branch. `team` asks for Spec approval on normal and major changes, and leaves Merge approval to the platform's review: the agent opens the PR and stops there.
- **Spec approval, asked plainly.** The agent asks "Approve SPEC-3?" with what the Spec covers. On your yes, it sets the Spec's `status: approved`, `approved_by`, and `approved_at`, and commits it with an `Approved-by` trailer. After that, editing the Spec's tests or Acceptance is `spec.revise`, which asks you again, puts the Spec back to `draft`, and adds a `revisions` entry.
- **The Spec** is the work item and the contract, `type: spec` in its front matter. It holds the intent, its `change_type` (a Conventional Commits type), the Acceptance, the scope, the tests, the risk, the rollback, an observe window, and a cost estimate that `aidd validate` checks against the project's budget. Its status runs from `draft` to `ready`, `approved`, `in_progress`, `in_review`, and `done`, or ends at `rolled_back` or `cancelled`.
- **Interfaces between Specs.** A Spec lists the interfaces it `provides` and `consumes`, by name: an API, an event, or a schema. When a Spec that provides one is revised, `aidd status` names the open Specs that consume it, so their owners hear first. `aidd validate` warns about a consumed interface that no Spec provides.
- **Deprecations.** A Spec's `deprecations` names what it deprecates and its sunset. A passed sunset warns until a Spec that removes it lands.
- **Requirements a machine can check.** A business rule with three or more conditions becomes a decision table, with one Acceptance id per row. `aidd validate` warns about a word the glossary says to avoid.
- **Open questions and unplanned work.** While a Spec asks for approval, `aidd validate` names each open question it still lists. Once the Spec is approved, and its branch changes no other Spec, it names each file the change alters that no Task's scope, test, design file, or linked doc names.
- **Plain prose.** `aidd validate` warns on a Spec's phrase that reads as machine-written, such as "I hope this helps" or "moreover", outside code and quotes; `schemas/ai-tells.json` holds the list, and aidd's own pages keep to it.
- **A check kept whole.** `aidd test --changed` notes each move that weakens a check since the base: a new skip marker, a new suppression comment, a deleted test file, or a lowered coverage floor. `schemas/weakening-moves.json` holds the patterns. A note, never a failure.
- **Runbook readiness.** `aidd validate` warns about a linked runbook's unchecked launch-readiness boxes while its Spec is in review.
- **Big goals and small goals.** A big goal is an Initiative of small goals, which are Epics of two weeks or less, each with its Specs.
- **Headless runs stop at an ask.** In CI or a scheduled run, an `ask` means stop and hand back with a handoff note, because silence is never a yes.
- **The loop fits the work to its reason.** A major change gets a tech spec, a threat model when it touches security, privacy, or data, and a rollout plan. A minor change gets none of them.
- **A cold reader on the major route.** Before Spec approval, the tech writer reads the Spec with no chat history and lists the terms and steps it assumes, so a gap goes back to the architect.
- **A kill criterion for a risky assumption.** The product-discovery skill gives each one a result and a date that end or reshape the work.
- **Fewer assertions, noted.** `aidd test --changed` also notes a test file that has fewer assertions on net since the base.

#### Risk rules

- **Actions, areas, and levels.** An agent acts by a risk rule's level: `allow` acts, `report` acts and then says what it did, and `ask` waits for your yes. Each action is `resource.verb`, such as `pr.open`, `git.push.force`, or `deploy.run`, with its command patterns and examples that no pattern catches. An area is a named set of path globs, such as `auth`, `payments`, or `personal_data`.
- **Modelled on authorization.** The rules borrow the shape and names of Cedar, Google Cloud IAM, and Kubernetes RBAC, with no engine of their own. A rule names an action, and optionally an area, a branch (`own`, `default`, or `shared`), and a role. The most specific rule that matches wins, then the higher level.
- **Built-in rules you can read.** `schemas/risks.json` holds the built-in actions, the areas, and the rules between them. Editing code is `allow`, and `ask` in `auth`, `payments`, `personal_data`, `secrets`, `migrations`, and `risk_rules`. Pushing your own branch is `allow`, and pushing to the default or a shared branch is `ask`. Force pushes, history rewrites, branch deletions, tags, merges, deploys, releases, production data, secrets, messages, and spending money all ask. A migration asks when it runs on a database other people use or with the tool's production flag, such as `prisma migrate deploy`, and when it undoes applied migrations, such as `alembic downgrade`. Dropping or wiping a database, such as `php artisan migrate:fresh`, is `data.delete`. A plain forward `migrate` on the agent's own database reports, as `migration.run.local`. aidd reads a tool's command without its runner, such as `npx`, `bundle exec`, or `uv run`, and writes each harness's ask rules in every runner form. A setting typed before the command, such as `RAILS_ENV=production`, counts, and a migrate that names a target, such as `rails db:migrate VERSION=0`, is a rollback. `git clean -f`, `git stash drop`, `git restore .`, `git push --tags`, `gh repo delete`, `docker push`, and `kubectl delete` ask. A local `git rebase` or `git commit --amend` does not, because the force push that publishes it asks. Every `git tag` asks, and so does every way of pushing a tag: by name, under another name, with `--tags` or `--follow-tags` (abbreviated too), or through `push.followTags`.
- **A yes holds only for what it showed.** When the head, the branch, or the command a question named changes before the agent acts, such as after a rebase, it asks again.
- **Tools that run agents side by side.** Orca's `orca.yaml` and worktrunk's `.config/wt.toml` sit in the `agent_config` area, because they run commands in every worktree.
- **Your own rules.** The config's `risks` adds areas, actions, and rules. A rule with a built-in's selector replaces it, so a project can lower a level as well as raise it. An `extends` preset can lock a rule, and `aidd risk` then reports a project's change to it as ignored.
- **One answer for every question.** `aidd risk --paths` gives the route, the lane, the areas hit, and the first step. `aidd risk --command "<cmd>"` gives the actions a command matches and the winning level, `aidd risk --action` gives one action's level, and `aidd risk --list` shows every effective rule. Each answer names where the deciding rule came from: built-in, the profile, the repository's config, or the preset it extends, by path or URL. `workflow.run` reports a CI workflow run by hand, and one that releases, publishes, or deploys asks.
- **Session overrides.** You may lower a rule for one session, such as "don't ask about pushes today". It lasts the session, and goes into the config only when you say so.
- **Environments.** The config's `environments` names each environment by its branches and tags. A push to one is `deploy.run` to that environment, so the question names it, and a rule's `environment` selector changes one environment's level. A push never asks less by accident.
- **A network listener reports.** `network.listen`, such as `aidd prototype --serve --lan`, is a `report` action, so an agent that follows the skill says when any device on the network can reach what it serves.
- **Commit statuses and check runs ask.** `commit_status.post` asks before `gh api` writes a commit status, a check run, or a GraphQL mutation. The ruleset's pin to GitHub Actions stays the control.

#### Every coding agent

- **Any coding agent.** The `aidd` skill is a self-contained Agent Skills folder. aidd supports <!-- aidd:gen count:harnesses -->26<!-- aidd:end --> coding agents, such as Claude Code, Codex, Cursor, and Copilot, and `aidd init` wires the ones it finds.
- **The harness's own ask rules.** `aidd init` and `aidd upgrade` write each `ask` rule's commands as the harness's own ask rules, in the format its documentation gives. Nine harnesses get them: Claude Code, OpenCode, Codex, Grok Build, Qwen Code, Devin's CLI, Factory Droid, Augment's CLI, and VS Code's agent. A test checks that all nine ask for the same commands. aidd changes only the entries it listed in `.aidd/harness-rules.json`, never yours, and never puts an ask where it would undo your deny. A harness without ask rules gets the skill alone, and `aidd doctor` says so.
- **What holds each ask.** A generated table in the guide gives each built-in `ask` action and what holds it besides the skill: the commands a harness's own ask rules ask before, and what branch protection refuses.
- **A branch ruleset.** On GitHub, `aidd init` writes `.github/rulesets/main.json` for the default branch, for you to import. It is the hard stop for merges and force pushes.
- **The team's flows in every harness that reads skills.** With `--team`, every agent that loads skills from `.agents/skills/` gets the flows there, and each role's file in `.agents/roles/` for its lead to hand a subagent.
- **The `aidd-cli` plugin.** It puts the `aidd` command on the PATH of Claude Code's Bash tool, so nothing else needs installing. Codex, OpenCode, Google Antigravity, and Grok Build document no plugin that puts a command on the agent's PATH, so no package ships for them, and there the agent runs the `aidd` you installed. A test keeps any future package a link to `scripts/aidd`, never a copy.
- **The agent that runs the session.** `aidd doctor` names it, from the variable it sets in its own shell. It says plainly when the repository does not wire it, with the `aidd init --harness` line that does. An empty `.claude/`, or one that holds only Claude Code's own `worktrees/`, is no sign of its wiring.
- **Records.** After the agent acts on an answered ask, or takes a `report` action, it records it: one immutable file in `.git/aidd/records/`, outside the working tree, so no commit carries it. A `decision` keeps the question and the person's reply word for word, and a `report` keeps what the agent did and said. `aidd records` lists the history, `aidd records add` writes a record, and `schemas/records.json` holds the types. `aidd records pull` and `push` share them through a remote's `refs/aidd/records`, merged by union, and pushing is `records.push`, an `ask`. A record is history, never a yes and never evidence. `aidd status <ID>` shows a work item's history: its decisions and reports, the commits that name it, and its linked documents, newest first. `aidd init` lets aidd's own four MCP tools run with no prompt in Codex and Claude Code, so a run with nobody watching records too.
- **The open work in every branch.** `aidd status --all-branches` shows the open work in every worktree and in every local and fetched branch, each item with the places that hold it. Two places that hold different versions of one Spec show both. It reads through an index, `.git/aidd/index.sqlite`, which reads a place again only when it changed; the index is only a cache, so a broken one is rebuilt.
- **Fewer asks, from the history.** `aidd risk --suggest` names each `ask` rule a person said yes to every time, at least 10 times, as a rule to consider lowering to `report`. It never names an action a person cannot undo, which `irreversible: true` marks in `schemas/risks.json`, such as a force-push, a deploy, or a message sent, even through a wildcard rule. Nor does it name a person's own decision points: Spec approval and revision, Merge approval, a push to the default branch, and an edit to the risk rules. It counts only the records this clone wrote, never pulled ones, and it only suggests: the person changes a rule.
- **MCP.** `aidd mcp` serves five tools: `risk`, `status`, `validate`, and `recall` only read, and `record` writes one record, marked `written_with: mcp`. `aidd init` approves them in Claude Code and Codex, and `mcp: {approve_own_tools: false}` keeps them asking. aidd then takes out only the approvals it wrote, never one you added. It does the same for the server's tool names once the aidd plugin serves the tools and `.mcp.json` names no `aidd` server.
- **Recall.** `aidd recall <words>` searches what the team already wrote: the records, the Specs and their documents, the ADRs, the glossary, and recent commit subjects. It uses SQLite's full-text search in the index and calls no model.
- **Claude Code Review reads `REVIEW.md` well.** The file says what Important means here, caps nits, lists what not to report, and with `--team` includes the code-review skill. The skill's Merge step reads Code Review's Important findings as a review report, and Code Review never approves.

#### Commands

- **18 commands, in three groups.** Setup is `init`, `upgrade`, `self-update`, `uninstall`, `doctor`, and `standard`. Work is `status`, `risk`, `trace`, `new`, `test`, `validate`, `explore`, `prototype`, and `help`. Maintainers and harnesses have `eval`, `mcp`, and `gen-docs`.
- **Short help first.** `aidd --help` lists only the everyday commands: `status`, `risk`, `new`, and `test`. `aidd help --all` lists every command by group, and `aidd help <command>` shows one in full.
- **Ask your agent first.** The README and the guide lead each step with the words for your agent. One sentence installs aidd through `llms-install.md`, which ends by naming the two steps only you take: restart your agent, and protect your main branch. The terminal commands stay as a fallback.
- **Setup.** `aidd init --dry-run` reads the repository first. `aidd init` writes the config, the block in `AGENTS.md`, the skill, the harness ask rules, and, with `--team` and `--ci`, the team and the CI test workflow. Run again, it adds only what's new, such as another agent with `--harness`. `aidd doctor` checks the wiring, `aidd upgrade` keeps the files current, and `aidd uninstall` reverses them.
- **From GitHub only.** aidd is not on PyPI, so a package named `aidd` there is not this one. `install.sh` installs a release's wheel from its GitHub Release. It installs once the wheel matches the release's `SHA256SUMS` and, with `gh` on PATH, once its build provenance verifies. `AIDD_RELEASE_URL` points it at a mirror of the releases, which also needs `AIDD_SHA256` or `gh`, because a mirror's `SHA256SUMS` proves nothing alone.
- **Python 3.11 to 3.15**, with the standard library only. Each release also carries the whole CLI as one file, `aidd.pyz`, for a machine where you can't install packages.
- **`aidd status`** lists the open work: each Spec and work item, its status, and its next step, with `--mine` and `--json`. docs/CLI.md gives four `jq` recipes for `aidd status --json`: what waits on you, what is blocked, what is past due, and one Spec's next step. A test runs each one.
- **`aidd trace`** shows what stands behind a path or a work item: its Specs, Epics, and Initiative, the work in flight there, its tests, docs, and interfaces, its route, and its last commits. It derives all of it from git and aidd's files, and stores nothing.
- **`aidd test`** runs the project's tests, green on the head and red on the base for new behavior, and writes the evidence: each exit code bound to the head commit. It marks evidence from a dirty tree. `--changed` runs only what changed, and `--watch` runs again on each save.
- **`aidd new`** writes a Spec, an Epic, an Initiative, a Proposal, an exploration, or a linked doc, from an ADR to a runbook.
- **`aidd standard`** lists the open choices, the library's standards, and the stacks, and `aidd standard add` copies one into a project.
- **Exit codes you can script.** 0 is ok, 1 is a check that failed (`test`, `validate`, `doctor`), and 2 is an error. Every stop names its next step, and a crash says it's a bug in aidd, with `AIDD_DEBUG=1` to print the traceback.

#### The delivery team

- **Agent roles led by humans.** The optional `aidd-team` plugin adds <!-- aidd:gen count:roles -->13<!-- aidd:end --> roles, from product manager to SRE, and <!-- aidd:gen count:commands -->19<!-- aidd:end --> commands, from `/aidd-team:plan` to `/aidd-team:maintain`. `/aidd-team:autopilot` runs the loop and stops at each ask.
- **The team in the README.** Why roles, a generated table of the roles with each one's model tier, a flow from `/aidd-team:specify` to Spec approval, and how to get the team in each agent.
- **One developer for every code Task.** The developer builds AI features and data work too, and the Task's `skills` load the specialty: `ai-evals`, `ai-features`, `schema-migration`, or a data pack.
- **Role placement.** The lead of each team command places each role: it plays the role for a small step of its own work, or starts it when it checks the work, runs cheaper, or works in parallel.
- **Each role thinks as hard as its tier asks.** In Claude Code, a reasoning role runs at `xhigh` effort and an execution role at `high`. `agents.effort` sets any level per tier or role.
- **Verify and Review side by side.** Once a head is green, the verifier and the reviewer check that head. A failure in either returns to Implement, and a new head needs both again.
- **Independent review and parallel Tasks.** `agents.independent_review` opts in to a verifier and a reviewer on another provider than the developer's. The team skill gives parallel Tasks a base, a setup step, a copy list, and cleanup as its own step.
- **Perspectives before a plan.** A consult round asks the architect, the designer, the security engineer, and the `domain-expert` for a card each. The domain expert speaks for its domain pack and edits no file.
- **Security guidance and findings with a shape.** `aidd init --team` writes `.claude/claude-security-guidance.md` for Claude Code's security-guidance plugin, which the developer and the security engineer recommend. A security finding names who attacks, the input they control, the control it gets past, the boundary, the impact, and the proof, or it's a hardening note with no severity. Severity follows the impact shown.
- **Worked examples for judgment.** The reviewer's code-review skill and the security engineer's threat-model skill each carry contrast pairs: a weak finding or threat entry, a strong one, and the line between them.
- **A `context` practice skill.** Every role reads by path, never re-reads what it has, and ends with the handoff note.
- **Living product documents.** `aidd new` writes a product brief, a metrics dictionary, a control register, an improvement log, and a service card for each service. Each Spec's document of that kind folds into its file. `aidd new srs` generates a requirements specification in ISO/IEC/IEEE 29148's outline. `aidd validate` indexes the threat models and warns about a threat id with no model.
- **Each role keeps its product-level work.** The team registry says which of a change's documents feeds which product-level work, such as the architecture overview or the product prototype. When a change feeds one and leaves it as it was, `aidd validate` warns, so the same change brings it in line.
- **Client work.** The `delivery-manager` role qualifies client work, keeps the RAID log, and writes the contract. Where it isn't installed, the product manager does its work as the `fallback`. `/aidd-team:handover` hands a delivered system over for sign-off.
- **Autopilot in Orca workers.** Where Orca is installed, `/aidd-team:autopilot` may run a step in an Orca worker in its own worktree. It reads each result from git, merges Task branches one at a time, and stops at `agents.max_tokens_per_run`, 10,000,000 tokens by default.
- **Delivery teams.** The config's `delivery_teams` names each team sharing a repository, with its areas or Epics, and `aidd status --delivery-team <name>` shows one team's work.
- **A second reviewer from another model family.** On the major route, or a change to the risk rules, the ask rules, or the release workflow, the review flow offers a read-only Codex reviewer. It asks you once first, because it spends that harness's quota.

#### Design and prototypes

- **The whole product, clickable.** `aidd new product-prototype` starts the designer's living prototype in `docs/design/app/`. `sitemap.json` defines the navigation once, so every screen shows the same items in the same order. `aidd prototype` assembles it into one page and checks it.
- **One prototype viewer, like a design tool.** A Spec's prototype and the whole product open in the same workspace. It has device frames for the web, iOS, and Android, a review column that opens the next unseen state, and a Board that shows every screen in every state. The Board is `view=board`. A comment pins to an element, as in a design tool: `comments=1` opens them, and each round keeps its own in `rounds/<N>/comments.json`. Each direction of an exploration keeps one file in the exploration's round, `comments-<direction>.json`.
- **A state counts as seen once shown everywhere.** The viewer marks a state seen after it has shown it on each platform group and theme the design styles. The review column ends with the one step left.
- **The prototype tool, aidd-team's own.** The viewer, the checks, and the component contract live in `plugins/aidd-team/tools/prototype/`, one standard-library file that runs without aidd. `aidd prototype --check <file>` names each problem with its line, and holds a design to the rules of the format it names.
- **Components named once, built once.** The designer names each reusable part with `data-component` and `data-variant`. `aidd prototype --components` prints the component contract, and `aidd prototype --stories storybook-static/index.json` fails when a variant has no story under its name.
- **The product designer checks the finish.** Its fidelity pass reads a screenshot of every state at three widths, in both themes, at 200% text and right to left. The pass is sized to the change.
- **Explorations.** `/aidd-team:explore` drafts two or three directions, and `aidd explore` renders one page that compares them.
- **Links that fail say so.** A link to a screen, state, frame, or theme the design lacks opens the nearest one with a banner, and that fallback never counts as seen.
- **One layout at each window width.** The viewer keeps its controls in one place from a phone-width window to a wide screen.
- **Images in a design.** `data-image` shows a fixture's image, a `data:` URI or a file beside the design, which the tool inlines. A path that leaves the design's folder is a problem `check` names.
- **A phone review.** `aidd prototype --serve` serves the design on 127.0.0.1 until you stop it, or on your network with `--lan`, and rebuilds the page on each reload.
- **A desktop window scan.** The desktop-apps pack says how to scan a running Electron or WebView2 build with Impeccable's `detect --cdp`.

A new `agent-to-agent` choice holds the official A2A SDKs for Python and TypeScript. None replaces a default, and an agent checks each again every 90 days.
- **Standards checked by agents.** Every registry entry, library standard, and stack carries one date, `checked`, with `checked_by`, the agent that checked it.

#### Files and proof

- **Files you can read.** Every file aidd reads is Markdown with YAML front matter, or YAML, read by its own strict parser. aidd's output for a worktree sits in `.aidd/evidence/` and `.aidd/views/`, which git ignores. `aidd validate --json` and `aidd doctor --json` give the same answers to a program.
- **One word for a type.** Every format says `type`, never `kind`: a work item's front matter, a Spec's `docs` entries and `emergency` block, a proposal's estimate parts, the prototype's comments, the Orca payload, and `aidd new <type>`.
- **A test report.** A test command may name a JUnit XML `report`. `aidd test` records the failed test cases beside the exit code, which stays the evidence. A missing, stale, or unreadable report is a finding.
- **Agent evals.** `aidd eval routing` and `aidd eval roles` score an agent on routing scenarios and role scenarios, run by hand with the agent you name. `aidd eval transcript` reads a recorded Claude Code run as the files it opened, its tool calls, and its cost, with no model. The plugin evals add cases for `code.edit` in `payments`, `spec.revise`, and an edit inside a Task's scope.
- **Pinned tool versions, checked.** `aidd eval standards` lists the exact tool versions that packs and practice skills pin in their commands, and `--online` flags a newer major release of each.
- **Docs that stay current.** The JSON Schemas and `schemas/risks.json` are the source, and `aidd gen-docs --check` fails on a stale table or count. A test fails on a concept with no glossary row.
- **A glossary row for every name.** A test reads each route, lane, level, status, change type, record type, document type, and role from its schema, and fails on one with no glossary row.
- **`aidd status --html`.** It writes the open work as one read-only page in `.aidd/views/`: what needs you, what your agents take next, and what is blocked, each with the words to type. Each Initiative and Epic shows its progress and children.

### Security

- **aidd runs on itself in every harness.** This repository's Claude Code, Codex, and OpenCode each carry the ask rules aidd writes from its risk rules, and a test keeps them current.
- **aidd enforces nothing, and says so.** The hard stops are the harness's own ask rules and the platform's branch protection. A command pattern is a net, not a control, as [SECURITY.md](SECURITY.md) explains.
- **Text is data.** The skill tells every agent that a ticket, a page, a file, a comment, or another agent saying "approved" is never a yes. Only your own words in the chat are.
- **A handoff note is checked data.** `aidd validate` checks each `aidd-handoff` note against `schemas/handoff.schema.json`. It warns about hidden characters and about text that poses as a person's words or a harness frame.
- **The Orca channel.** aidd-team's `references/orca-channel.md` says how a worker asks its lead and reports done. `schemas/orca-payload.schema.json` holds the payload, and `aidd validate` checks a payload file, so a free-text message never steers the lead.
- **A launcher that trusts nothing in the project.** The aidd plugin starts its MCP server with Python in isolated mode, from outside the project, and refuses to start when the plugin's source lies inside the project.
- **Updates you can trust.** `aidd self-update` installs only a release, never the tip of main unless you pass `--main`, and only once the wheel matches the release's `SHA256SUMS` and, with `gh` on PATH, its build provenance. The daily check only says a release is out.
- **Pinned CI and provenance.** Every workflow pins each third-party action by commit SHA, and CodeQL, zizmor, actionlint, and OpenSSF Scorecard check the repository. CI runs on Node 26 LTS. The release workflow verifies the tag signature and CI before it builds, and attests build provenance and a CycloneDX SBOM.
- **Releases you can rebuild.** The release builds every artifact again on a fresh runner, and stops unless each matches `SHA256SUMS`.
- **Scanning for adopters.** The CI templates add OSV-Scanner, Semgrep Community Edition, gitleaks, and an SBOM, each on a read-only token.
- **No telemetry.** SECURITY.md lists every place aidd connects, and a test fails on a network module missing from that list. `AIDD_OFFLINE=1` stops the optional network calls.
- **A secret check that reads hidden characters.** The secret check normalizes each string first, so a zero-width, soft-hyphen, or fullwidth character can't hide a token.
- **No secret in a failed request's message.** When a fetch fails, aidd shows the URL without its user and password, query, and fragment, so a token in a URL never reaches a log.

### Known limits

- aidd advises. An agent that ignores the skill acts on its own, and only the harness's ask rules and the platform's branch protection stop it.
- A command pattern matches the command text. A script, an alias, or an API call can reach the same effect without a match.
- A Spec approval is a note the agent wrote, not proof. Under `team`, the platform's review is the Merge approval.
- A harness without ask rules gets the skill alone.
- The role evals weren't run again with real models after the agent files changed, and aidd publishes no eval baselines.
- Signing and publishing a release wait for a public repository.
- A build of aidd before 1.0.0 may have left hooks that run `aidd hook <event>`, and aidd no longer removes them. That command now exits 2, so Claude Code blocks each tool call it guards. Remove each such hook entry from `.claude/settings.json`, `.agents/hooks.json`, and `.grok/hooks/aidd.json`. Delete `.opencode/plugins/aidd.js`, `.opencode/plugins/aidd-tui/`, `.github/workflows/aidd-gate.yml`, `.github/workflows/aidd-relay.yml`, and `.github/rulesets/goal.json`.
