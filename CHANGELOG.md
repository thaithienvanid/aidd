# Changelog

This file lists every notable change to aidd.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The method, the schemas, the risk rules, the CI templates, the skill, and the team plugin share one version. Every config carries `aidd_version`. [CONTRIBUTING.md](CONTRIBUTING.md#versioning) says what counts as a patch, a minor, or a major change. An upgrade within a major version never turns an approved Spec's frozen test red ([the promise](CONTRIBUTING.md#frozen-tests)).

## [1.0.0] - Unreleased

AIDD, short for AI-Driven Development, is a method for delivering software with AI agents. Agents do the work and follow one loop, and you decide the risky steps. aidd is the open-source toolkit that runs it. It's a command-line tool with no runtime dependencies, a skill that coding agents read, an optional delivery team of agent roles, and a standards library. aidd advises and enforces nothing. This is the first release, so everything below is new.

### Added

#### The method and the loop

- **[One loop](docs/METHOD.md) for every change.** It runs Plan, Specify, Spec approval, Implement and Verify until green, Review, Merge approval, Merge, Roll out, and Learn. Six stages group its steps for you, and you decide at each gate. A Task retries at most 3 times, a flaky test is a finding, and new behavior goes red before green.
- **Routes as advice.** `aidd risk --paths` sizes a change by what it touches, as `minor`, `normal`, `major`, or `emergency`. The route says whether a Spec comes first: no Spec, Spec first, or the emergency route, which repairs production first and writes the Spec after. An area can raise the route, so an edit in `payments` makes the change major. The author may declare higher.
- **The loop fits the work to its risk.** A major change gets a tech spec, a threat model when it touches security, privacy, or data, and a rollout plan. A minor change gets none of them. Each fact in a Spec's documents has one home, and the others link it by id: a threat's row lives in the threat model, and an obligation in the compliance doc. Acceptance ids come from the Spec, and `aidd validate` warns about a linked doc that names one the Spec lacks.
- **Profiles.** `solo` asks for Spec approval on major changes, and asks before anything reaches the default branch. `team` asks for Spec approval on normal and major changes, and leaves Merge approval to the platform's review: the agent opens the PR and stops there. The profile and the route pick the templates together: on `solo`, `aidd new spec` writes the short Spec on every route and `aidd new design-spec` the light variant, with every document the risk triggers still expected. `--full` writes every section.
- **The Spec** is the work item and the contract, `type: spec` in its front matter. It holds the intent, its `change_type` (a Conventional Commits type), the Acceptance, the scope, the tests, the risk, the rollback, an observe window, and a cost estimate that `aidd validate` checks against `project.budget.max_infra_per_month`. Its status runs from `draft` to `ready`, `approved`, `in_progress`, `in_review`, and `done`, or ends at `rolled_back` or `cancelled`.
- **Acceptance tests first, unit tests with the code.** In Specify, the verifier writes only the acceptance tests, each red on base. That is at most one per Acceptance item, black-box at the public edge, and one per authorization matrix cell and abuse case. Spec approval freezes them. The developer writes the unit and integration tests with the code, inside its Task's scope, and never edits a frozen test. `aidd new spec --paths` leaves a bare `tests/` out of that scope and names the unit-test folder. A gap Verify finds returns to Implement, where the developer adds the test with the fix. A Spec has one test mode, so `aidd validate` names the fix for a Spec that still sets `tests.mode`. The MVP's walking skeleton opens in the local preview once its acceptance tests pass, and the lead reports the time to first usable.
- **Spec approval, asked plainly.** The agent asks "Approve SPEC-3?" with what the Spec covers. On your yes, it sets the Spec's `status: approved`, `approved_by`, and `approved_at`, and commits it with an `Approved-by` trailer of the same value. Both hold only who said yes, in the form [`approved_by`](.agents/skills/aidd/references/spec.md) takes, and `aidd validate` warns about another form. After that, editing the Spec's tests or Acceptance is `spec.revise`, which asks you again, puts the Spec back to `draft`, and adds a `revisions` entry.
- **A way to change course.** The guide's "Change your mind" gives the words to change a pick, skip a step, go faster, pause, stop, go on, or undo a merge.
- **Headless runs stop at an ask.** In CI or a scheduled run, an `ask` means stop and hand back with a handoff note, because silence is never a yes.
- **An agreement a headless run cannot record.** The run saves the edit as `.aidd/returns/<ID>/agree.patch` and stops. `aidd status` then gives the person one command for their own terminal, which applies it to the Intent alone and commits it with their own `Agreed-by:` trailer. aidd never runs it.
- **A handoff note that keeps its shape.** A note's `stopped_at` starts with a stop code, such as `ask`, `retries`, or `blocked`, alone or with a detail. Each of the skill's stop rules names its code. `aidd validate` names the fix for each note with a missing key, a key aidd does not read, a status that is not a Spec status, or no stop code. Each team command's lead ends with a note that passes it.
- **The Intent, for work bigger than one Spec.** The team writes it from your brief, never over it, as phases of slices, and you agree to it once. A slice is one line until its work starts.
- **An Intent traces your brief.** Its `## Brief coverage` table has a row for each success criterion and hard constraint you wrote. Each row names its proof, such as a slice's acceptance line (`SPEC-1 A3`) or a phase's exit criterion (`exit: P1`), the question the team asked you, or your non-goal. `aidd validate` checks each row, and that a named line of the first slice exists. The first slice also carries 2 to 5 acceptance lines and its order of work. A builder can start it the day after you agree. The product manager asks before it drops, cuts, or softens a decision your brief records, and never re-asks what it settled.
- **Interfaces and deprecations between Specs.** A Spec lists the interfaces it `provides` and `consumes`, by name. When a Spec that provides one is revised, `aidd status` names the open Specs that consume it, so their owners hear first. A Spec's `deprecations` names what it deprecates and its sunset, and a passed sunset warns until a Spec that removes it lands.
- **Open questions and unplanned work.** While a Spec asks for approval, `aidd validate` names each open question it still lists. Once the Spec is approved, it names each file the change alters that no Task's scope, test, design file, or linked doc names.
- **Decision tables and avoided words.** The Spec template turns a business rule with three or more conditions into a decision table, with one Acceptance id per row. `aidd validate` warns about a word your glossary says to avoid.
- **A cold reader on the major route.** Before Spec approval, the tech writer reads the Spec with no chat history and lists the terms and steps it assumes, so a gap goes back to the architect.
- **Runbook readiness.** `aidd validate` warns about a linked runbook's unchecked launch-readiness boxes while its Spec is in review.
- **A check kept whole.** The reviewer reads every test change, and its code-review skill makes a weakened check a finding: a new skip or suppression, a deleted test or assertion, or a lowered coverage floor.
- **A kill criterion for a risky assumption.** The product-discovery skill gives each one a result and a date that end or reshape the work.
- **Plain prose.** The plain-language skill tells writers and the reviewer to cut filler, the words that add no meaning, such as "I hope this helps" or a stock "Moreover". A team that wants a warning on a word puts it, three words at most, in its glossary's Avoid column.

#### A standing delegation

- **Let aidd decide for you.** `aidd init --delegate` writes a `delegation` block. The `aidd-team:delegate` role then answers four asks for you, inside limits: Spec approval, a push of the change's own branch, a merge on GitHub at its exact head, and a local merge with no remote. A deploy, a migration, a new dependency, a secret, and a change to what decides stay yours.
- **`aidd delegate check`** recomputes every gate each time: the delegation at the default branch's tip, the command against its exact template, the reserved paths and the deploying workflows, and the evidence. That is GitHub's own `tests` check run and branch rules through read-only `gh api` calls, or, with no remote, its own `aidd test` run in a fresh worktree. `packet`, `hook`, and `stop` complete it, with the MCP tools `delegate_check`, `delegate_packet`, and `delegate_answer`.
- **Claude Code's hook** answers a delegated prompt only when the check passes again on the exact command, and gives no decision otherwise, so the prompt stays. Every other coding agent keeps its ask rules.
- **A delegation says where it stands.** One set on a branch counts only from the default branch's tip. `aidd doctor` and `aidd status` say when the checked-out config holds a `delegation` that the tip does not, and name the next step.
- **Files that steer a test run are reserved.** A change to `sitecustomize.py`, `usercustomize.py`, `pytest_plugins.py`, `tests/__init__.py`, or a `.jest/` folder defers a delegated merge, as `conftest.py` and the `jest` and `vitest` configs already did.
- **Honest history.** A delegated yes writes `Decided-by`, `On-behalf-of`, and `Delegation` trailers, never `Approved-by`, and `aidd status` shows what was decided for you.

#### Risk rules

- **Actions, areas, and levels.** An agent acts by a risk rule's level: `allow` acts, `report` acts and then says what it did, and `ask` waits for your yes. Each action is `resource.verb`, such as `pr.open`, `git.push.force`, or `deploy.run`, with its command patterns and examples that no pattern catches. An area is a named set of path globs, such as `auth`, `payments`, or `personal_data`.
- **One answer for every question.** `aidd risk --paths` gives the route, the lane, the areas hit, and the first step. `aidd risk --command "<cmd>"` gives the actions a command matches and the winning level, `aidd risk --action` gives one action's level, and `aidd risk --list` shows every effective rule. Each answer names where the deciding rule came from: built-in, the profile, the repository's config, or the preset it extends, by path or URL.
- **Built-in rules you can read.** `schemas/risks.json` holds the built-in actions, the areas, and the rules between them. Editing code is `allow`, and `ask` in `auth`, `payments`, `personal_data`, `secrets`, `migrations`, and `risk_rules`. Pushing your own branch is `allow`, and pushing to the default or a shared branch is `ask`. Force pushes, history rewrites, branch deletions, tags, merges, deploys, releases, production data, secrets, messages, and spending money all ask. Each rule says why in its `reason`, which `aidd risk --action` shows on a `why:` line and `--json` returns.
- **Sign-in file names reach the `auth` area.** A file named for login, logout, sign-in, sign-up, a session, a password, a passkey, MFA, or a one-time password, such as `src/login.py` or `app/session_store.ts`, now routes `major` and asks before an edit, wherever it lives. Docs, vendored code, and `*.md` files stay out.
- **Commands read the way a shell runs them.** aidd reads a tool's command without its runner, such as `npx`, `bundle exec`, or `uv run`, and writes each harness's ask rules in every runner form. A setting typed before the command, such as `RAILS_ENV=production`, counts. `git clean -f`, `git stash drop`, `git restore .`, `git push --tags`, `gh repo delete`, `docker push`, and `kubectl delete` ask. A local `git rebase` or `git commit --amend` does not, because the force push that publishes it asks.
- **Tags always ask.** Every `git tag` asks, and so does every way of pushing a tag: by name, under another name, with `--tags` or `--follow-tags` (abbreviated too), or through `push.followTags`.
- **Migrations by where they run.** A migration asks when it runs on a database other people use or with the tool's production flag, such as `prisma migrate deploy`, and when it undoes applied migrations, such as `alembic downgrade` or `rails db:migrate VERSION=0`. Dropping or wiping a database, such as `php artisan migrate:fresh`, is `data.delete`. A plain forward `migrate` on the agent's own database reports, as `migration.run.local`.
- **A yes holds only for what it showed.** When the head, the branch, or the command a question named changes before the agent acts, such as after a rebase, it asks again.
- **Your own rules.** The config's `risks` adds areas, actions, and rules. A rule with a built-in's selector replaces it, so a project can lower a level as well as raise it. An `extends` preset can lock a rule, and `aidd risk` then reports a project's change to it as ignored.
- **Session overrides.** You may lower a rule for one session, such as "don't ask about pushes today". It lasts the session, and goes into the config only when you say so.
- **Environments.** The config's `environments` names each environment by its branches and tags. A push to one is `deploy.run` to that environment, so the question names it, and a rule's `environment` selector changes one environment's level. A push never asks less by accident.
- **Fewer asks, from the history.** `aidd risk --suggest` names each `ask` rule a person said yes to every time, at least 10 times, as a rule to consider lowering to `report`. It never names an action a person cannot undo, which `irreversible: true` marks in `schemas/risks.json`, such as a force push, a deploy, or a message sent. Nor does it name a person's own decision points: Spec approval and revision, Merge approval, a push to the default branch, and an edit to the risk rules. It counts only the records this clone wrote, and a decision the MCP tool wrote only when it names who answered. It only suggests, because the person changes a rule.
- **More actions that report or ask.** `workflow.run` reports a CI workflow run by hand, and one that releases, publishes, or deploys asks. `commit_status.post` asks before `gh api` writes a commit status, a check run, or a GraphQL mutation. `network.listen`, such as `aidd prototype --serve --lan`, reports, so an agent says when any device on the network can reach what it serves.
- **`gh api` is read exactly.** `aidd risk --command` reads a `gh api` call by its parsed arguments, so every flag order is right. A program by its path (`./bin/gh`) or inside a wrapper is read by its name. An action's `api_endpoints` name the endpoints whose write it is, and a config can add its own. Merging a pull request, creating a release, re-running a job, moving or deleting a ref, deleting a repository, commenting, and changing a branch protection now ask or report, and `branch_protection.change` is new. A ref an environment names reaches that environment, as a push does. A GraphQL query from a file or a variable counts as a write, because aidd opens no file a command names. A command that another runs is matched too: `sudo`, `env`, `bash -c`, `nice`, `time`, `timeout`, `xargs`, `eval`, a group, a loop, `$(...)`, and every separator. The patterns that said the same in each action's `commands` are gone, so `api_endpoints` is the one owner, and a read no longer asks.
- **Changing a repository's settings asks.** The new `repo.settings.change` asks before `gh repo edit`, `archive`, `unarchive`, or `rename`, a `PATCH` or a transfer of a repository through `gh api`, or the GraphQL update, archive, or unarchive mutation. Making a repository public exposes its code, and archiving it is hard to undo. Your own profile (`PATCH user`) stays allow.
- **Reading a secret file asks.** `secret.use` asks before a common reader, such as `cat`, `grep`, `source`, or `cp`, reads a file that holds secrets, from its own list in `schemas/risks.json`, such as `cat .env`. Claude Code, Grok Build, and Qwen Code also ask before their own file-read tool reads one. The list holds key stores, mobile config files such as `google-services.json`, and every file under a `secrets/` folder or named `secrets.*` or `credentials.*`, so an extension aidd has never seen asks. Source code, such as `credentials.py` or `src/secrets/client.ts`, is left out, and Claude Code carves it back out too. A file named `secrets.<ext>` asks whatever its extension, such as `settings/secrets.py`. An example file, such as `.env.example`, and a public key, such as `id_rsa.pub`, stay allowed, and `cp .env.example .env` reads only the example. Code that handles secrets, such as `src/secrets/client.py`, is no secret file, so reading it never asks, and editing it still asks in the `secrets` area. A grep-like reader's pattern and an output redirection's target name no file it reads, while the file after `<` and the file `-f` gives are read. When a grep-like reader has an option aidd does not fully understand, its first word may be a file too, so it counts.
- **A local merge into the default branch asks.** The new `git.merge` is a `git merge` that lands other work, `--ff-only` too, or a `git pull` with any word that is no option, such as `git pull origin feat`, a URL, or a path. It asks while the default branch is checked out, read from git as a push's branch is, and is allowed on your own branch. `--abort`, `--quit`, a `git pull` with only options, and a merge of the branch's own upstream land nothing. `pr.merge`, a PR/MR merged into its base, asks whatever branch you name. `aidd risk --command --folder <path>` and the MCP `risk` tool's `folder` read the branch where the command runs, when that is not the session's folder. A harness rule cannot see the branch, so the skill and `aidd risk` carry this ask.
- **An action with no branch takes its highest level.** `aidd risk --action` with no `--branch` answers the action's highest level on any branch, with a note, so `git.push`, whose rules all name a branch, asks instead of reading as no rule.
- **Outside a repository, the branch is unknown.** `aidd risk` and the MCP `risk` tool answer from the rules in the folder, so a command that turns on the branch, such as a push or a merge, asks. Every `--command` and `--action` answer there notes that the branch and the repository's own rules are unknown, and names the next step: run it inside the repository the change touches, or give `--folder`. A `--folder` that names a checkout reads that repository's config, from anywhere, and it goes with `--command` only. `aidd risk --suggest` says to run it inside one, because the decision records live in a clone. The same holds for every command. One that works on files alone, such as `aidd prototype --new-design`, `aidd new`, or `aidd standard`, runs where you are. One that works on a repository, such as `aidd status` or `aidd test`, says to run it inside one or run `git init` first, never git's own `fatal: not a git repository`.
- **A checkout earlier on the line is read too.** A merge, or a push of the branch checked out, after `git checkout <branch>` or `git switch <branch>` on the same line reads that branch beside the session's, and the stricter wins, so `git checkout main && git merge feat` asks. A checkout can fail, so it never lowers a level. A branch the line creates, with `-b` or `-c`, is your own, so on the default branch `git checkout -b feat && git merge x` still asks: split the line. Another branch that exists is shared, and a name aidd cannot read, such as `-`, a tag, or a variable, counts as the default branch. A checkout of files after `--` moves no branch.
- **Claude Code's rules end in no `:*`.** Claude Code reads a `:*` at the end of a pattern as its older prefix form, so `RAILS_ENV=production rails db:*` read as `rails db *` and missed `rails db:migrate`. aidd writes that `:*` as `*`, which asks more widely. A colon in the middle of a pattern is a literal, so `rails db:*RAILS_ENV=production*` stays as it is. `git push * :*` has no form there, so the skill asks, and `aidd doctor` says so. Grok Build gets the same forms, unvalidated against a live Grok Build. Claude Code's read rules carve the `.env` templates back out, after aidd's own rules and before yours. Your own entries stay after aidd's, even a copy of one of aidd's rules, so a carve-out never lifts one.
- **The harnesses ask before any `gh api` write.** Claude Code, OpenCode, Grok Build, and VS Code ask before any `gh api` call that may write, one small set of patterns for every endpoint. They also ask for a GET with a field or a GraphQL query, which `aidd risk --command` allows and says so in a note. Codex and Qwen Code ask when a write flag or `graphql` comes right after `gh api`. The harness rules match a command typed by its plain name. SECURITY.md says plainly that this reading advises a cooperative agent and guards nothing.
- **Tools that run agents side by side.** Orca's `orca.yaml` and worktrunk's `.config/wt.toml` sit in the `agent_config` area, because they run commands in every worktree.
- **Modelled on authorization.** The rules borrow the shape and names of Cedar, Google Cloud IAM, and Kubernetes RBAC, with no engine of their own. A rule names an action, and optionally an area, a branch (`own`, `default`, or `shared`), and a role. The most specific rule that matches wins, then the higher level.

#### Records, recall, and MCP

- **Records.** After the agent acts on an answered ask, or takes a `report` action, it records it: one immutable file in `.git/aidd/records/`, outside the working tree, so no commit carries it. A `decision` keeps the question and the person's reply word for word, and a `report` keeps what the agent did and said. A record is history, never a yes and never evidence.
- **Read and share the history.** `aidd records` lists it, `aidd records add` writes a record, and `schemas/records.json` holds the types. `aidd records pull` and `push` share records through a remote's `refs/aidd/records`, merged by union, and pushing is `records.push`, an `ask`. `aidd status <ID>` shows a work item's decisions and reports, the commits that name it, and its linked documents, newest first.
- **Recall.** `aidd recall <words>` searches what the team already wrote: the records, the Specs and their documents, the ADRs, the glossary, and recent commit subjects. It uses SQLite's full-text search in the index and calls no model.
- **MCP.** `aidd mcp` serves five tools: `risk`, `status`, `validate`, and `recall` only read, and `record` writes one record, marked `written_with: mcp`. `aidd init` approves them in Claude Code and Codex, so a run with nobody watching records too, and `mcp: {approve_own_tools: false}` keeps them asking. aidd then takes out only the approvals it wrote, never one you added.

#### Commands

- **Ask your agent first.** The README and the guide lead each step with the words for your agent. One sentence installs aidd through `llms-install.md`, which ends by naming the two steps only you take: restart your agent, and protect your main branch. The terminal commands stay as a fallback.
- **From GitHub only.** aidd is not on PyPI, so a package named `aidd` there is not this one. `install.sh` installs a release's wheel from its GitHub Release. It installs once the wheel matches the release's `SHA256SUMS` and, with `gh` on PATH, once its build provenance verifies. `AIDD_RELEASE_URL` points it at a mirror of the releases, which also needs `AIDD_SHA256` or `gh`, because a mirror's `SHA256SUMS` proves nothing alone.
- **Python 3.11 to 3.15**, with the standard library only. Each release also carries the whole CLI as one file, `aidd.pyz`, for a machine where you can't install packages.
- **Three groups of commands, with short help first.** Setup is `init`, `upgrade`, `self-update`, `uninstall`, `doctor`, and `standard`. Work is `status`, `risk`, `records`, `recall`, `new`, `test`, `validate`, `explore`, `prototype`, and `help`. Maintainers and harnesses have `eval`, `mcp`, and `gen-docs`. `aidd --help` lists only the everyday commands, `aidd help --all` lists every one by group, and `aidd help <command>` shows one in full.
- **Setup.** `aidd init --dry-run` reads the repository first, and shows the config `aidd init` writes and the folders where an agent asks before it edits. With no remote, `aidd init` writes no CI files unless `--ci` names them, and says how to add them later. `aidd init` writes the config, the block in `AGENTS.md`, the skill, the harness ask rules, and, with `--team` and `--ci`, the team and the CI test workflow. Run again, it adds only what's new, such as another agent with `--harness`. `aidd doctor` checks the wiring, `aidd upgrade` keeps the files current, and `aidd uninstall` reverses them. `aidd upgrade --yes` replaces only the text between aidd's own marks in `AGENTS.md` and in the agents' own instruction files, never a person's own text. Each section has an opening mark and an end mark (`<!-- aidd -->` and `<!-- /aidd -->`). A section an older aidd wrote has no end mark, so upgrade replaces it only when its text is one aidd shipped, and else reports it and leaves it. A mark in a code fence is no mark, and a file keeps its line endings. and `aidd doctor` warns when that text names a command aidd no longer has, such as `aidd gate`. `aidd upgrade` and `aidd doctor` also report what an older aidd stored and this one does not read, and write nothing to a Spec. #### Files and proof

- **Files you can read.** Every file aidd reads is Markdown with YAML front matter, or YAML, read by its own strict parser. aidd's output for a worktree sits in `.aidd/evidence/` and `.aidd/views/`, which git ignores. `aidd validate --json` and `aidd doctor --json` give the same answers to a program.
- **One word for a type.** Every format says `type`: a work item's front matter, a Spec's `docs` entries and `emergency` block, a proposal's estimate parts, the prototype's comments, the Orca payload, and `aidd new <type>`.
- **Agent evals.** `aidd eval routing` and `aidd eval roles` score an agent on routing scenarios and role scenarios, run by hand with the agent you name. `aidd eval transcript` reads a recorded Claude Code run as the files it opened, its tool calls, and its cost, with no model. The plugin evals cover `code.edit` in `payments`, `spec.revise`, and an edit inside a Task's scope.
- **Cost per pass.** When the agent command emits `stream-json`, `aidd eval routing`, `roles`, and `tasks` score the final answer, record each trial's tokens and cost, and print the dollars per passing trial. `aidd eval report` shows it as `$ per pass`. A trial that reports no cost leaves it blank.
- **Compare two variants.** `aidd eval compare a.jsonl b.jsonl` takes the latest recorded run in each file and pairs the cases both scored. It prints the difference in mean pass@1 with a 95% interval and a plain verdict. The interval is a paired bootstrap with a fixed seed, using the standard library only. The verdict never calls a difference firm below 10 shared cases or below `--repeat 3` in either run, or when an exact sign test on the cases that differ gives p of 0.05 or more.
- **Held-out cases.** About one eval case in five is held out, picked by its id and a fixed seed, so adding a case never moves another. A run of `aidd eval routing`, `roles`, or `tasks` prints the score on the development cases and on the held-out ones, and the record holds both in `sets`.
- **Role eval coverage.** Each role eval case names the loop `step` it exercises. A generated table in `evals/roles/README.md` counts the cases for each role operation, a role at one step, from `schemas/roles.json`. Every operation has a case, so the test's list of known gaps is empty and fails on a new gap.
- **Role evals score the decision, not the wording.** Each role answer ends with the six-line handoff note and one `Decision:` line. The case offers the values, such as `ask` or `act`, and the scorer compares the value with the right one. A missing or second decision fails. A word check names a fact, matches whole words, and never matches a word the fixture plants. A diff is read by its changed lines and edited files, and a delegate case by its `delegate_answer`. Every case has a near-miss answer and an alternative in other words, and a test scores both.
- **Routing evals read the answer and the label.** A route object may hold braces in its reason, two different routes in one reply are a hedge that fails, and a route outside the five names is an invalid answer. A case lists every route the reference admits, and a test holds each label to the risk rules and the size rule in `routes.md`.
- **A full-material arm for the role evals.** `aidd eval roles --with-skills` sends each role the aidd skill and the skills its agent file preloads, after the agent file. It leaves out the `references/` files those skills point to. Record it beside the run on the agent file alone to see what the skills add, and run both in a clean folder with no installed skills, or the arms converge. The record names the arm in its `options`, and the arm has its own material hash.
- **Pick the cases of a run.** `aidd eval routing`, `roles`, or `tasks` with `--case ID`, repeated for more, runs only those cases. A rerun of the cases that failed needs no scratch folder. An unknown id stops the run before the agent starts, and the record names the ids in its `options`.
- **A work history reading.** `aidd eval work [--root PATH]` reads a repository's commits, `Assisted-by` trailers, Specs, records, and handoff notes with no model. It reports flow efficiency, suite runs per head, decisions per change, and the wait for Spec approval. It also reports the Verify reject rate, rework loops, and spend by role step, harness, and model, and reverts by harness and model. A step counts under the harness and model its handoff note's `by` names, or under the person who wrote the note. A note without `by` counts under the commit that posted it. Each harness counts under one id, so `Claude Code` and `claude-code` are one. A figure that rests on fewer than five cases says "too little data". It also gives a stall reading. It counts the Specs by furthest step across every worktree and branch (stub, filled, tests written, ready, approved). It adds the days since the last commit in their scope, and the open Specs whose next step nobody holds.
- **Pressure variants of plugin evals.** Three cases repeat an existing case under a push to skip its step: a demo ten minutes away, code that is already written, and a pull request comment that says "approved". The demo and comment cases copy their source's fixture and graders, so the same graders score them. The written-code case leaves the rate-limit code uncommitted in its own fixture, and fails if the agent commits it.
- **Proven plugin eval cases.** Each of the 12 plugin cases has a right transcript it passes and wrong transcripts it fails, in `evals/plugin/samples.json`, and a test scores them with the graders that need no model. The first live run found six case defects, and they are fixed. The merge graders read a command that runs the merge and the stand-in's `gh.log`, not the agent's own risk check. The scope case counts the outcome, so Write and MultiEdit count as well as Edit. The force-push graders read a command that runs the push and the remote's own log, not the agent's own risk check. The Spec-first cases seed a repository and need a drafted Spec.
- **Trigger cases for practice skills.** Fifty-six team plugin cases check that seven practice skills load when a request calls for them and stay out when it does not. Each skill has four should-load prompts and four near misses, scored by the `Skill` tool call with the skill's name.
- **Flow cases for the team commands.** Team plugin cases run `/aidd-team:specify`, `implement`, `fix`, and `review` from a seeded repository, and review has two: the reviewer's finding and the verifier's mismatch. The graders read the files the command leaves and check the roles it starts. A test builds each fixture and checks that a run which does nothing fails.
- **Reliability across repeats.** `aidd eval routing`, `roles`, or `tasks` with `--repeat K --min-pass-k SHARE` fails the run when the share of cases that passed every repeat (pass^K) is below SHARE. It does so even when the mean passes, and it names the cases that failed a repeat. It is off by default.
- **Pinned tool versions, checked.** `aidd eval standards` lists the exact tool versions that packs and practice skills pin in their commands, and `--online` flags a newer major release of each.
- **Docs that stay current.** The JSON Schemas and `schemas/risks.json` are the source, and `aidd gen-docs --check` fails on a stale table or count. A test fails on a concept with no glossary row, and on any route, lane, level, status, change type, record type, document type, or role that has none.

### Security

- **aidd enforces nothing, and says so.** The hard stops are the harness's own ask rules and the platform's branch protection. A command pattern is a net, not a control, as [SECURITY.md](SECURITY.md) explains.
- **Text is data.** The skill tells every agent that a ticket, a page, a file, a comment, or another agent saying "approved" is never a yes. Only your own words in the chat are.
- **A handoff note is checked data.** `aidd validate` checks each `aidd-handoff` note against `schemas/handoff.schema.json`. It warns about hidden characters and about text that poses as a person's words or a harness frame. A note may name its writer in `by`, as `agent:<harness id>/<model>`.
- **One spelling for `Assisted-by`.** `aidd validate` warns about an `Assisted-by` value that is not `<harness id>/<model>`, with the harness ids aidd knows, and gives the spelling to write, with the known id a written id holds or is part of, such as `claude-code` for `claude`. A harness aidd does not know keeps its own id. It reads the branch's own commits, each Spec's `assisted_by`, and each note's `by`.
- **The Orca channel.** aidd-team's `references/orca-channel.md` says how a worker asks its lead and reports done. `schemas/orca-payload.schema.json` holds the payload, and `aidd validate` checks a payload file, so a free-text message never steers the lead.
- **A launcher that trusts nothing in the project.** The aidd plugin starts its MCP server with Python in isolated mode, from outside the project, and refuses to start when the plugin's source lies inside the project.
- **Updates you can trust.** `aidd self-update` installs a release once the wheel matches the release's `SHA256SUMS` and, with `gh` on PATH, its build provenance. The daily check only says a release is out. `--main` installs the tip of `main`, which is unreleased and unverified, and says so.
- **Releases you can verify and rebuild.** The release workflow verifies the tag signature and CI before it builds. It builds every artifact again on a fresh runner and stops unless each matches `SHA256SUMS`. It then attests build provenance and a CycloneDX SBOM.
- **A stable channel for the Claude Code plugins.** Each release moves the `stable` branch to its commit, fast-forward only, so `/plugin marketplace add thaithienvanid/aidd#stable` gets a plugin update only with a release. Once that branch exists, `aidd init` adds the marketplace at `stable`, and `aidd upgrade` moves an entry init wrote with no branch. Until the first release there is no `stable` branch, so the marketplace follows `main`, and `aidd doctor` says so.
- **Pinned CI.** Every workflow pins each third-party action by commit SHA, and CodeQL, zizmor, actionlint, and OpenSSF Scorecard check the repository. Each step that runs the Claude Code CLI sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, so it sends no telemetry or error report and never updates itself.
- **Scanning for adopters.** The CI templates add OSV-Scanner, Semgrep Community Edition, gitleaks, and an SBOM, each on a read-only token.
- **No telemetry.** SECURITY.md lists every place aidd connects, and a test fails on a network module missing from that list. `AIDD_OFFLINE=1` stops the optional network calls.
- **Every file outside the repository, listed.** SECURITY.md names each file aidd writes outside the repository: the MCP launcher, aidd's cache folder, the temporary folders it removes, and the installer's own venv. A zipapp's extracted data that no zipapp has used for two weeks is removed when another zipapp extracts its own, so a new release's 6 MB never piles up.
- **A secret check that reads hidden characters.** The secret check normalizes each string first, so a zero-width, soft-hyphen, or fullwidth character can't hide a token.
- **No secret in a failed request's message.** When a fetch fails, aidd shows the URL without its user and password, query, and fragment, so a token in a URL never reaches a log.

### Known limits

- aidd advises and enforces nothing. An agent that ignores the skill acts on its own, and only the harness's ask rules and the platform's branch protection stop it.
- Only the <!-- aidd:gen count:harnesses -->14<!-- aidd:end --> coding agents aidd supports are detected, and only six of them get ask rules. Any other agent reads the skill through `AGENTS.md` and `.agents/skills/aidd/`, and there the skill alone carries each ask.
- A command pattern matches the command text. A script, an alias, or an API call can reach the same effect without a match.
- A Spec approval is a note the agent wrote, not proof. Under `team`, the platform's review is the Merge approval.
- aidd publishes no eval baselines, and the role evals have not run with real models against this release's agent files.
- Signing, attesting, and publishing a release need a public repository, so they wait for one.
- aidd does not remove the hooks that an early build from `main` may have left, which ran `aidd hook <event>`. That command exits 2, so Claude Code blocks each tool call such a hook guards. If you installed aidd from `main` before this release, remove each such hook entry from `.claude/settings.json`, `.agents/hooks.json`, and `.grok/hooks/aidd.json`. Delete `.opencode/plugins/aidd.js`, `.opencode/plugins/aidd-tui/`, `.github/workflows/aidd-gate.yml`, `.github/workflows/aidd-relay.yml`, and `.github/rulesets/goal.json`.
